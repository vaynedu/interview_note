# 三层考察框架:业务模型 / 系统设计 / 技术架构

> **核心思想**:把面试考察分成三层,**区分"背八股"和"真做过 / 真想过系统"**——
> 业务模型看抽象能力,系统设计看边界能力,技术架构看落地能力。

## 〇、一句话总览

```text
业务模型:你到底在解决什么业务问题?
系统设计:你怎么把业务问题拆成系统能力?
技术架构:你用什么技术手段保证性能、稳定性、一致性?
```

**为什么这样分**:
- 大多数候选人**一上来就讲技术方案**(Redis、Lua、MQ),但说不清自己在解决什么业务问题
- 真正的资深工程师能**自上而下**:先定义业务口径 → 再拆领域边界 → 最后谈技术权衡

## 一、第一层:业务模型(考抽象能力)

**考察**:候选人是否理解**业务对象和业务规则**。

### 1.1 提问示例(电商库存)

```text
商品是什么?
SKU 和 SPU 怎么区分?
库存是什么?
可售库存、锁定库存、已售库存分别是什么?
什么时候扣库存?
下单扣、支付扣、发货扣有什么区别?
什么叫超卖?
什么叫少卖?
取消订单怎么释放库存?
```

### 1.2 这一层看什么

> **看候选人有没有业务抽象能力**。

**判断信号**:
- ✓ 能用业务语言准确定义对象(SKU vs SPU、库存承诺量 vs 履约能力)
- ✓ 能说清业务规则的边界(下单扣 vs 支付扣的业务后果)
- ✓ 能区分"超卖"和"少卖"是两种不同的业务事故
- ✗ 只能用技术词汇回答(Redis 扣库存、Lua 防超卖)
- ✗ 说不清"库存承诺量"和"履约能力"的关系

**典型反例**:
> "我们用 Redis 扣库存,Lua 防超卖。"
>
> → 这是技术点,**没回答业务问题**。

**典型正面回答**:
> "库存有 3 个核心概念:可售库存(对外承诺的可卖数量)、锁定库存(下单未支付的占用)、已售库存(支付完成的最终扣减)。
> 我们采用'下单锁定 + 支付扣减'模式,因为业务上接受 30 分钟的支付窗口,
> 超卖会赔客户,少卖会损失 GMV——两边都要防。"

> **一句话**:业务模型层 = **业务专家也能听懂的语言** + **能区分相似概念的边界**(SKU/SPU、可售/锁定/已售)。

## 二、第二层:系统设计(考边界能力)

**考察**:候选人能不能把业务模型**拆成合理的服务和流程**。

### 2.1 提问示例(商品详情页)

**拆领域**:

```text
商品域:SKU / SPU / 类目 / 属性 / 上下架
价格域:销售价 / 会员价 / 渠道价 / 价格快照
库存域:可售库存 / 锁定库存 / 库存流水
营销域:优惠券 / 满减 / 活动价
订单域:下单 / 支付 / 取消 / 履约
```

**追问边界 + 链路**:

```text
为什么价格服务不放营销服务里?
为什么库存服务要独立?
订单确认页要调用哪些服务?
哪些是强依赖,哪些是弱依赖?
扇出扇入怎么做?
部分失败怎么降级?
```

### 2.2 这一层看什么

> **看候选人有没有边界意识和链路意识**。

**判断信号**:
- ✓ 能说清服务边界划分的依据(职责单一 / 数据一致性 / 变更频率 / 团队归属)
- ✓ 能区分强依赖和弱依赖(订单 → 库存强依赖,订单 → 营销弱依赖)
- ✓ 能讲清扇出扇入:并行调用 + 部分失败降级策略
- ✗ 把所有逻辑塞一个"订单服务"里
- ✗ 说不清为什么价格不能放营销服务

**强弱依赖的判断**:

```
强依赖:失败必须整体回滚(订单 → 库存)
弱依赖:失败可降级或跳过(订单 → 推荐 / 积分 / 风控的非阻塞规则)
```

> **一句话**:系统设计层 = **服务边界 + 强弱依赖 + 链路扇出** + **部分失败的降级策略**。

## 三、第三层:技术架构(考落地能力)

**考察**:候选人能不能把系统设计**落到可运行、可治理的技术方案**。

### 3.1 提问示例(库存扣减)

```text
Redis 预扣减还是 DB 扣减?
Redis Cluster 怎么分片?
Lua 怎么保证原子性?
Redis 主从异步复制会不会丢数据?
min-replicas-to-write 有什么作用?
Redis Cluster failover 时会发生什么?
MQ 异步落库失败怎么办?
如何保证幂等?
如何做库存对账?
```

### 3.2 这一层看什么

> **看候选人有没有工程落地能力**。

**判断信号**:
- ✓ 能讲技术选型的权衡(Redis vs DB、同步 vs 异步、强一致 vs 最终一致)
- ✓ 能讲清失败兜底(MQ 死信 / 对账 / 幂等)
- ✓ 能给出量化数据(QPS / 延迟 / 一致性窗口)
- ✓ 知道**技术方案的代价**(Redis 异步复制可能丢数据)
- ✗ 只会堆名词(Redis + Lua + MQ),说不清为什么这样选
- ✗ 不知道失败场景,只讲 happy path

> **一句话**:技术架构层 = **选型权衡 + 失败兜底 + 量化数据** + **知道代价**。

## 四、递进式追问示例(秒杀库存怎么设计?)

> 把同一个问题从业务到技术挖三层,**就能看出候选人在哪一层就崩了**。

### 第一层:业务模型

```text
库存有哪些状态?
什么时候算卖出?
下单占库存还是支付扣库存?
订单超时怎么释放?
```

候选人如果答**"用 Redis 扣"** → 还没进入业务模型,**停留在技术点**。

### 第二层:系统设计

```text
库存服务和订单服务怎么交互?
库存扣减是同步还是异步?
库存流水怎么设计?
如何避免超卖和少卖?
```

候选人如果答**"调一个 RPC 扣一下"** → 没有边界意识,**没考虑超时 / 重试 / 幂等**。

### 第三层:技术架构

```text
Redis Lua 怎么扣?
DB 如何兜底?
MQ 消息丢了怎么办?
Redis failover 丢数据怎么办?
热点 SKU 怎么抗?
多机房怎么设计?
```

候选人如果答**"Redis Cluster + Lua + MQ"但说不清失败场景** → 没有落地能力,**只会画图不会扛事故**。

## 五、判断标准

### 5.1 好的回答(自上而下)

```text
✓ 先定义业务口径(库存有 3 种状态、下单锁 + 支付扣)
✓ 再拆领域边界(库存服务为啥独立、和订单怎么交互)
✓ 最后谈技术方案和权衡(Redis Lua + DB 兜底 + 对账,讲清楚每个选择的代价)
```

### 5.2 差的回答(只有一层)

```text
✗ 一上来就说 Redis + Lua + MQ
✗ 但说不清库存模型、订单状态、失败补偿
✗ 追问"为什么这样选"答不上来
✗ 追问"失败怎么办"只能讲 happy path
```

### 5.3 一句话核心

```text
业务模型看抽象能力,系统设计看边界能力,技术架构看落地能力。
```

### 5.4 再狠一点

```text
只会讲技术架构,不讲业务模型 → 是堆技术
只会讲业务流程,不讲技术架构 → 落不了地
能从业务模型推导系统设计,再从系统设计推导技术架构 → 才是真有自己的理解
```

## 七、面试官的用法(评估候选人时)

```
1. 先从一个业务场景切入(秒杀库存 / 优惠券 / 评论系统)
2. 第一层试探:让候选人讲业务模型
   → 答不出 → 停留在技术点 → 直接 P5- 评估
   → 答出来 → 继续第二层
3. 第二层追问:服务边界 + 强弱依赖 + 失败降级
   → 边界划不清 → P5-P6 边缘
   → 能讲边界 + 强弱依赖 → 继续第三层
4. 第三层追问:技术选型 + 失败兜底 + 量化数据
   → 只会堆名词 → P6 普通
   → 能讲权衡 + 失败 + 量化 → P7 资深
5. 最后看能不能闭环:
   → 技术方案 → 反推系统设计 → 反推业务模型
   → 能闭环 → 真有自己的理解
```

## 八、候选人的用法(准备面试时)

```
拿出简历每一个项目点,问自己三个问题:

1. 这个项目解决的业务问题是什么?
   (用业务语言讲清楚,不出现 Redis/MQ/MySQL)

2. 我把它拆成了哪几个服务?边界是什么?哪些强依赖?
   (服务清单 + 边界依据 + 强弱依赖 + 失败降级)

3. 关键技术选型是什么?为什么这样选?代价是什么?
   (选型理由 + 失败场景 + 量化数据)

三个都能讲清,这个项目点能撑住资深面试追问。
任一个崩盘,准备就是不充分。
```

## 九、一句话核心(全篇精炼)

> 三层考察 = **业务模型(WWDR/抽象)→ 系统设计(边界/链路)→ 技术架构(选型/兜底/量化)**;
> **好回答自上而下**(先定义业务口径,再拆领域,最后讲技术权衡),
> **差回答只有底层**(一上来 Redis+Lua+MQ,说不清业务和边界);
> 能在三层之间闭环推导,才算真有自己的理解——这是 P6 → P7 的分水岭。
