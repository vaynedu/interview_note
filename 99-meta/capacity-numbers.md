## 一、估算公式（必会算盘）

### 1.1 DAU 推 QPS（最高频）

```
公式: 平均 QPS = DAU × 人均 PV/天 / 86400

业务系数（人均 PV/天）:
  - 新闻资讯       20-50 PV
  - 电商           5-15 PV（含搜索、详情、列表）
  - 社交 / IM      100-500 (消息收发)
  - 短视频         30-100 (含刷流)
  - 游戏           10-30
  - 工具类         3-10
  - 后台管理       10-30

峰值系数（× 平均 QPS）:
  - 一般业务      3-5x
  - 电商日常      5x
  - 电商大促      10-30x
  - 秒杀          100-1000x（瞬时）
  - 直播首页      峰值集中在开播前 5 分钟

举例: 1000w DAU 电商
  日 PV = 1000w × 8 = 8000w
  平均 QPS = 8000w / 86400 ≈ 926
  日常峰值 = 926 × 5 = 4600 QPS
  大促峰值 = 926 × 20 = 1.8w QPS
```

### 1.2 QPS → 带宽

```
带宽（bps）= QPS × 平均响应大小（B）× 8

平均响应大小经验值:
  - API JSON 响应       2-10 KB
  - 网页 HTML           20-50 KB
  - 图片                100 KB - 1 MB
  - 短视频              2-10 MB
  - 文件下载            几 MB - GB

举例: 1w QPS × 10 KB = 10w KB/s = 100 MB/s = 800 Mbps
     10w QPS × 10 KB = 8 Gbps
     1w QPS × 2 MB（短视频）= 160 Gbps（必须 CDN！）
```

### 1.3 QPS → 并发连接数（小定律 Little's Law）

```
并发连接数 = QPS × 平均响应时间（s）

举例:
  10w QPS × 100ms = 1w 并发
  10w QPS × 1s    = 10w 并发（慢接口要小心）
  100 QPS × 5s    = 500 并发（长接口）

含义: 设计连接池 / Nginx worker_connections / DB 连接池都看这个
```

### 1.4 写 QPS → IOPS

```
IOPS = 写 QPS × 单次写 IO 数

MySQL 写一次的 IO（顺序+随机混合）:
  - redo log    1 (顺序写)
  - binlog      1 (顺序写)
  - undo log    1 (随机)
  - 数据页      1-3 (随机, 看是否命中 buffer pool)
  - 索引页      0-2

总计: 一次 INSERT 大约 4-10 IO

举例: MySQL 写 5000 QPS → 2-5w IOPS（接近 SSD 上限）
     → 这就是为什么 MySQL 写 1w+ 需要 NVMe
```

### 1.5 数据量 → 存储

```
原始数据 → 实际占用:

行数 × 单行字节 = 原始数据
+ 索引膨胀（每个二级索引 ≈ 主键大小 × 行数）
+ 副本（主 + 从 + 异地）= × 3
+ 历史 / 归档       = × 2
+ 增长预留          = × 1.5-3（看周期）
+ 文件系统 / page 开销 = × 1.2

最终 = 原始 × 5-10

举例:
  订单表: 1 亿行 × 1 KB = 100 GB 原始
  + 5 个二级索引（每个 8B 主键）× 5 = 4 GB
  + 副本 × 3 = 312 GB
  + 增长 3 年 × 3 = 1 TB
  → 实际规划 1-2 TB
```

### 1.6 机器数估算

```
所需机器 = 峰值 QPS / 单机 QPS / 水位

水位经验:
  - 日常运营       0.5（留 50% 余量给波动）
  - 大促预备       0.3-0.4（留更多）
  - 极限节省       0.7（高风险）

举例: 峰值 10w QPS / 单机 5000 QPS / 0.5 水位 = 40 台
```

| **单 SQL 修改行数** | < 1w | 锁范围 / binlog 大小 |

### 2.3 配置经验

| 配置 | 默认 | 生产推荐 | 备注 |
| --- | --- | --- | --- |
| **max_connections** | 151 | **1000-5000** | 每连接 ~10 MB 内存（含线程栈）|
| **innodb_buffer_pool_size** | 128 MB | **物理内存的 60-80%** | 16 GB 内存 → 10-12 GB |
| **innodb_log_file_size** | 48 MB | 1-2 GB | 大事务 / 高写入 |
| **innodb_flush_log_at_trx_commit** | 1 | 1（强一致）/ 2（性能）| 0/2 可能丢秒级事务 |

| **wait_timeout** | 28800（8h）| 600-1800（10-30 min）| 连接复用 |
| **long_query_time** | 10s | **1s** | 慢日志告警 |

### 2.4 主从延迟红线

| 延迟 | 状态 | 应对 |
| --- | --- | --- |
| < 100ms | 健康 | 无 |
| 100ms - 1s | 注意 | 监控 |
| 1s - 10s | 告警 | 排查（大事务 / 主从规格不一致 / 网络）|
| > 10s | 危险 | **暂停切流**（避免读到旧数据 + 故障切换可能丢数据）|

```
  2   12w 行
  3   1.4 亿行
  4   160 亿行

  500w-2000w 行就接近 3 层临界 → 拆表线
```

### 3.3 内存占用经验

| 数据结构 | 单元素内存（小数据）| 备注 |
| --- | --- | --- |
| **String（< 44B，embstr）** | ~56 B | 含元数据 |
| **String（> 44B，raw）** | value + ~80 B | 两次 malloc |
| **List（listpack 编码）** | ~10 B / 元素 | 紧凑 |
| **List（quicklist）** | ~20 B / 元素 + 链表开销 | 大 list |
| **Hash（listpack）** | ~20 B / 字段 | 紧凑 |
| **Hash（hashtable）** | ~64 B / 字段 | 大 hash |
| **Set（intset，整数）** | 8 B / 元素 | 极省 |
| **Set（hashtable）** | ~60 B / 元素 | |
| **ZSet（listpack）** | ~30 B / 元素 | |
| **ZSet（skiplist + dict）** | ~85 B / 元素 | 双索引 |
| **Bitmap** | **1 bit / 元素** | 100 万用户 ≈ 125 KB |
| **HyperLogLog** | **12 KB / key（固定）** | 估算亿级 UV |

**估算举例**：
```
1 亿用户存"是否签到":
  - 用 Hash: 1 亿 × 64 B = 6 GB
  - 用 Bitmap: 1 亿 / 8 = 12 MB
  → Bitmap 节省 500x

10 亿 PV 估算 UV:
  - 用 Set 精确去重: 10 亿 × 60 B = 56 GB
  - 用 HLL（0.81% 误差）: 12 KB
  → HLL 节省 500w 倍
```

### 3.5 大 key 检测命令

```bash
# 扫描大 key（生产慎用，--bigkeys 抽样）

```

```
中流量服务: 4C8G  → 5k-1w QPS
大流量服务: 8C16G → 1-3w QPS
极致优化:   16C32G + 调度优化 → 5w+ QPS

经验: CPU 是瓶颈 → 加核; 内存富余 → 别浪费
```

## 七、网络 / 磁盘 / CPU 基线

### 7.1 延迟尺度（必背）

```
L1 cache hit          0.5 ns
L2 cache hit          7 ns
分支错误预测           5 ns
Mutex lock/unlock      25 ns
主内存随机访问         100 ns
                       
压缩 1 KB（zlib）      3 μs
SSD 随机读             150 μs
SSD 顺序读 1 MB        1 ms
内网 RTT               0.5 ms
机械硬盘随机读         10 ms
跨城 RTT（同国）       30-50 ms
跨国 RTT               150-300 ms
跨洲 RTT               200-500 ms

经验:
  - 跨网络调用 = 不要做（能本地做就本地）
  - 跨城 RTT > 内存访问 10w 倍
  - 一次 HTTP 请求 ≈ 100w 次内存操作的时间
```

## 八、业务场景估算样板（套路）

### 8.1 电商秒杀（100w 用户抢 1w 件 iPhone）

```
时间窗口: 1 秒抢光

第一层 - 用户流量:
  100w 用户瞬时点击
  → 假设 80% 真实发起请求 = 80w 请求/秒
  → 实际命中后端: 80w QPS（不可承受）

第二层 - 接入层削峰:
  CDN + Nginx + 限流: 削到 10w QPS
  
第三层 - 业务逻辑:
  Redis Lua 原子扣库存: 10w QPS
  库存 1w 件 → 0.1s 售罄
  
第四层 - 异步落库:
  消息队列削峰填谷
  MySQL 写入 1k-3k TPS
  10w 订单 → 50s 全部落库

带宽估算:
  10w QPS × 5 KB（请求 + 响应）= 4 Gbps
  CDN 静态化页面 → 实际后端带宽 < 1 Gbps

机器估算:
  Nginx 接入: 10w / 5w QPS = 2 台 × 2 = 4 台
  Redis: 5w QPS × 2 = 10w（单机扛得住，加副本）
  MySQL: 3k TPS（单机够用）
```

### 8.2 IM 系统（1000w DAU）

```
长连接数:
  1000w DAU × 50% 同时在线 = 500w 长连接
  单接入机 100w 长连接 → 5-10 台接入机
  
消息量:
  人均 50 条/天 = 5 亿/天
  平均 5 亿 / 86400 = 6000 条/秒
  峰值 ×10 = 6w 条/秒

存储:
  5 亿/天 × 100 B = 50 GB/天
  保留 1 年 = 18 TB
  → 必须分库分表（按 user_id）

群聊扇出:
  100 人群 × 1 条消息 = 100 次推送
  扇出比 ×100
  → 6w 消息/秒 × 100 = 600w 推送/秒

带宽:
  500w 长连接 × 1 KB/min（心跳）= 600 Mbps
  推送 600w × 200 B = 1.2 GB/s = 10 Gbps
```

### 8.3 Feed 系统（1000w DAU）

```
内容生产:
  UGC 率 1% = 10w 内容/天
  
消费量:
  人均 30 PV = 3 亿/天
  平均 3500 QPS
  峰值 ×10 = 3.5w QPS

推拉混合:
  普通用户（< 1w 粉丝）: 推（写扩散）
  大 V（> 1w 粉丝）: 拉（读时合并）
  
Redis Feed 流缓存:
  1000w 用户 × 1000 条最新 × 8 B（id）= 80 GB
  Cluster 4 节点

存储:
  10w 内容/天 × 1 KB = 100 MB/天
  10 年 = 360 GB（小）
```

### 8.4 短视频（1000w DAU）

```
播放量:
  人均 30 视频 = 3 亿 vv/天
  平均 3500 QPS
  峰值 ×10 = 3.5w QPS

带宽（CDN）:
  3.5w QPS × 2 MB（单视频）= 70 GB/s = 560 Gbps
  → 必须 CDN（自建机房扛不住）

存储:
  10w 视频/天 × 50 MB = 5 TB/天
  3 年 = 5 PB
  → 对象存储 + CDN 缓存

转码:
  每视频转 5 个分辨率 = 250 MB
  CDN 边缘节点缓存
```

### 8.5 估算套路总结

```
1. 算用户量 → DAU
2. 算行为量 → 日 PV/事件数（人均 × DAU）
3. 算 QPS  → 日量 / 86400, ×峰值系数
4. 算带宽  → QPS × 响应大小
5. 算存储  → 行数 × 单行 × 副本 × 周期
6. 算并发  → QPS × 平均响应时间
7. 算机器  → 峰值 / 单机能力 / 0.5 水位
```

## 九、典型故障 / 性能"红线"

### 9.1 当出现以下数字，立即报警

| 指标 | 红线 | 含义 |
| --- | --- | --- |
| **MySQL CPU** | > 80% 持续 5 min | 慢 SQL / 死锁 / 高并发 |
| **MySQL 主从延迟** | > 10s | 切流危险 |
| **MySQL 连接使用率** | > 80% | 即将拒绝连接 |
| **Redis 内存使用率** | > 80% | 即将淘汰 |
| **Redis CPU** | > 80% | 大 key / 慢命令 / 单线程瓶颈 |
| **Redis 慢日志** | > 10ms 命令出现 | 大 key / 复杂命令 |
| **Kafka 消费 lag** | > 10w 条 | 堆积 |
| **接口 P99** | > 1s | 异常 |
| **接口错误率** | > 1% | 故障 |
| **机器 CPU** | > 90% | 紧急扩容 |
| **机器内存** | > 90% | OOM 风险 |
| **磁盘使用率** | > 80% | 清理 / 扩容 |
| **磁盘 inode** | > 80% | 小文件爆 |
| **网络丢包率** | > 0.1% | 网络故障 |
| **TCP TIME_WAIT** | > 10w | 短连接过多 |
| **GC 暂停** | > 100ms | 调优 |

### 9.2 容量水位经验

```
日常运营水位: < 50%
  → 留 50% 余量给突发流量

大促预备水位: < 30%
  → 留 70% 余量

报警水位:    > 70%
  → 准备扩容

红线水位:    > 80%
  → 紧急扩容 + 限流

崩盘水位:    > 90%
  → 服务降级 + 熔断
```

## 十、如何验证（不要背数字，要会压测）

### 10.1 压测工具

| 工具 | 用途 |
| --- | --- |
| **wrk** | HTTP 压测，单机几十万 QPS |
| **ab（Apache Bench）** | 简单 HTTP，单机几万 |
| **jmeter** | 复杂场景，GUI |
| **k6 / Locust** | 脚本化压测 |
| **sysbench** | MySQL 压测 |
| **redis-benchmark** | Redis 压测 |
| **kafka-producer-perf-test** | Kafka 压测 |
| **OpenMessaging Benchmark** | 跨 MQ 标准化 |

### 10.2 压测原则

```
1. 单机摸底 → 知道单机极限
2. 找最佳工作点 → CPU 70% 时的 QPS
3. 找崩溃点 → 持续加压直到失败
4. 设置日常水位 → 最佳工作点的 50%
5. 全链路压测 → 真实业务路径

最佳工作点 != 单机极限
  - 极限是不可持续的（CPU 100% 早晚崩）
  - 工作点要留余量给波动 / GC / 突发

经验: 单机 QPS 上限 / 业务 QPS = 2-3x（健康）
     如果业务跑在单机极限附近 → 风险极高
```

### 10.3 不要相信文档数字（包括本文）

```
本文数字都是经验值（业内中位数），实际差异:
  - 业务复杂度: × 0.3 - × 3
  - 硬件规格:   × 0.5 - × 5
  - 数据规模:   × 0.1 - × 10
  - 调优程度:   × 0.5 - × 2

→ 综合下来，实际可能和本文差 10x 以上

正确姿势:
  ✓ 用本文数字做"心算估算"（面试 / 设计阶段）
  ✓ 真上线前必须压测
  ✓ 持续监控生产数据（建立自己的基线）
```

## 十二、面试时如何用这份速查表

### 12.1 估算 4 步法

```
面试官: "设计一个 1000w DAU 的 IM 系统"

第 1 步: 算流量
  1000w DAU × 在线率 50% = 500w 长连接
  人均 50 消息/天 = 5 亿/天 = 6000/s 平均, 6w/s 峰值

第 2 步: 算资源
  长连接: 500w / 100w/机 = 5 台接入机
  消息存储: 50 GB/天 → 一年 18 TB → 分库分表
  推送扇出: 群消息 ×100 = 600w/s 推送

第 3 步: 算瓶颈
  长连接: 接入机内存
  消息: MySQL 写入（拆 / 异步）
  推送: 扇出后的下游能力

第 4 步: 兜底
  限流 / 降级 / 灰度
  监控红线
```

### 12.2 资深加分句

```
✓ "我会先压测，这些数字是经验值起点"
✓ "数量级比精确数字重要，5000 QPS 还是 5w QPS 决定架构选型"
✓ "水位留 50% 余量，应对突发和波动"
✓ "MySQL 单表 2000w 行是经验线，实际还要看索引和访问模式"
✓ "Redis 单机 25 GB 是同步 RDB 时间的考虑（30 分钟左右恢复）"
✓ "QPS / RT / 并发是三位一体，用小定律 N = QPS × RT 互相验证"
```
