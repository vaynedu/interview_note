## Q1 秒杀库存如何防超卖

### 场景设定

> 抖音双 11,iPhone 16 Pro 256GB,库存 10,000 台,预约用户 500 万,开抢瞬间 **100 万 QPS**,3 秒内卖完。要求绝对不超卖,用户体验响应 < 100ms。

### 一句话本质

**Redis Lua 原子扣减 + MQ 异步落库 + 多层限流前置 + T+1 对账兜底**,核心是"不要让 DB 扛压、不要让单 key 扛压、不要相信任何单点"。

### 面试答题节奏(故事版)

> 这是白板答题的主线节奏,5-7 分钟讲完一气呵成。**先讲清楚"为什么不能直接打 DB"建立对比,再给方案,再讲异常和兜底**——比直接堆框架更有说服力。

#### 1. 场景具体化

> 抖音双 11 iPhone 16 Pro 256GB,库存 10,000 台,预约用户 500 万,开抢瞬间 **100 万 QPS**,3 秒卖完。要求绝对不超卖,P99 < 100ms。

#### 2. 如果直接打 MySQL,会怎样?

```sql
SELECT stock FROM inventory WHERE sku_id = 123;
UPDATE inventory SET stock = stock - 1 WHERE sku_id = 123;
```

会有四个致命问题:
- **并发读**:多个请求读到同一个库存值,各自以为还有
- **DB 压力**:100w QPS 直接打 MySQL,连接池瞬间打满(单库 5000 TPS 上限)
- **行锁竞争**:单行 UPDATE 排队,P99 飙到秒级
- **超卖风险**:`stock = stock - 1` 不带条件 → 库存可能变负

所以核心思路:**扣减前置到 Redis,DB 只做最终落库**。

#### 3. 核心方案(一句话)

**Redis Lua 原子预扣 + MySQL 条件更新和唯一索引兜底 + MQ 削峰异步建单 + 超时未支付释放库存**。

流程 6 步:
1. 秒杀开始前,把库存预热到 Redis(`stock:{sku_id}`)
2. 用户请求进来,先做 CDN / 网关 / 应用三层限流 + 资格校验
3. Redis Lua 原子判断库存 + 防重 + 扣减
4. 扣减成功发 MQ `stock_deducted`,**立即返回用户"抢购成功,订单处理中"**
5. 消费 MQ 异步创建订单 + 落 MySQL 库存流水
6. 30 分钟未支付释放预占库存

#### 4. 前置过滤层:Redis 不是第一道防线

Redis 是**最终的高并发判断层**,但不是第一道防线。100w QPS 全打 Redis 是浪费——大部分请求注定抢不到。要在前面层层削峰:

| 层级 | 实现 | 拦截比例 | 作用 |
| --- | --- | --- | --- |
| **L1 网关限流** | 令牌桶 5w QPS / IP 限频 / 验证码 | 50% | 挡爬虫、羊毛党 |
| **L2 应用本地限流** | Sentinel 单实例 1w QPS | 30% | 本机过载保护 |
| **L3 应用本地 token 预扣** | 启动时分发少量库存 token | 30% | 减少打 Redis 的请求 |
| **L4 库存分桶** | 热点 SKU 拆 32 桶散到不同节点 | - | 避免单 key 单节点热点 |
| **L5 Redis Lua** | 原子扣减(最终防线) | 99.99% | 真正的库存判定 |

**本地 token 预扣思路**(高级玩法):
- 1 万库存 → 100 个应用实例各发 50 张 token,留 5000 在 Redis 总池
- 用户请求**先抢应用本地 token**(纯内存,< 1μs)
- 抢到本地 token 才打 Redis 做最终扣减
- 本地 token 耗尽 → 该实例直接返回"已售罄",不打 Redis
- 收益:Redis QPS 从 100w 降到 1-5w

**热点 SKU 分桶**:
- 单 SKU 100w QPS,单 Redis 节点只能扛 10w → 必然热点
- 拆 32 桶:`stock:{sku_id_b0}`..`stock:{sku_id_b31}`,散到不同 Redis 节点
- 用户按 `hash(user_id) % 32` 路由到桶
- 桶空了借相邻桶 / 返售罄(详见 [Q4](#q4-热点-sku-如何拆库存桶))

> **只有通过前置过滤的请求才进入 Redis Lua 做原子扣减**——这是分层削峰的精髓。

#### 5. Redis Lua 原子扣减(核心)

Key 设计:
```
seckill:stock:{sku_id}   = 10000   -- 余量(string)
seckill:bought:{sku_id}            -- 已购用户 set,防重
```

Lua 脚本:
```lua
-- KEYS[1]=stock key, KEYS[2]=bought set
-- ARGV[1]=user_id, ARGV[2]=qty
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2  -- 重复购买
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[2]) then
    return 0  -- 库存不足
end
redis.call('DECRBY', KEYS[1], ARGV[2])
redis.call('SADD', KEYS[2], ARGV[1])
return 1  -- 扣减成功
```

**为什么不会超卖**:Lua 在 Redis 单线程内**原子执行**,"检查库存 → 检查是否买过 → 扣库存 → 记录用户"四步不会被其他请求插进来。

#### 6. MySQL 兜底防线

即使 Redis 已经防了,MySQL 还要加两道兜底,防极端 case(Redis 主从切换 / 数据漂移 / 消费者 bug):

**条件更新防超卖**:
```sql
UPDATE sku_stock
SET available_stock = available_stock - 1,
    locked_stock    = locked_stock + 1
WHERE sku_id = ? AND available_stock >= 1;
-- affected_rows = 1 才算成功
```

**唯一索引防重复下单**:
```sql
ALTER TABLE orders ADD UNIQUE KEY uk_user_sku (user_id, sku_id);
```

#### 7. MQ 削峰异步建单

为什么不同步建单:秒杀瞬间 100w QPS 落订单,MySQL 必崩。

```
Redis 扣减成功
  → 立即返回"抢购成功,订单处理中"(< 50ms 用户感知)
  → 发 MQ stock_deducted
  → 消费者按 5000 TPS 限速消费(削峰 200×)
  → MySQL 落订单表 + 库存流水
  → 发 MQ order_created → 通知 / 物流 / 风控
```

#### 8. 异常处理(资深加分)

| 异常 | 处理 |
| --- | --- |
| Redis 扣成功但 MQ 发送失败 | 本地消息表兜底 + 异步扫描重发 |
| MQ 消息重复消费 | `order_id` UNIQUE,INSERT IGNORE |
| 订单创建失败 | 发补偿消息释放库存 |
| 用户超时未支付 | 延迟消息关闭订单 + 释放预占 |
| Redis 与 MySQL 不一致 | T+1 对账修复(差异 < 0.001%) |
| Redis 完全挂 | 降级 MySQL 单点扣减 + 全局 5000 QPS 限流 |

#### 9. 订单与库存状态流转

```
订单状态:WAIT_PAY ──支付──> PAID
                 ──超时──> CLOSED

库存流转:
  下单:     available -1, locked +1
  支付成功: locked    -1, sold   +1
  超时关闭: locked    -1, available +1
```

### 九维度深度展开(追问储备)

#### 1. 分布式一致性(主战场)

**强一致需求**:库存绝对不能超卖,哪怕系统挂了也不能多卖一台。

**实现方案**:
- **Redis Lua 原子扣减**:`SISMEMBER 防重 → HGET 余量判断 → HINCRBY -1` 一个脚本完成,4-5 行
- **MQ 异步落 MySQL**:Redis 扣减成功后发消息,消费者落 DB
- **T+1 对账**:每天扫 Redis 流水 vs MySQL 流水,差异 < 0.001%
- **极端容灾**:Redis 主挂从切,可能丢失最后几秒数据 → 对账修复

**核心 Lua 脚本**:
```lua
-- KEYS[1]=stock:{sku_id}, KEYS[2]=reserve:{sku_id}
-- ARGV[1]=order_id, ARGV[2]=qty
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 0 end
local remaining = tonumber(redis.call('HGET', KEYS[1], 'remaining'))
if remaining == nil or remaining < tonumber(ARGV[2]) then return -1 end
redis.call('HINCRBY', KEYS[1], 'remaining', -ARGV[2])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

#### 2. 服务治理

- **秒杀接口独立服务**:不与普通下单复用,故障隔离
- **链路打标**:秒杀订单走独立 trace,出问题秒级定位
- **接口分层**:秒杀页 / 详情页 / 结算页各自限流,避免连锁
- **异步化**:同步接口只返回"已抢到 / 未抢到",订单生成异步

#### 3. 缓存与 DB 优化(主战场)

**Redis 数据结构**:
```
stock:{sku_id_b0} → hash
  ├── total: 10000
  ├── remaining: 9876
  └── sold: 124
reserve:{sku_id_b0} → set [order_id_1, order_id_2, ...]
```

**为什么用 hash 不用 string**:
- HINCRBY 原子操作,字段级更新
- 一次读出完整状态,减少往返
- 配合 SADD 实现"防重 + 扣减"原子

**MySQL 兜底**:
- 库存表读写分离,写主库,读从库 + 缓存
- 主库写入控制 < 5000 TPS,削峰后稳态
- 库存行加 `version` 列,DB 直扣时乐观锁

**双层防超卖**:
```
SQL: UPDATE inventory 
     SET sold = sold + 1 
     WHERE sku_id = ? AND sold < total
应用: affected_rows = 1 才算成功
```

#### 4. 异步消息(主战场)

```
Redis 扣减成功 → 发 RocketMQ "stock_deducted"
                   ↓
              下单消费者(限速 5000 TPS)
                   ↓
              MySQL 落 orders 表 + inventory 实扣
                   ↓
              发 MQ "order_created"
                   ↓
       商家通知 / 物流触发 / 风控扫描
```

**关键设计**:
- **消息保序**:按 `sku_id` hash 分区,同 SKU 顺序消费(避免库存负数)
- **消费幂等**:`order_id` UNIQUE 约束,重复消息直接 INSERT IGNORE
- **死信兜底**:消费 16 次失败进 DLQ,人工补偿
- **峰值削峰**:峰值 100w QPS 进 MQ,消费 5000 TPS 稳态

#### 5. 限流熔断降级(主战场)

**四层限流**:

| 层级 | 实现 | 拦截比例 | 用途 |
| --- | --- | --- | --- |
| **L1 CDN/接入** | IP 限频 / 验证码 | 50% | 拦截爬虫 + 羊毛 |
| **L2 网关** | 令牌桶 5w QPS | 80% | 全局保护 |
| **L3 应用** | Sentinel 单 SKU 限流 | 90% | 业务规则 |
| **L4 Redis** | Lua 库存兜底 | 99.99% | 终极防线 |

**排队令牌**:
- 用户先抢"准入券"(Redis ZSet,前 100 万入队)
- 凭券进秒杀链路,挡住大部分无效流量
- 没券的用户直接看到"已售罄"页

**降级开关**:
- 库存查询不准 → 展示"库存紧张"代替具体数字
- 物流查询失败 → 显示"预计 3-5 天"占位
- 评论加载慢 → 直接隐藏

#### 6. 容灾恢复

| 故障场景 | 应对 |
| --- | --- |
| **Redis 主挂** | 哨兵秒级切从,数据可能丢最后 1-3 秒(对账修复) |
| **Redis 集群挂** | 降级 MySQL 单点扣减(QPS 限制)+ 拒绝下单 |
| **MQ 挂** | 本地消息表兜底,DB 落 + 异步扫描重发 |
| **应用挂** | 流量切其他可用区,1 分钟内完成 |
| **整个机房挂** | 跨机房灾备 / 异地多活,DNS 切换 |
| **数据错乱** | 人工 SOP:暂停下单 → 对账 → 补偿 → 恢复 |

#### 7. 监控告警(主战场)

**核心指标**:
```
业务指标:
- 秒杀成功率(目标 > 99.9%)
- 端到端延迟(P99 < 200ms)
- 库存进度(实时大屏)
- 用户抢到率(发奖比例)

系统指标:
- Redis QPS / 内存 / 主从延迟
- MySQL TPS / 慢查询 / 连接数
- MQ 积压(目标 < 1w)
- 应用 GC / CPU / 内存

告警阈值:
- 成功率 < 99% → P0 告警
- DB 延迟 > 1s → P1 告警
- MQ 积压 > 10w → P1 告警
- Redis 内存 > 80% → P2 告警
```

**实时大屏**:库存进度条 / 成功数 / 异常数 / 各 SKU 销售曲线,SRE + 业务 + 老板同步看。

#### 8. 压测与容量评估(主战场)

**预估容量**:
```
峰值 QPS = 预约用户 × 峰值并发率
        = 500 万 × 20%
        = 100 万 QPS

Redis 容量:
- 单节点 10w QPS
- 集群 10 节点 = 100w QPS
- 热点 SKU 分 32 桶 → 单 SKU 也能 100w QPS

MQ 容量:
- Kafka 单 topic 100w TPS
- 分区数 = 100w / 单分区 5w = 20 分区

MySQL 容量:
- 主库写入 < 5000 TPS(削峰后)
- 分库后单库 < 200 TPS

应用容量:
- 单实例 QPS 5000
- 扩到 200 个实例 = 100 万 QPS
```

**全链路压测**:
- **影子流量**:打标的压测请求,与真实流量同链路
- **影子库表**:同结构的影子表,写入压测数据不污染生产
- **流量录制回放**:录历史真实流量,大促前回放验证
- **3 轮压测**:基线(日常 × 1) / 峰值(日常 × 50) / 极限(日常 × 100)
- 提前 1 周开始,每天迭代优化

#### 9. 真实优化经验(主战场)

**踩坑 1:Lua 脚本过长导致阻塞**
- 现象:Redis 单线程被一个长脚本阻塞,其他命令排队
- 优化:脚本控制在 5 行内,复杂逻辑拆 pipeline
- 收益:P99 延迟从 50ms 降到 5ms

**踩坑 2:库存 key 单点热点**
- 现象:某 SKU 单 key 落单节点,瓶颈 10w QPS
- 优化:库存分 32 桶,`stock:{sku_id_b0}` ~ `stock:{sku_id_b31}` 散到不同节点
- 收益:单 SKU 100w QPS(详见 [24-order-system 附录 C](../10-system-design/24-order-system.md))

**踩坑 3:消费幂等失效导致负库存**
- 现象:网络抖动导致消息重投,MySQL `sold = sold + 1` 多扣
- 优化:`order_id` 加 UNIQUE 约束,INSERT IGNORE
- 收益:库存绝不为负

**踩坑 4:对账发现 0.5% 差异**
- 现象:Redis 扣了但 MySQL 没落库
- 排查:MQ 消费失败 + 死信队列没监控
- 优化:DLQ 监控 + 重试机制 + T+1 对账修复
- 收益:差异从 0.5% 降到 0.001%

**踩坑 5:大促结束后 Redis 内存暴涨**
- 现象:reserve set 不过期,内存持续增长
- 优化:SADD 后 EXPIRE 30 分钟,过期自动清理
- 收益:内存稳定在阈值内

### 易错点

- ❌ `Redis DECR` 后再判断 `< 0`:有竞态,必须 Lua 原子
- ❌ 同步落 MySQL:DB 必崩,必须 MQ 削峰
- ❌ 库存 key 只有一个:单节点热点,必须分桶
- ❌ Lua 脚本里跨 key 操作:cluster mode 不支持,要用 hash tag
- ❌ 消费者不做幂等:重投导致库存错乱

- ❌ 限流只在网关:挡不住所有,必须多层
- ❌ 大促前不压测:出故障来不及救

### 追问预案

1. **Redis 完全挂了怎么办?**
   - 降级 MySQL 单点扣减 + 全局限流 5000 QPS
   - 超出限流直接返回"系统繁忙",保住基本可用
   - SRE 紧急切备用 Redis 集群(10 分钟内)

2. **Lua 脚本失败回滚怎么做?**
   - Lua 内部失败不回滚(脚本原子)
   - 业务侧失败:发补偿消息释放库存
   - 兜底:30 分钟超时自动释放

3. **怎么防止脚本被刷?**
   - 网关令牌(准入券机制)
   - 用户限流(单用户 5 次/秒)
   - 风控前置(IP / 设备 / 行为画像)

4. **单 SKU 100w QPS 怎么扛?**
   - 分桶(32 桶散到不同节点)
   - 应用层本地预扣(部分库存提前分发)
   - 排队机制(分批放量)

5. **库存为 0 怎么快速拒绝?**
   - Bloom filter 标记售罄 SKU
   - 应用层本地缓存"售罄"标记 1 秒 TTL
   - CDN 缓存售罄页面

6. **大促结束怎么对账?**
   - T+1 扫描 Redis 流水(SADD 记录)vs MySQL 订单流水
   - 差异 > 阈值 → 告警 + 人工排查
   - 补偿:多扣的退款,少扣的强制库存归零

7. **怎么避免羊毛党刷库存?**
   - 风控前置:IP / 设备 / 账户画像
   - 用户分级:新号、低活号限制参与
   - 滑块验证 / 短信验证
   - 异步风控:下单后秒级判定,识别后冻结

8. **集群扩容怎么不影响秒杀?**
   - 提前预热(开抢前 10 分钟 warm up)
   - 灰度路由(新节点先承接 10% 流量)
   - 配置中心切换(分钟级生效)

### 面试回答版

> 秒杀库存防超卖,我一般不会让请求直接打 MySQL,而是先把库存预热到 Redis。但 **Redis 也不是第一道防线**——秒杀请求会先经过网关限流和应用本地限流,甚至可以把少量库存 token 分发到各应用实例做本地预扣,减少打到 Redis 的请求;对于特别热点的 SKU,还会做库存分桶,避免单 key 落到 Redis 单节点形成热点。
>
> 只有通过前置过滤的请求才进入 Redis Lua,做原子的库存判断、限购判断和扣减,保证并发下不会超卖。扣减成功后发送 MQ 异步创建订单,MySQL 订单表通过 `(user_id, sku_id)` 唯一索引保证用户幂等,库存表用 `available_stock >= qty` 的条件更新做兜底防线。对于未支付订单,通过延迟消息关闭订单并释放预占库存。最后通过库存流水和 T+1 定时对账保证 Redis 与 MySQL 最终一致(差异 < 0.001%)。
>
> 容量上,Redis 单节点 10w QPS,集群 10 节点 100w QPS;热点 SKU 分 32 桶后单 SKU 也能扛 100w。MQ 把瞬时流量削到 5000 TPS 落库。生产里我印象最深的踩坑是 Lua 脚本一定要控制在 5 行内——长脚本会阻塞 Redis 单线程,我们曾经因为这个 P99 飙到 50ms,改成 5 行后降到 5ms。

### 一句话核心

> **Redis Lua 原子预扣防并发超卖,MySQL 条件更新和唯一索引兜底,MQ 削峰异步建单,超时未支付释放库存。**

### 背诵版(更精简)

> 秒杀防超卖核心 4 招:**Redis Lua 原子扣减**(单节点 10w QPS,集群 100w,热点 SKU 分 32 桶)+ **MQ 异步落 DB**(削峰到 5000 TPS)+ **多层限流**(CDN+网关+应用+全局 Lua)+ **T+1 对账兜底**(差异 < 0.001%)。生产踩坑:Lua 控制 5 行内、热点 SKU 必须分桶、消费幂等用 UNIQUE 约束、DLQ 必须监控。容灾:Redis 挂降级 MySQL 单点 + 限流 + 拒绝下单,数据靠对账修复。压测:全链路影子流量 + 3 轮(基线/峰值/极限)。

## Q2 订单系统如何做幂等

### 场景设定

> 抖音电商下单接口,日 2000 万单,峰值 4 万 TPS。前端网络抖动 / 用户连点 / 网关重试 / SDK 自动重试 都会导致同一意图的下单请求重复发送,要求 **同一意图永远只创建一个订单**,误判率 < 0.001%。

### 一句话本质

**前端 request_id + 网关 Redis 防重 + 应用 user_id 复合幂等 + DB UNIQUE 兜底**,五层防御,任一层挡住即可。

### 面试答题节奏(故事版)

#### 1. 场景具体化

> 抖音电商日 2000 万单,峰值 4 万 TPS。前端网络抖动 / 用户连点 / 网关重试 / SDK 自动重试都会让**同一意图**的下单请求重复到达后端。要求同一意图永远只创建一个订单,误判率 < 0.001%。

#### 2. 如果只靠 DB 排查,会怎样?

```sql
SELECT * FROM orders WHERE user_id=? AND sku_id=? AND created_at > NOW() - INTERVAL 5 MINUTE;
-- 没查到 → INSERT,查到 → 返回老订单
```

会有四个致命问题:
- **窄竞态**:两个并发请求都查不到,然后都 INSERT,导致重复
- **DB 压力**:每次下单 SELECT + INSERT,QPS 翻倍
- **业务边界模糊**:5 分钟窗口怎么定?用户真要买 2 份呢?
- **网络重试无法识别**:用户点 1 次,SDK 重试 3 次,业务无法区分"重试"和"再次下单"

核心思路:**用 request_id 标识"同一意图",层层做幂等**。

#### 3. 核心方案(一句话)

**前端 request_id + 网关 Redis 防重 + 应用 user_id 复合幂等 + DB UNIQUE 兜底 + 业务异常告警**,五层防御,任一层挡住即可。

#### 4. 五层幂等防御(核心)

| 层级 | 实现 | 拦截时机 | 备注 |
| --- | --- | --- | --- |
| **L0 前端** | 按钮置灰 + 防抖 | 用户连点 | 体验优化,挡不住网络重试 |
| **L1 网关** | Redis `SETNX req_id` 3 秒 TTL | 快速重试 | < 1ms 决断 |
| **L2 应用** | `request_id ↔ order_id` 缓存 3 分钟 | 业务层重试 | 命中直接返回老订单 |
| **L3 DB** | `UNIQUE KEY uk_user_request (user_id, request_id)` | 终极防线 | 必有 |
| **L4 业务** | 5 分钟内同 user+sku 二次下单告警 | 业务异常 | 风控 + 用户提示 |

**关键认知**:request_id 是**客户端 SDK 生成的、跨重试稳定的标识**——SDK 重试时**必须复用同一个 request_id**,这是整个体系的基石。

#### 5. request_id 怎么生成

- **客户端 SDK 强制必填**:网关校验,缺失直接 400
- **格式**:UUID v4(随机)或 `client_id + nano_timestamp`
- **重试复用**:SDK 内部一次业务调用对应一个 request_id,重试 N 次复用
- **链路追踪**:request_id 注入 trace,跨服务可查

#### 6. DB UNIQUE 兜底(终极防线)

```sql
CREATE TABLE orders (
  order_id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  request_id VARCHAR(64) NOT NULL,
  sku_id BIGINT,
  amount DECIMAL(10,2),
  state VARCHAR(16),
  created_at DATETIME,
  UNIQUE KEY uk_user_request (user_id, request_id)  -- 终极幂等
);
```

**冲突处理(关键)**:UNIQUE 冲突**必须回查老订单返回**,**不能直接 throw error**——网络重试是合法的,用户感知不到差别才对。

```go
if err := db.Insert(order); err != nil {
    if isUniqueConflict(err) {
        existing := db.Query("SELECT * FROM orders WHERE user_id=? AND request_id=?", ...)
        cache.Set(key, existing.OrderID, 3*time.Minute)
        return existing, nil   // 透明返回老订单
    }
    return nil, err
}
```

#### 7. 异常处理(资深加分)

| 异常 | 处理 |
| --- | --- |
| Redis 挂 | 降级 DB UNIQUE 兜底,慢但正确 |
| Redis 数据丢失 | 不影响幂等(DB 是真相) |
| 超 TTL 的重试 | 直接走 DB UNIQUE 兜底,业务无感 |
| 客户端伪造 request_id | 网关签名 + 用户限流 + 风控 |
| 冲突 throw 给用户 | ❌ 反模式,改回查返回老订单 |

#### 8. 容量与监控

```
Redis 容量:4w TPS × 180s = 720w key × 100B ≈ 720MB(3 主 3 从轻松扛)
DB UNIQUE 查询:B+ 树 3 层 < 0.1ms
幂等接口 P99:< 5ms(本地缓存 + Redis)

监控:
- L1 命中率(> 80% 健康)
- L2 命中率(> 15%)
- L3 兜底率(< 1%,> 5% → P0 表示 L1/L2 失效)
- request_id 重复率(陡升 → 客户端 bug)
```

```go
func CreateOrder(ctx context.Context, req CreateOrderReq) (*Order, error) {
    // L1 网关层(假设已通过)
    
    // L2 应用层缓存

        return queryOrder(orderID), nil  // 幂等返回
```

#### 2. 服务治理

- **request_id 必填**:网关层校验,缺失直接 400
- **格式标准**:UUID v4 或 client_id + nano_timestamp
- **链路追踪**:request_id 注入 trace,跨服务可查
- **客户端 SDK**:重试时复用同 request_id(关键!)
- **灰度兼容**:新版幂等逻辑向后兼容老 request_id 格式

#### 3. 缓存与 DB 优化(主战场)

**Redis 数据结构**:
```
key: idem:{user_id}:{request_id}
value: order_id
TTL: 3 分钟(覆盖大多数重试窗口)
```

**为什么 3 分钟 TTL**:
- 1 分钟太短:慢重试可能逃逸到 DB(虽然有 UNIQUE,但走 DB 慢)
- 10 分钟太长:Redis 内存爆炸(2000w 单 × 10min ≈ 1.4 亿 key)
- 3 分钟:99% 重试在此窗口内,Redis 容量可控

**DB UNIQUE 优化**:
- 索引列顺序:`(user_id, request_id)` 而非反过来
- 原因:基因法定位库后,用户维度查询走前缀
- 冲突时:必须**回查老订单**返回,而不是直接报错

#### 4. 异步消息

- **下游幂等**:order_id 作为消费幂等键
- **MQ event_id**:消息层 UNIQUE 防重
- **重试机制**:RocketMQ 自动 16 次,失败入 DLQ
- **死信处理**:人工补偿 + 报告业务方

#### 5. 限流熔断降级

- **单用户限流**:5 次/秒下单(防恶意刷)
- **request_id 限流**:同 request_id 1 次/秒(防 SDK bug)
- **接口熔断**:DB 异常时降级返回"系统繁忙,请稍后"
- **降级策略**:Redis 挂 → 直接走 DB UNIQUE(慢但正确)

#### 6. 容灾恢复

| 故障 | 应对 |
| --- | --- |
| Redis 挂 | 降级 DB UNIQUE 兜底,QPS 限制 |
| Redis 数据丢失 | 不影响幂等(DB UNIQUE 是真相)|
| DB 主挂 | MHA 切从,期间幂等可能"晚响应"30s |
| 应用挂 | 流量切其他实例,无状态可漂移 |
| 极端错单 | 对账发现 + 人工补偿(退款 / 关单) |

#### 9. 真实优化经验

**踩坑 1:没用 request_id,光靠用户行为去重**
- 现象:用户连点产生多单,客诉爆炸
- 优化:前端 SDK 强制生成 request_id,后端必填
- 收益:重复下单率从 0.5% 降到 0.001%

**踩坑 2:Redis 没 TTL 内存爆炸**
- 现象:idem key 永不过期,Redis 内存 24h 内打满
- 优化:`SET key val EX 180`,加 TTL
- 收益:内存稳定在 1GB

**踩坑 3:UNIQUE 冲突直接报错给用户**
- 现象:用户看到"订单已存在",但其实是网络重试
- 优化:冲突时回查并返回老订单,对用户透明
- 收益:用户体验显著提升

**踩坑 4:幂等接口性能差**
- 现象:每次都查 Redis,P99 50ms
- 优化:本地缓存 1 秒 TTL + Bloom filter 预检 + 异步刷新
- 收益:P99 降到 5ms

**踩坑 5:支付回调与下单共用 request_id 命名空间**
- 现象:trade_no 与 request_id 撞库
- 优化:分别用 `idem:order:` 和 `idem:payment:` 前缀
- 收益:业务隔离

### 易错点

- ❌ request_id 选 UUID v1(含 MAC,泄露隐私)→ 用 v4 随机
- ❌ Redis 没 TTL → 内存炸
- ❌ DB UNIQUE 索引顺序错(request_id 在前)→ 走不到基因法定位
- ❌ 冲突直接 throw error → 业务异常,改回查返回
- ❌ 幂等结果不缓存 → 每次都查 DB,慢
- ❌ Token 一次性(用过失效)→ 网络抖动客户端拿不到结果,业务卡死

### 追问预案

1. **request_id 怎么生成?** 客户端 SDK 用 UUID v4,或 `client_id + nano_ts`
2. **Redis 挂了怎么办?** 降级 DB UNIQUE,QPS 限制 + 告警
3. **超过 TTL 的重试怎么办?** 走 DB UNIQUE 兜底,业务无感
4. **怎么避免恶意伪造 request_id?** 网关签名 + 用户限流 + 风控
5. **分布式锁能不能做幂等?** 可以但太重,Redis SETNX + DB UNIQUE 更轻
6. **GET 请求需要幂等吗?** 天然幂等(读操作),无需特殊处理
7. **幂等和并发是一回事吗?** 不是。幂等关心"多次执行结果一致",并发关心"同时执行不冲突"
8. **如何测试幂等?** 单元测试连续调用 N 次,断言只生效一次 + 结果一致

### 面试回答版

> 订单幂等的本质是**识别"同一意图"**——所以根基是客户端 SDK 生成的 request_id,SDK 重试时必须复用同一个,这是整个体系的基石。
>
> 我一般做五层防御:前端按钮防抖挡用户连点,网关用 `SETNX request_id` 3 秒 TTL 挡快速重试,应用层用 `request_id ↔ order_id` 缓存 3 分钟挡业务层重试,DB 用 `(user_id, request_id)` 唯一索引做终极兜底,最外面再加一层"5 分钟同 user+sku 二次下单"的业务告警。任意一层挡住即可。
>
> 这里有个最容易踩的坑:UNIQUE 冲突**不能直接 throw 给用户**,必须回查老订单返回——因为对客户端来说网络重试是合法的,要让用户感知不到差别。Redis 挂了也不影响正确性,降级走 DB UNIQUE 即可,慢但正确。
>
> 容量上 4w TPS × 180s TTL ≈ 720MB Redis 内存,完全扛得住;DB UNIQUE 走联合索引 P99 < 0.1ms。监控上重点看 L3 DB 兜底率,正常 < 1%,> 5% 就是 P0,说明 L1/L2 挂了。

### 一句话核心

> **客户端 request_id 跨重试稳定 + 五层防御(前端 / Redis / 应用缓存 / DB UNIQUE / 业务告警)+ UNIQUE 冲突回查老订单不 throw**。

### 背诵版(更精简)

> 订单幂等五层防御:前端按钮防抖 + 网关 Redis SETNX(3s)+ 应用 user_id+request_id 缓存(3min)+ DB UNIQUE(user_id, request_id)+ 业务异常告警。Redis 容量 720MB(4w TPS × 180s),DB UNIQUE 兜底确保正确性。生产踩坑:request_id 必填、TTL 必加、冲突要回查不要 throw、共用 namespace 要前缀隔离。监控 L1/L2/L3 各层命中率,L3 兜底率 > 5% 是 P0 告警。

## Q3 支付回调如何防重复

### 场景设定

> 抖音电商接微信 / 支付宝支付,日支付 1000 万笔。三方回调因网络抖动 / 通道重投 / 我方处理慢导致同一笔支付重复回调,要求 **一笔支付永远只更新一次订单,资金 100% 一致,差异 = 0**。

### 一句话本质

**签名验证 + trade_no 唯一约束 + 状态机 CAS 推进 + 主动对账兜底**,资金类业务**零容忍数据错乱**,所以双向校验(我方收 + 主动拉)。

### 面试答题节奏(故事版)

#### 1. 场景具体化

> 抖音电商接微信 / 支付宝支付,日支付 1000 万笔。三方回调因网络抖动 / 通道重投 / 我方处理慢导致同一笔支付重复回调。要求一笔支付永远只更新一次订单,**资金 100% 一致,差异 = 0**。

#### 2. 如果只接收回调、不去重不校验,会怎样?

- **重复扣款**:同一笔支付收到 3 次回调 → 用户被多次扣订单 → 客诉爆炸
- **资金错乱**:订单已 PAID 还在推进状态机 → 状态混乱
- **伪造攻击**:不验签 → 攻击者伪造回调让订单变 PAID,白嫖
- **三方持续重试**:回调慢 / 错误响应 → 三方按指数退避重试 24 小时(微信),雪上加霜

资金类业务**零容忍数据错乱**,必须**双向校验**(被动收 + 主动拉)。

#### 3. 核心方案(一句话)

**签名验证 + trade_no UNIQUE + 状态机 CAS + 主动对账 + T+1 资金对账**,五道防线缺一不可。

#### 4. 回调接收链路(防伪造 + 快响应)

```
三方支付 → CDN → WAF → 网关(IP 白名单)→ 支付回调服务(独立部署)
                                            ↓
                                     1. 签名验证(RSA,证书缓存)
                                     2. 写 payment_log(trade_no UNIQUE)
                                     3. 异步处理(发 MQ)
                                     4. < 50ms 返回 success
```

**为什么 < 50ms**:三方回调超时(微信 100ms)会触发持续重试,把我方雪上加霜。**收到即落 log + 发 MQ,然后秒返**,业务处理走异步。

#### 5. trade_no UNIQUE + payment_log(防重核心)

```sql
-- 我方 ↔ 三方映射(防重)
CREATE TABLE payment_order_map (
  order_id BIGINT NOT NULL,
  trade_no VARCHAR(64) NOT NULL,
  channel VARCHAR(16),
  UNIQUE KEY uk_trade_no (channel, trade_no)
);

-- 回调流水(审计 + 防重)
CREATE TABLE payment_log (
  trade_no VARCHAR(64),
  event_type VARCHAR(32),   -- PAY_SUCCESS / REFUND
  raw_payload TEXT,
  UNIQUE KEY uk_trade_event (trade_no, event_type)  -- 防重
);
```

重复回调直接 `INSERT IGNORE`,审计追溯完整。

#### 6. 状态机 CAS 推进(只推一次)

```sql
UPDATE orders
SET state = 'PAID', paid_at = NOW()
WHERE order_id = ?
  AND state = 'WAIT_PAY'
  AND pay_amount = ?       -- 防金额篡改
```

**affected_rows 判定**(关键):
- `= 1` → 推进成功,触发下游(库存实扣 / 通知 / 物流)
- `= 0` → **必须回查当前态**:
  - 已 PAID + 金额一致 → 幂等成功,返回 success
  - 已 PAID + 金额不一致 → **P0 告警**(可能金额篡改)
  - 其他态 → P0 告警(状态异常)

**反模式**:CAS 失败直接 throw error → 告警风暴,正确做法是回查。

#### 7. 主动对账(双向校验,资金类必备)

```
每 5 分钟:
  扫我方 state=WAIT_PAY AND created_at > NOW() - 30min
  → 调三方"订单查询"接口
  → 三方说 PAID 我方 WAIT_PAY → 触发补单
  → 我方 PAID 三方 NOT_FOUND   → P0 告警

T+1 资金对账:
  三方对账文件 vs 我方 orders + payment_log
  差异:我方少 → 补单 / 我方多 → 退款 / 金额不一致 → 人工
```

**为什么必须主动拉**:三方回调可能因网络永久丢失,资金类零容忍——只靠被动接收会有漏单。

#### 8. 异常处理 + 退款

| 异常 | 处理 |
| --- | --- |
| 签名失败 | 拒绝 + 计数,陡升 → P0(可能被攻击) |
| 三方故障期间回调全丢 | 主动对账兜底,5 分钟内自动恢复 |
| 通道金额规则差异(费率) | 对账区分"应收 vs 实收",独立流水 |
| 退款回调 | 独立 event_type,状态机分支不同 |
| 大促支付通道挂 | 多渠道兜底(微信挂自动切支付宝) |

### 面试回答版

> 支付回调防重的本质是**资金零容忍**——多收一笔钱、漏推一个订单都是事故。所以做的不是"一道防线",而是**双向校验**:被动收三方回调 + 主动拉三方查询接口,两条链路互为兜底,任何一条断了另一条都能补上。
>
> 核心是五道防线层层叠加。**第一道签名验证**——IP 白名单 + RSA 验签,防止伪造回调;证书 24h 缓存,验签延迟控制在 1ms 以内。**第二道 trade_no UNIQUE**——payment_log 表用三方交易号唯一约束,INSERT IGNORE,网络重试 / 三方重推都被数据库挡掉。**第三道状态机 CAS**——`UPDATE orders SET state='PAID' WHERE order_id=? AND state='WAIT_PAY' AND pay_amount=?`,affected_rows=1 才推进;CAS 失败必须回查,如果当前已是 PAID 且金额一致就当作幂等返回 success,**绝对不能直接报错让三方重推**;但如果金额不一致直接 P0 告警,可能被攻击。
>
> 还有两件事很重要。**回调接收必须 < 50ms 返回 success**——微信回调超时 100ms,响应慢三方会持续重推 1/5/15min 共 8 次,把回调入口打爆。所以接收链路只做"签名 + 落 payment_log",**业务推进异步走 MQ**,失败可重试。**主动对账兜底**——每 5 分钟扫一遍 state=WAIT_PAY 且 30 分钟前下的单,调三方查询接口,如果三方说 PAID 我方还是 WAIT_PAY,就触发补单;再加 T+1 资金对账文件比对,保证差异 = 0。
>
> 监控四个核心指标:回调成功率 > 99.99% / 资金对账差异 = 0 / 签名失败率 < 0.01% / MQ 积压 < 1000。

### 一句话核心

> **双向校验(被动收回调 + 主动查对账)+ 五道防线(签名 / trade_no UNIQUE / 状态机 CAS / 主动对账 / T+1 资金对账)+ 回调 < 50ms 返回 success + CAS 失败必须回查不报错**

### 背诵版(更精简)

> 支付回调防重三件套:**签名验证**(IP 白名单 + RSA 验签)+ **trade_no UNIQUE**(payment_log 表 INSERT IGNORE)+ **状态机 CAS**(CAS 失败回查当前态)。资金类业务双向校验:**被动收回调** + **主动查对账接口**(5 分钟扫描)+ **T+1 资金对账**(差异 = 0)。生产踩坑:回调必须 < 50ms 返回 success 防三方重试、CAS 失败要回查、签名证书要缓存、必须有主动对账兜底。监控:回调成功率 / 资金对账差异 / 签名失败率 / MQ 积压。

## Q4 热点 SKU 如何拆库存桶

### 场景设定

> 双 11 iPhone 16 Pro 库存 10,000 台,单 SKU 100 万 QPS。Redis 单节点上限 10 万 QPS,**单 key 落单节点**,直接成瓶颈。需要把"一个 SKU"拆到多个 Redis 节点上,同时**保证总库存正确**。

### 一句话本质

**`sku_id + bucket_id` 哈希分桶散到不同节点**,扣减时**先选桶 + 桶内 Lua 原子扣减**,桶空了**邻桶借库存或返售罄**,核心是"用空间换并发,用调度换均衡"。

### 面试答题节奏(故事版)

#### 1. 场景具体化

双 11 iPhone 16 Pro 库存 1 万台,单 SKU 峰值 100 万 QPS——这种现象级单品在大促期间太常见了。Redis 单节点上限大概 10 万 QPS,**单 key 就是单节点**,直接成瓶颈,而且这一个节点挂了整个 SKU 就废了。

#### 2. 为什么不能用单 key

* 单 SKU 一个 Redis key → 一个 slot → 一个节点
* 100 万 QPS 打一个节点 = CPU 100% + 网卡打满
* 该节点挂了 → 1 万台库存全废,**故障半径太大**
* 单点扩容只能垂直(加 CPU / 内存),性价比极低

所以**必须横向拆**——把一个 SKU 的库存切成多份,散到不同节点上,把"单 key 单节点"变成"N key N 节点",QPS 平摊。

#### 3. 核心方案——哈希分桶

把 10000 台库存拆到 32 个桶:
```
stock:{sku_id_b0}  → {total: 313, remaining: 280, sold: 33}
stock:{sku_id_b1}  → {total: 313, remaining: 295, sold: 18}
...
stock:{sku_id_b31} → {total: 313, ...}
stock:{sku_id}:meta → {total_stock: 10000}
```

**两个关键细节**:
1. **桶 key 必须用 hash tag** `{sku_id_bN}`——大括号锁定 hash slot,**保证桶内 Lua 跨 key 操作不报 CROSSSLOT**(Redis Cluster 硬要求)。
2. **桶之间散到不同节点**——不同的 `sku_id_bN` 哈希到不同 slot 即可,Cluster 自动分散。

#### 3.5 深度补充:怎么严格保证 N 个桶落到不同节点

§3 说"桶之间散到不同节点",但 Redis Cluster 用 `CRC16(tag) % 16384`,**不保证 32 个桶严格覆盖所有节点**——可能某节点 0 桶,某节点 6 桶,造成新的倾斜。三种精度递增的做法:

**方案 1:CRC16 自然分布(默认,简单)**

| 做法 | key 设计 | 适用 |
| --- | --- | --- |
| 每桶独立 tag | `{sku_id_b0}`、`{sku_id_b1}`、… | 节点数 ≤ 16 且桶数 ≥ 32 |
| 依赖 CRC16 哈希 | 32 tag → 32 slot → 大概率覆盖所有节点 | 不要求严格均匀 |

- ✅ 8 节点集群、32 桶,期望每节点 4 桶
- ❌ 实际可能 0-7 桶/节点(标准差 ~2),小概率某节点 0 桶 = 桶全废
- **判定**:简单场景够用,大促前必须看监控

**方案 2:slot 感知预生成(精确,生产推荐)**

启动时遍历集群拓扑,显式选 key 让分布均匀:

```go
func generateBucketKeys(sku string, N int, cluster *redis.ClusterClient) []string {
    nodes := cluster.MasterNodes()       // 假设 8 节点
    perNode := (N + len(nodes) - 1) / len(nodes)  // 每节点 ⌈N/8⌉ 桶
    keys, cnt := []string{}, map[string]int{}

    for i := 0; len(keys) < N; i++ {
        key := fmt.Sprintf("stock:{sku_%s_b%d}", sku, i)
        slot := crc16(extractTag(key)) % 16384
        node := cluster.SlotToNode(slot)
        if cnt[node] < perNode {
            keys = append(keys, key)
            cnt[node]++
        }
    }
    return keys                          // 把这个列表下发到所有 Pod
}
```

- ✅ **严格 N/nodeCount 均匀分布**
- ❌ 扩缩容时 slot 重新映射,key 列表要重算并下发(用配置中心 watch)
- **判定**:大促必备,平时可省

**方案 3:hash tag 显式分组(借库存的真实落地形式)**

把 32 桶分成 8 组,**每组 4 桶共享一个 hash tag**:

```
组 0 (落节点 N0):  stock:{grp0}_b0、{grp0}_b1、{grp0}_b2、{grp0}_b3
组 1 (落节点 N1):  stock:{grp1}_b0..b3
...
组 7 (落节点 N7):  stock:{grp7}_b0..b3
```

- ✅ **组内可以 Lua 跨桶借库存**(同 tag → 同 slot → 同节点)
- ✅ 组间分散 = 节点级分散
- ❌ 每组的 tag(grp0/grp1...)要预先用 `CLUSTER KEYSLOT` 命令探测,确保落不同节点
- **判定**:**§7 借库存机制的真正落地形式**,不分组的话借库存 Lua 必然 CROSSSLOT

#### 3.6 hash tag 的双重作用辨析(高频混淆点)

| 场景 | tag 用法 | 例子 | 出现在 Q4 哪里 |
| --- | --- | --- | --- |
| 同一个桶内的多个 key 要 Lua 跨 key | **同 tag** | `stock:{b0}`、`reserve:{b0}` 同 slot | §6 桶内扣减 |
| 桶之间要散到不同节点 | **不同 tag** | `{sku_b0}` vs `{sku_b1}` 不同 slot | §3 §3.5 方案 1/2 |
| 桶之间要支持借库存 | **分组同 tag** | 同组 `{grp0}_b0..b3` 同 slot,组间不同 | §7 借库存(方案 3) |

→ **不要混用**:单桶独立 tag 的方案 1/2 必然不支持 Lua 跨桶借,只能客户端两阶段(查 + 扣,有竞态);要 Lua 借就必须方案 3 分组。

#### 3.7 客户端选桶要跟 key 生成对齐

```go
// 方案 1/2:32 桶平铺
key := bucketKeys[hash(userID) % 32]

// 方案 3:8 组 × 4 桶
grp := hash(userID) % 8
sub := (hash(userID) / 8) % 4
key := fmt.Sprintf("stock:{grp%d}_b%d", grp, sub)
```

key 生成方案变了,**路由逻辑必须跟着改**,否则会落到错的桶,直接 KEY_NOT_FOUND。

#### 4. 桶数怎么选——3 个公式定死

```
最少桶数 = 峰值 QPS / 单节点上限 = 100w / 10w = 10
预留抖动 = 10 × 2 = 20
向上取 2 的幂(便于哈希)= 32
```

为什么是 2 的幂:**位运算 `hash & 31` 比 `hash % 32` 快**,大流量场景 CPU 节省可观。32 是经过抖音双 11 真实压测验证的"甜点值"——再大(64 / 128)会带来元数据膨胀和管理复杂度,再小(8 / 16)余量不够。

#### 5. 用户路由——同用户同桶

```go
bucket := hash(user_id) % 32
key := fmt.Sprintf("stock:{sku_%d_b%d}", skuID, bucket)
```

**为什么用 user_id 而不是随机**:
- 同用户多次点击落同一桶 → **天然幂等**(配合 order_token,重复扣减容易识别)
- 用户分布相对均匀(不是绝对均匀,后面有兜底)
- 如果用随机,同一用户重复请求会散到不同桶,幂等成本上升

#### 6. 桶内 Lua 原子扣减

```lua
-- KEYS[1] = stock:{sku_id_bN}
local r = tonumber(redis.call('HGET', KEYS[1], 'remaining'))
if not r or r < 1 then return 0 end
redis.call('HINCRBY', KEYS[1], 'remaining', -1)
redis.call('HINCRBY', KEYS[1], 'sold', 1)
return 1
```

Lua 单线程原子,桶内绝对不超卖。

#### 7. 桶倾斜怎么办——虚拟桶 + 借库存

理想情况各桶均匀,**实际抖动很大**——抖音双 11 真实数据,32 桶里**前 5 桶占 60% 流量**,因为用户 ID 哈希分布不绝对均匀,加上"网红推荐链接"会把流量集中到特定哈希区间。

**两层兜底**:
- **虚拟桶映射**(预防):物理桶 0 ← 虚拟桶 0/8/16/24,把哈希倾斜稀释掉
- **借库存机制**(救火):本桶 remaining=0 时,Lua 扫描**同节点内**其他桶,找第一个 remaining > 0 的桶扣减(跨节点会 CROSSSLOT 报错,直接返售罄)

借库存 Lua:
```lua
for i = 1, #KEYS do
  local r = tonumber(redis.call('HGET', KEYS[i], 'remaining'))
  if r and r >= 1 then
    redis.call('HINCRBY', KEYS[i], 'remaining', -1)
    return i  -- 返回扣减的桶 index,便于排查
  end
end
return -1  -- 全空售罄
```

#### 8. 监控——必须看桶利用率

| 指标 | 阈值 | 含义 |
| --- | --- | --- |
| 桶利用率差异 | > 30% → P2 | 倾斜,调虚拟桶映射 |
| 借库存触发率 | > 10% → P2 | 分配不均加剧 |
| 单桶 QPS | 接近 8w → P1 | 快到 Redis 节点上限 |
| 总库存 vs 桶库存和 | ≠ 0 → P0 | 数据错乱,资金类事故 |

#### 9. 大促结束的尾单问题

真实踩过的坑:32 桶里有 5 桶各剩 1-2 台,合计 8 台库存,但单个桶**Lua 内只查本桶**,显示"售罄";用户能下单的只剩 27 桶。库存利用率从 100% 降到 99.2%——大促对库存利用率特别敏感,这 0.8% 是真金白银。

**优化**:大促进入尾声时(remaining 总量 < 50)启动"全局扫描模式"——任意桶下单都触发借库存 Lua,把所有桶清空再判售罄。利用率回升到 99.9%。

### 九维度深度展开(追问储备)

#### 1. 分布式一致性(主战场)

**总库存 = ∑ 各桶库存**:
- 初始化:10,000 台 / 32 桶 ≈ 313 台/桶,余数补给前几个桶
- 扣减:用户路由到一个桶,桶内 Lua 原子扣减
- 借库存:本桶为 0 时,随机/顺序探测 N 个其他桶
- 关闭:总库存 = 0 时,标记 SKU 售罄(避免无效探测)

**Key 设计**:
```
stock:{sku_id_b0}  → hash {total: 313, remaining: 280, sold: 33}
stock:{sku_id_b1}  → hash
...
stock:{sku_id_b31} → hash
stock:{sku_id}:meta → hash {total_stock: 10000, sold_total: ...}
```

**hash tag 关键点**:`{sku_id_bN}` 用大括号锁定 hash slot,**保证桶内 stock 和 reserve 在同一个 slot**(Redis Cluster 要求 Lua 跨 key 必须同 slot)。

#### 2. 服务治理

- **桶分配策略**:`bucket = hash(user_id) % 32` → 同用户固定桶,避免热点扩散
- **降级返回**:总库存 = 0 → CDN 缓存"售罄"页 1 分钟
- **链路追踪**:`bucket_id` 注入 trace,排查时一眼看出落哪个桶

#### 3. 缓存与 DB 优化(主战场)

**桶数怎么选**:
```
单 SKU 峰值 QPS = 100 万
单节点上限   = 10 万
最少桶数     = 100w / 10w = 10
预留 2× 抖动  = 20
向上取 2 的幂 = 32
```

**桶大小不均**:
- 抖音双 11 真实数据:32 桶里前 5 桶占 60% 流量(用户分布不均)
- 解决:**虚拟桶**(每个物理桶映射 N 个虚拟桶,减少哈希倾斜)
- 兜底:**借库存机制**(本桶空了从其他桶借)

**借库存 Lua**:
```lua
-- KEYS[1..N] = stock:{sku_id_b0..bN}
-- 找到第一个 remaining > 0 的桶扣减
for i = 1, #KEYS do
  local r = tonumber(redis.call('HGET', KEYS[i], 'remaining'))
  if r and r >= 1 then
    redis.call('HINCRBY', KEYS[i], 'remaining', -1)
    return i  -- 返回扣减的桶 index
  end
end
return -1  -- 全部桶空,售罄
```

**注意**:借库存 Lua 跨 key 操作只能用于**同 slot 的桶**;真正跨节点借库存需要**两阶段**(先查再扣,有竞态),所以一般限定**同节点内的 N 个桶**互借,跨节点直接售罄。

#### 4. 异步消息

- 各桶扣减成功后,带 `bucket_id` 发 MQ
- 消费者按 `sku_id` 聚合落 MySQL `inventory` 表
- 总库存 = 所有桶 sold 之和(MySQL 视角)

#### 5. 限流熔断降级

- **单桶限流**:Sentinel 按 `sku_id + bucket_id` 限流 1 万 QPS
- **总限流**:网关按 `sku_id` 限流 100 万 QPS
- **降级**:借库存失败 N 次 → 直接返回"已售罄",避免持续探测

#### 6. 容灾恢复

| 场景 | 应对 |
| --- | --- |
| 单桶 Redis 节点挂 | 该桶库存"假死",其他桶继续 → 损失 1/32 库存 |
| 整集群挂 | 降级 MySQL 单点扣减 + 全局限流 |
| 桶库存数据错乱 | T+1 对账修复(见 Q1) |

#### 7. 监控告警

- **桶利用率**:各桶 sold / total,差异 > 30% → 调虚拟桶映射
- **借库存触发率**:正常 < 5%,陡升 → 桶分配不均
- **单桶 QPS**:接近 8 万 → P1 告警(快到上限)
- **总库存 vs 桶库存和**:差异 → P0(数据错乱)

#### 8. 压测与容量评估

```
峰值:单 SKU 100w QPS,32 桶 × 5w/桶(留余量)= 160w QPS 容量
单桶 Lua 耗时 < 1ms
桶数选择:10w QPS 节点 → 至少 10 桶 → 取 32 防倾斜
内存:10000 台 × 32 桶 × ~200 字节 = 64KB(可忽略)
```

#### 9. 真实优化经验

**踩坑 1:桶数选 10,实际不够用**
- 现象:10 桶里 3 个热点桶各扛 30w QPS,直接打满
- 优化:桶数提到 32 + 虚拟桶
- 收益:单桶 QPS 降到 5w 内

**踩坑 2:借库存 Lua 跨节点失败**
- 现象:Redis Cluster 报 `CROSSSLOT keys in request`
- 优化:借库存只在同节点桶之间(用 hash tag 控制)
- 收益:Lua 正常执行

**踩坑 3:总库存 vs 桶库存对账差 0.1%**
- 现象:借库存后 MQ 消费失败,MySQL 没落
- 优化:借库存路径加 idempotent key + DLQ 监控
- 收益:差异 < 0.001%

**踩坑 4:大促结束桶库存留尾**
- 现象:32 桶里有 5 桶剩余 1-2 台,显示"售罄"但实际有库存
- 优化:借库存策略改"全局扫描后再判定售罄"
- 收益:库存利用率从 95% 提到 99.9%

### 量化数据卡

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 默认桶数 | 32 | 2 的幂 + 余量 |
| 单桶 QPS 上限 | 5 万 | 留 50% 余量 |
| 单 SKU 总容量 | 100w QPS+ | 32 桶 × 5w |
| 借库存触发率 | < 5% | 正常水位 |
| 库存利用率 | > 99.9% | 借库存兜底 |
| Lua 跨 key 限制 | 同 slot | hash tag 锁定 |

### 易错点

- ❌ 桶 key 不用 hash tag → Lua 跨 slot 报错
- ❌ 桶数选奇数 → 哈希分布不均
- ❌ 借库存跨节点 → CROSSSLOT 错误
- ❌ 不监控桶利用率 → 倾斜不可见
- ❌ 桶数太多(如 1024)→ 元数据膨胀,管理复杂

### 追问预案

1. **为什么是 32 桶不是 16 / 64?** 100w / 10w = 10 桶起,留 2-3× 余量,2 的幂便于哈希
2. **桶数能动态扩吗?** 不能,扩桶 = 全量 rehash,只能初始化时定好
3. **借库存会有超卖吗?** 不会,Lua 内原子扣减,跨桶逐一探测
4. **桶 0 永远是热点怎么办?** 虚拟桶映射(物理桶 0 ← 虚拟桶 0/8/16/24)
5. **怎么提前预热?** 大促前 10 分钟加载所有桶到 Redis,验证数据一致

### 面试回答版

> 单 SKU 高 QPS 的本质问题是**Redis 单 key 单 slot 单节点**——10000 台库存对应一个 key,100w QPS 全打一个节点,CPU 100% 是必然,而且这个节点挂了 1 万台库存全废,**故障半径不能接受**。所以核心思路是**横向拆**——一个 SKU 拆成 N 个桶,散到不同 Redis 节点上,QPS 平摊,故障半径也降到 1/N。
>
> 桶数怎么定有公式:**峰值 QPS / 单节点上限 × 余量,向上取 2 的幂**。100w / 10w = 10 桶起,留 2-3× 抖动余量,取 32。为什么是 2 的幂——位运算 `& 31` 比 `% 32` 快,大流量下 CPU 节省可观。Key 设计用 hash tag `stock:{sku_id_bN}`,**桶内 Lua 跨 key 操作不能跨 slot**,这是 Cluster 硬要求,踩过坑。
>
> 用户路由用 `hash(user_id) % 32`,**同用户同桶**——天然幂等,重复请求方便去重。但用户分布从来不绝对均匀,抖音双 11 真实数据**前 5 桶占 60% 流量**,所以必须有两层兜底:**虚拟桶映射**(物理桶 0 ← 虚拟桶 0/8/16/24,预防倾斜)+ **借库存机制**(本桶空了 Lua 扫同节点其他桶,跨节点会 CROSSSLOT 报错直接返售罄)。
>
> 大促尾声还有一个隐藏问题——32 桶里 5 桶各剩 1-2 台,合计 8 台库存,但单桶视角显示售罄,**库存利用率掉到 99.2%**,这 0.8% 是真金白银。优化是 remaining < 50 时启动全局扫描模式,任意桶下单都触发借库存,利用率回到 99.9%。
>
> 监控四个指标:桶利用率差异 < 30% / 借库存触发率 < 10% / 单桶 QPS < 8w / 总库存 = 桶库存和。

### 一句话核心

> **32 桶 hash tag 散到不同节点 + `hash(user_id)%32` 路由 + 桶内 Lua 原子扣减 + 虚拟桶防倾斜 + 借库存兜底(同节点)+ 尾单全局扫描**

### 背诵版(更精简)

> 单 SKU 100w QPS 拆 **32 桶**(`stock:{sku_id_b0..b31}`,hash tag 同 slot),**`hash(user_id) % 32` 路由 + 桶内 Lua 原子扣减 + 桶空借邻桶**。桶数公式:峰值 / 单节点 × 余量 → 取 2 的幂。生产踩坑:桶倾斜用虚拟桶映射、借库存只能同节点(跨 slot 报错)、对账兜底防数据错乱。监控:桶利用率 / 借库存触发率 / 单桶 QPS。详见 [24-order-system 附录 C](../10-system-design/24-order-system.md)。

## Q5 短码如何发号防冲突

### 场景设定

> 短链平台日均生成 5000 万短码,峰值 5 万 QPS。短码长度 6-8 位 base62,要求**全局唯一、不可猜测、低延迟、可回收**。冲突率 < 0.0001%,生成 P99 < 5ms。

### 一句话本质

**号段池预分配 + 哈希加扰 + Bloom filter 防重 + DB UNIQUE 兜底**,核心是"批量发号削峰 + 多层去重 + 失败回退"。

### 面试答题节奏(故事版)

#### 1. 场景具体化

短链平台日均生成 5000 万短码,峰值 5 万 QPS。短码长度 6-8 位 base62,要求**全局唯一、不可猜测、低延迟(P99 < 5ms)、可回收**。冲突率 SLO < 0.0001%——3 个 9 的可用性,因为短码冲突会让两个不同长链指向同一个短链,是 P0 故障。

#### 2. 为什么不能直接 base62 随机

第一反应都是"6 位 base62 = 62^6 ≈ 568 亿,够用了直接随机吧"——但**生日悖论**会让冲突率快速上升:
- 5000w/天 × 365 = 180 亿/年
- 在 568 亿空间里放 180 亿 → **冲突率约 30%**,完全不可接受

而且即使有 DB UNIQUE 兜底,冲突重试的 P99 会被拖得很难看,大促期间还可能产生雪崩。

**正确思路**:用**自增 ID 保证唯一**,再 XOR 加扰避免规律暴露。

#### 3. 核心方案——号段池预分配

```
全局发号表:id_alloc(biz='short_url', max_id=10000000, step=10000)

应用启动 → CAS 拿一段 [10000001, 10010000) → 内存自增
拿完 → 再申请下一段 [10010001, 10020000)
ID → XOR 加扰 → base62 → 短码
```

**为什么这套**:
- 内存自增 → P99 < 1ms(对比单次申请 DB 50ms+)
- 号段批量发 → DB QPS 从 5w 降到 5(降 1 万倍)
- CAS 保证多实例不重叠

#### 4. 双 buffer 号段——发号不阻塞的关键

单 buffer 有个致命问题:**号段用完才申请,DB 抖动期间发号全挂**。生产真实事故:DB 主从切换 3 秒,期间所有发号 timeout。

双 buffer 设计:
```
应用内存:
  buffer_A: [10000001, 10010000)  ← 当前用
  buffer_B: empty                  ← 备用

buffer_A 用到 80% → 异步预取 buffer_B
buffer_A 用完 → 切到 buffer_B(切换无感)
buffer_B 也快用完 → 再异步预取
```

**实测收益**:P99 从 50ms(单 buffer)降到 0.5ms(双 buffer)。

#### 5. ID → 短码的加扰——防爬虫扫描

踩过的坑:连续 ID 生成相邻短码,爬虫顺序扫,**1 天扫了 1 亿短链**,把别人的长链全爬了。

```go
const MAGIC_KEY = 0x5A5A5A5A5A5A5A5A  // 密钥定期轮换

func encode(id int64) string {
    scrambled := id ^ MAGIC_KEY  // XOR 加扰
    return base62(scrambled)     // 转 base62
}
```

XOR 是双射,加扰后**短码看起来随机但保证唯一**,爬虫扫描成功率从 80% 降到 0.001%。

#### 6. DB UNIQUE 兜底——理论冲突率 0 也要兜

```sql
CREATE TABLE short_url (
  id BIGINT PRIMARY KEY,
  short_code VARCHAR(10) NOT NULL,
  long_url TEXT,
  UNIQUE KEY uk_short_code (short_code)
);
```

**为什么必须有**:
- 号段池理论上不会冲突,但跨机房 / 跨集群极小概率配置错误会导致段重叠
- DB UNIQUE 是**最后一道防线**——出问题立刻报错而不是污染数据
- 报错后内存 ID++ 重试,用户无感

#### 7. step 怎么选——两难权衡

| step | 优点 | 缺点 |
| --- | --- | --- |
| 100 | 应用挂浪费少 | DB QPS 高(5w/100=500 次/秒) |
| 10000 | DB 压力小(5 次/秒) | 应用挂浪费 1w ID |
| 1000000 | DB 压力极小 | 应用挂浪费 100w,业务方误以为 ID 连续会出 bug |

**生产甜点**:10000——DB 压力可忽略,浪费率 < 0.01%,可接受。

#### 8. ID 不连续——必须和业务方约法三章

最容易踩的契约坑:业务方用 ID 做自增统计、做"上一条 / 下一条"导航,**默认 ID 连续**。应用重启 / 切 buffer 都会跳跃,业务报 bug。

**对策**:发号服务对外契约**显式声明 ID 不保证连续**,业务方不能依赖。Snowflake / 号段池都是这个问题,提前讲清楚比事后修代码省 10 倍力气。

### 九维度深度展开(追问储备)

#### 1. 分布式一致性(主战场)

**号段池模型(主推荐)**:
```
全局发号表:id_alloc(biz='short_url', max_id=10000000, step=10000)
应用启动 → CAS 拿一段 [10000001, 10010000) → 内存自增
拿完 → 再申请下一段 [10010001, 10020000)
ID → base62 → 短码
```

**为什么不直接 base62 随机**:
- 6 位 base62 = 62^6 ≈ 568 亿,看起来够,但**生日悖论**下冲突率快速上升
- 5000w/天 写满 1 年 = 180 亿,**冲突率 ≈ 30%**(不可接受)
- 解决:用自增 ID 保证唯一,加扰避免规律暴露

**ID → 短码的加扰**:
```go
// 防止短码被猜测(连续 ID 会生成相邻短码)
func encode(id int64) string {
    scrambled := id ^ MAGIC_KEY  // XOR 加扰
    return base62(scrambled)
}
```

#### 2. 服务治理

- **独立发号服务**:对外 RPC,内部预取号段
- **多实例**:每个实例独立持有号段(无锁、无竞争)
- **健康检查**:号段剩余 < 20% → 主动续段

#### 3. 缓存与 DB 优化(主战场)

**双 buffer 号段(关键!)**:
```
应用内存:
  buffer_A: [10000001, 10010000)  ← 当前用
  buffer_B: empty                  ← 备用
  
buffer_A 用到 80% → 异步预取 buffer_B
buffer_A 用完 → 切到 buffer_B(切换无感)
buffer_B 也快用完 → 再异步预取
```

**为什么需要双 buffer**:
- 单 buffer:用完才申请,DB 抖动期间发号阻塞
- 双 buffer:预先准备好,DB 抖动 1 秒内不影响发号
- 实测:P99 从 50ms(单)降到 0.5ms(双)

**DB UNIQUE 兜底**:
```sql
CREATE TABLE short_url (
  id BIGINT PRIMARY KEY,
  short_code VARCHAR(10) NOT NULL,
  long_url TEXT,
  UNIQUE KEY uk_short_code (short_code)  -- 兜底防重
);
```

#### 4. 异步消息

- 短码生成不需要 MQ(同步即可)
- 但**统计 / 审计**链路异步:生成后发 MQ,消费者落明细

#### 5. 限流熔断降级

- **单用户限流**:防恶意刷短码,单 IP 100 次/秒
- **降级**:号段服务挂 → 切到本地 Snowflake → base62

#### 6. 容灾恢复

| 故障 | 应对 |
| --- | --- |
| 号段 DB 挂 | 双 buffer 续命 1-2 秒,期间继续发号 |
| 应用挂 | 已分配号段未用完 → 浪费(可接受) |
| 短码冲突(极小概率) | DB UNIQUE 报错 → 重新生成 ID 重试 |

**已分配未用号段**:
- 一台机器拿 10000 段没用完就挂了 → 这一段废弃
- 损失:每天 N 台机器 × 万级 ID,占总池 < 0.01%
- 不回收(回收复杂度 >> 收益)

#### 7. 监控告警

- 号段消耗速度(预测耗尽时间)
- 双 buffer 切换频率(过高 → step 不够大)
- DB UNIQUE 冲突率(目标 = 0)
- 发号 P99(< 1ms 健康)

#### 8. 压测与容量评估

```
峰值 QPS:5w
号段 step:10000
申请频率:5w / 10000 = 5 次/秒(DB 压力可忽略)
DB 容量:5000w/天 × 365 = 180 亿/年
分库:按 short_code 哈希,32 库 1024 表
```

#### 9. 真实优化经验

**踩坑 1:单 buffer 号段,DB 抖动导致发号阻塞**
- 现象:DB 主从切换 3 秒,期间所有发号 timeout
- 优化:双 buffer + 80% 阈值预取
- 收益:P99 从 200ms 降到 0.5ms

**踩坑 2:短码可猜测,被爬虫扫**
- 现象:连续 ID 生成相邻短码,爬虫 1 天扫了 1 亿短链
- 优化:ID XOR magic_key 加扰 + base62 编码
- 收益:扫描成功率从 80% 降到 0.001%

**踩坑 3:号段 step 太小导致 DB QPS 高**
- 现象:step=100,5w QPS → 500 次/秒申请号段,DB 撑不住
- 优化:step 提到 10000,降到 5 次/秒
- 收益:DB 压力降 100×

**踩坑 4:Bloom filter 误判率没监控**
- 现象:误判率从 0.001% 涨到 1%,大量重复生成
- 优化:监控误判率 + 定期重建 Bloom filter
- 收益:误判率稳定 < 0.01%

**踩坑 5:号段未用完应用挂导致 ID 跳跃**
- 现象:业务方误以为 ID 连续,统计 / 校验逻辑出错
- 优化:**明确告诉业务方 ID 不保证连续**(契约层面)
- 收益:业务方不再依赖连续性

### 量化数据卡

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 短码长度 | 6-8 位 | base62 |
| 号段 step | 10000 | DB QPS 5 次/秒 |
| 双 buffer 阈值 | 80% | 预取 buffer_B |
| 冲突率 SLO | < 0.0001% | DB UNIQUE 兜底 |
| 发号 P99 | < 1ms | 内存自增 |
| ID 浪费率 | < 0.01% | 应用挂的损失 |

### 易错点

- ❌ 单 buffer 号段 → DB 抖动期间发号挂
- ❌ ID 直接 base62 不加扰 → 短码可猜测
- ❌ 业务方依赖 ID 连续性 → 应用重启后断号
- ❌ 不用 DB UNIQUE 兜底 → 极小概率冲突无法发现
- ❌ step 选太小 → DB 压力大
- ❌ step 选太大(100w)→ 应用挂浪费严重

### 追问预案

1. **为什么不用 Snowflake?** 短链需要短码(6-8 位),Snowflake 是 64 位,base62 后太长
2. **为什么不用 UUID?** 36 字符太长,无序导致 DB B+ 树插入抖动
3. **多机房怎么发号?** 号段 step 包含 region 前缀(R1: 1xxx, R2: 2xxx),无冲突
4. **怎么实现短码可读?** 排除易混字符(0/O、1/l/I)→ base58 或自定义字符集
5. **怎么防短码被恶意猜测?** XOR 加扰 + 密钥定期轮换 + 风控限频
6. **短码能复用吗?** 一般不复用(过期标记 deleted,空间换简单)
7. **6 位短码用完怎么办?** 升级到 7 位(无缝,长尾用户感知小)
8. **怎么做短码 → 长链查询?** 短码哈希分表 + Redis 缓存(命中率 > 99%)

### 面试回答版

> 短码发号的本质是**"内存自增 + DB 兜底"的两层架构**——不能直接打 DB(5w QPS 撑不住),也不能纯随机(生日悖论冲突率 30%)。所以核心是**号段池预分配**:应用启动 CAS 抢一段 ID(如 1w-2w),内存自增发号,用完再申请下一段,DB QPS 从 5w 降到 5,降了 1 万倍。
>
> 但单 buffer 号段有个致命问题——**用完才申请,DB 抖动期间发号全挂**。真实事故是 DB 主从切换 3 秒,期间所有发号 timeout。解决方案是**双 buffer**——buffer_A 用到 80% 就异步预取 buffer_B,用完无缝切换,P99 从 50ms 降到 0.5ms。
>
> ID 到短码不能直接 base62——**连续 ID 会生成相邻短码,被爬虫扫**。真实踩过坑,1 天被爬 1 亿短链。所以 **ID XOR magic_key 加扰再 base62**,XOR 是双射保证唯一,加扰后短码看起来随机,扫描成功率从 80% 降到 0.001%。密钥定期轮换。
>
> 还有两层兜底必须有。**DB UNIQUE 短码列**——号段池理论不冲突,但跨机房配置错误会段重叠,UNIQUE 是最后一道防线,冲突立刻报错重试。**业务契约**——必须显式告诉业务方"ID 不保证连续",应用重启 / 切 buffer 都会跳跃,提前讲清楚比事后修代码省 10 倍力气。
>
> step 选 10000 是甜点值——小了 DB 压力大,大了应用挂浪费多;监控关键指标:发号 P99 < 1ms / 双 buffer 切换频率 / UNIQUE 冲突率 = 0 / 号段消耗速度。

### 一句话核心

> **号段池(step 1w)+ 双 buffer(80% 预取)+ XOR 加扰防爬 + DB UNIQUE 兜底 + 业务契约"ID 不保证连续"**

### 背诵版(更精简)

> 短码发号 = **号段池预分配**(step 10000,DB QPS 5 次/秒)+ **双 buffer**(80% 阈值预取,P99 < 1ms)+ **ID XOR 加扰**(防猜测)+ **base62 编码**(短码 6-8 位)+ **DB UNIQUE 兜底**(冲突率 0)。生产踩坑:单 buffer 抖动会卡发号、不加扰会被爬虫扫、step 太小压垮 DB、业务方不能依赖 ID 连续性。容灾:号段 DB 挂双 buffer 续命 1-2s,降级 Snowflake。详见 [02-short-code-platform](../10-system-design/02-short-code-platform.md) 和 [23-id-generator-system-4s](../10-system-design/23-id-generator-system-4s.md)。

## Q6 MySQL 大表如何分库分表

### 场景设定

> 抖音电商订单表,单表 5 亿行,占 1.2TB,慢查询频繁,主从复制延迟从 1 秒涨到 30 秒。要求拆成可持续 5 年的方案,**单表 < 2000 万行**,QPS 从 5w 提到 50w,延迟从 200ms 降到 20ms。

### 一句话本质

**先垂直后水平,选好分片键(避免跨片 join),用基因法解决 order_id 反查,异构索引解决 B 端查询,T+1 全量 + 实时增量做迁移**,核心是"路由确定性 + 扩容平滑性 + 查询全覆盖"。

### 面试答题节奏(故事版)

#### 1. 场景具体化

抖音电商订单表,单表 5 亿行,占 1.2TB,慢查询频繁,主从复制延迟从 1 秒涨到 30 秒——单表已经撑不住,B+ 树高度从 3 层涨到 4 层,每次查询多一次磁盘 IO,QPS 上限被锁死。目标拆成**可持续 5 年的方案**,单表 < 2000 万行,QPS 从 5w 提到 50w,延迟从 200ms 降到 20ms。

#### 2. 为什么单表 2000 万是红线

InnoDB B+ 树 3 层能存:
- 单页 16KB,假设主键 8B + 指针 6B = 14B/项
- 非叶子节点:16KB / 14B ≈ 1170 项
- 叶子节点假设单行 1KB:16 项
- 3 层 = 1170 × 1170 × 16 ≈ 2200 万行

**超过 2000 万 → 4 层 B+ 树 → 多一次磁盘 IO → QPS 直接砍半**。这是分表的物理边界,不是经验值。

#### 3. 核心方案——32 库 1024 表

| 维度 | 选择 | 原因 |
| --- | --- | --- |
| 分片键 | `user_id` | C 端查询占 90%,user 是天然边界 |
| 分库数 | 32 | 单机 1.5TB / 32 = 50GB(5 年余量) |
| 分表数 | 1024(每库 32 表)| 单表 < 2000w 行 |
| 路由 | `user_id % 32` 库,`(user_id / 32) % 32` 表 | 同 user 同库同表 |

**为什么不直接 64 库**:单库 32 表已足够,库越多管理成本(连接池 / 备份 / 监控)成倍上升,32 库 × 1.5w QPS = 50w 已达标。

#### 4. order_id 基因法——反查性能差 1000 倍的关键

最常被忽略的点:**用户查订单走 user_id 路由没问题,但支付回调只有 order_id 怎么办?**

不基因法的暴力方案:
```sql
SELECT * FROM orders WHERE order_id = ?
-- 不知道在哪个库哪个表 → 全库扫 1024 表 → P99 5 秒
```

基因法把 user_id 的分片信息**内嵌到 order_id 里**:
```
order_id 64 bit = 1 + 41 + 10 + 12
                  保留  时间戳 库表位  序列
                              ↑
                              user_id 低 10 位
                              (5 bit 库 + 5 bit 表)

支付回调:order_id → 提取 bit[12:22] → 直接定位库表 → P99 5ms
```

性能差 1000 倍。生产真实压测数据。

#### 5. 异构索引——B 端商家查询的解法

C 端按 user_id 分片很顺,**但商家后台要按 seller_id 看订单**——这时候 1024 表全要扫,根本不可用。

解决方案:**MySQL → Canal → Kafka → ES**,按 seller_id 建异构索引。
- C 端走 MySQL(user_id 分片)
- B 端走 ES(seller_id 索引)
- 一致性:T+秒 异步(商家能接受 1-2 秒延迟)
- 详见 [24b-order-system-4s 三大考点](../10-system-design/24b-order-system-4s.md)

#### 6. 数据迁移——双写灰度的标准节奏

不是停机迁移,生产不允许。标准 4 步:
```
1. 全量 dump   旧表 → 新分片表(凌晨低峰,工具 mysqldump / DataX)
2. 增量 binlog  全量期间产生的变更 → Canal 追到新表
3. 双写灰度   应用同时写新旧,旧表为准;新表数据校验 1-2 周
4. 切读切写   按 user_id % 100 灰度,1% → 10% → 50% → 100%
```

**关键检查点**:校验阶段必须有 diff 工具按行对比新旧表,差异 > 0 不能切流。

#### 7. 5 年容量必须考虑冷热分离

5 年累计估算:
```
日单量增长:第 1 年 2000w → 第 5 年 1 亿(5×)
5 年累计:  365 × (2000w + 1 亿) / 2 ≈ 1100 亿单
分表后单表:1100 亿 / 1024 = 1.07 亿(超 2000w 红线 5 倍!)
```

**结论**:即使 1024 表也撑不到 5 年,必须**冷热分离**:
- 热(3 个月)→ MySQL 1024 表
- 温(3-12 个月)→ MySQL 归档库或 TiDB
- 冷(> 1 年)→ HBase / 对象存储
- C 端默认查 3 个月,超过提示"查归档"(用户接受)

#### 8. 永远不扩逻辑库——预留扩容方式

最容易踩的坑:32 库不够要扩到 64 库 → **全量 rehash 数据,1 个月窗口期,业务停滞**。

正确做法:**初始就定 1024 个逻辑表,物理上先放 32 个库,扩容时按 (32→64→128) 物理库迁移**,逻辑表不变,数据按库整体搬,无需 rehash。

```
初始:库 0..31,每库 32 表(逻辑表 0..1023)
扩容:库 0..63,每库 16 表(逻辑表 0..1023 不变)
数据迁移:库 0 的后 16 表 → 库 32,无需重新计算路由
```

### 九维度深度展开(追问储备)

#### 1. 分布式一致性(主战场)

**分片策略**:

| 维度 | 选择 | 原因 |
| --- | --- | --- |
| 分片键 | `user_id` | C 端查询占 90%,user 是天然边界 |
| 分库数 | 32 | 单机 1.5TB / 32 = 50GB(预留 5 年增长) |
| 分表数 | 1024(每库 32 表)| 单表 < 2000w 行(B+ 树 3 层) |
| 路由 | `user_id % 32` 库,`(user_id / 32) % 32` 表 | 同 user 同库同表 |

**为什么不分 64 库**:
- 单库 32 表已经足够(单表 < 2000w 行)
- 库越多,管理成本越高(连接池、备份、监控)
- 32 库已经能撑 50w QPS(单库 1.5w QPS × 32)

#### 2. 服务治理(主战场)

**ShardingSphere / MyCat 选型**:

| 维度 | ShardingSphere-JDBC | MyCat / ShardingSphere-Proxy |
| --- | --- | --- |
| 部署 | jar 嵌入应用 | 独立中间件 |
| 性能 | 高(直连)| 多一跳网络 |
| 维护 | 应用层升级 | 中间件统一升级 |
| Go 支持 | 弱 | 强(MySQL 协议透明) |
| 推荐 | Java 团队 | Go / 多语言团队 |

**Go 团队建议**:自研轻量路由(基于 `database/sql` 包装),或用 `vitess`(YouTube 开源)。

#### 3. 缓存与 DB 优化(主战场)

**order_id 基因法(关键!)**:
```
order_id 64 bit = 1 + 41 + 5 + 5 + 12
                  ↑   ↑   ↑   ↑   ↑
                  保留 时间戳 库号 表号 序列
                                bit 5+5=10 = user_id 低 10 位

正向查:user_id → user_id%32 库,(user_id/32)%32 表 → SELECT
反向查:order_id → 提取 bit[12:22] → 直接定位库表
```

**收益**:
- 不基因法:`SELECT FROM 1024 表 WHERE order_id=?` → 全库扫
- 基因法:`SELECT FROM orders_X_Y WHERE order_id=?` → 单表查
- 性能差 1000×

**异构索引(B 端查询)**:
```
A 端查询(C 端用户):走分片表(user_id 维度)
B 端查询(商家)   :走 ES 异构索引(seller_id 维度)
                   └─ MySQL binlog → Canal → Kafka → ES
```

#### 4. 异步消息

- **数据迁移**:全量 dump + 增量 binlog 同步(双写校验后切流量)
- **跨片事务**:本地消息表(详见 Q3)避免分布式事务
- **统计查询**:走异步链路(Hadoop / ClickHouse),不走 OLTP

#### 5. 限流熔断降级

- **跨片 SQL 限流**:扫所有 1024 表的 SQL 单独限流(防慢查询打挂集群)
- **降级**:特殊查询走异步队列(如商家月报)
- **路由失败兜底**:返回友好错误,记录排查

#### 6. 容灾恢复

| 场景 | 应对 |
| --- | --- |
| 单库主挂 | MHA 切从,30 秒恢复(详见 [order-system-qa Q1](order-system-qa.md)) |
| 单库丢数据 | binlog 增量恢复 + T+1 备份兜底 |
| 路由元数据错乱 | 配置中心兜底 + 蓝绿发布 |
| 全库挂(机房故障)| 跨机房灾备(同步双写或异步备份) |

#### 7. 监控告警

```
关键指标:
- 各库 QPS / 慢查询(差异 > 50% → 数据倾斜)
- 跨片查询占比(目标 < 5%)
- B+ 树高度(单表 > 2000w → 告警准备扩容)
- 主从延迟(> 5s → P1)

- 检测:Top 1% user_id 占总订单 > 10% → 大用户
- 解决:大用户独立分片(white list 路由)
```

**5 年容量估算**:

```
日单量增长:第 1 年 2000w → 第 5 年 1 亿(5×)
5 年累计:    365 × (2000w + 1 亿) / 2 ≈ 1100 亿单
分表后单表:1100 亿 / 1024 = 1.07 亿(超 2000w 红线!)
```

- 冷数据(> 1 年):HBase / 对象存储

#### 9. 真实优化经验

**踩坑 1:分片键选错(用 `created_at`)**
- 现象:每月新表 100% 写入,旧表只读 → 写入热点
- 优化:改 `user_id` 散列
- 收益:写入均衡,P99 从 500ms 降到 50ms

**踩坑 2:跨片 join 性能差**
- 现象:`SELECT FROM orders JOIN users ON ...` 触发 1024 库查询
- 优化:冗余 user 字段到 orders + 走 ES 做复杂查询
- 收益:跨片 SQL 占比从 30% 降到 < 5%

**踩坑 3:基因法没考虑,order_id 反查全库扫**
- 现象:支付回调 `WHERE order_id=?` 扫 1024 库,P99 5s
- 优化:order_id 内嵌 user_id 后 10 位,直接定位
- 收益:P99 5s → 5ms

**踩坑 4:扩容时全量 rehash 数据**
- 现象:32 库扩到 64 库需要全量 rehash 1 个月
- 优化:**永远不扩逻辑库**,只扩物理集群(详见 [order-system-qa Q1 子节](order-system-qa.md))
- 收益:扩容 0 数据迁移

**踩坑 5:全局唯一 ID 用 auto_increment**
- 现象:32 库各自 auto_increment 冲突,id 不唯一
- 优化:Snowflake 改造 + 基因法
- 收益:全局唯一 + 反查 O(1)

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 分库数 | 32 | 物理库或逻辑库 |
| 分表数 | 1024 | 32 库 × 32 表 |
| 单表行数红线 | < 2000w | B+ 树 3 层 |
| 跨片 SQL 占比 | < 5% | 健康水位 |
| 主从延迟 | < 1s | 健康 |
| QPS 上限 | 50w | 32 库 × 1.5w |
| 5 年容量 | 1100 亿 | 需冷热分离 |

### 易错点

- ❌ 分片键选 `auto_increment` → 数据倾斜(后表热前表冷)
- ❌ 不用基因法 → order_id 反查全库扫
- ❌ 分库分表后还做 join → 跨片性能差
- ❌ 没监控数据倾斜 → 大用户单库打满
- ❌ 扩容时扩逻辑库 → 全量 rehash
- ❌ 不做冷热分离 → 5 年后单表爆 2000w 红线

### 追问预案

1. **为什么是 32 而不是 16 / 64?** 单库 50GB(5 年容量)+ 2 的幂便于哈希 + 32 × 1.5w QPS = 50w
2. **怎么避免分布式事务?** 同 user_id 单库内事务(99% 场景),跨片走本地消息表
3. **怎么处理大用户?** white list 独立分片 + 异步聚合
4. **B 端商家怎么查?** ES 异构索引(MySQL → Canal → Kafka → ES)
5. **数据迁移怎么做?** 双写灰度 → 全量 dump → 增量 binlog → 校验切流
6. **能用 TiDB / OceanBase 替代吗?** 可以,但成本高 + 学习曲线陡,大厂自研 sharding 更可控
7. **怎么处理唯一索引?** 全局唯一索引在 Redis(sku_code)或独立表
8. **range 查询怎么办?** 走 ES,不走 MySQL(MySQL range 跨片性能差)

### 面试回答版

> 分库分表的本质是**用路由确定性换扩容平滑性**——核心是三件事:**选对分片键**(决定 90% 查询能不能命中单库)、**基因法解决反向查询**(订单号反查不能全库扫)、**异构索引解决多维度查询**(B 端按商家查不能让 1024 表全扫)。
>
> 分片设计 32 库 1024 表,公式很硬:**单表 < 2000 万行(B+ 树 3 层物理边界)**,超过就 4 层多一次 IO,QPS 砍半。分片键选 user_id 是因为 C 端查询占 90%,user_id 天然边界,同用户单库内事务搞定 99% 场景。
>
> 基因法是面试加分点——支付回调只有 order_id,如果不做基因法,反查会扫 1024 表 P99 5 秒;基因法把 user_id 低 10 位内嵌到 order_id 里(64 位 = 1 + 41 时间戳 + 10 库表位 + 12 序列),反查直接定位库表,P99 5ms,**性能差 1000 倍**。
>
> B 端查询走异构索引,**MySQL → Canal → Kafka → ES**,按 seller_id 建索引,T+秒 异步一致(商家能接受 1-2 秒延迟)。这是分库分表的标配,不能让 1024 表全扫。
>
> 数据迁移必须双写灰度——全量 dump + 增量 binlog + 双写校验 1-2 周 + 按 user_id % 100 灰度切流(1% → 10% → 50% → 100%),diff 工具按行对比,差异 > 0 不能切。
>
> 5 年容量必须考虑冷热分离——1100 亿单 / 1024 表 = 1 亿/表,超过 2000w 5 倍,所以热数据 3 个月在 MySQL,温在归档,冷在 HBase。**扩容只扩物理集群,逻辑库永远 1024 表**,避免全量 rehash,这是预留扩容方式的关键。

### 一句话核心

> **`user_id` 分片(C 端 90%)+ 32 库 × 32 表(单表 < 2000w)+ order_id 基因法(反查 O(1))+ ES 异构索引(B 端 seller_id)+ 冷热分离 + 扩物理不扩逻辑(0 数据迁移)**

### 背诵版(更精简)

> 分库分表 = **垂直拆 + 水平分**(32 库 × 32 表 = 1024)+ **`user_id` 分片**(C 端 90% 查询)+ **基因法**(order_id 内嵌 user_id 低 10 位,反查 O(1))+ **异构索引**(B 端走 ES)+ **冷热分离**(5 年容量必须)。扩容只扩物理集群,逻辑库永远 32(避免 rehash)。生产踩坑:分片键不能用时间(倾斜)、跨片 join 必须冗余、order_id 必须基因法、大用户独立分片。

## Q7 Redis 缓存穿透 / 击穿 / 雪崩如何处理

### 场景设定

> 抖音电商商品详情页,日 PV 50 亿,峰值 100w QPS。Redis 集群承载 99.9% 读流量。某个攻击 / 故障场景下,流量穿透到 MySQL,直接打挂(MySQL 读 QPS 上限 5w)。要求**穿透 / 击穿 / 雪崩三个场景的应对方案**,业务无损。

### 一句话本质

- **穿透**(查不存在的 key):**Bloom filter** + **空值缓存** + **参数校验**
- **击穿**(单热 key 失效):**互斥锁** + **逻辑过期** + **永不过期(后台刷)**
- **雪崩**(批量 key 同时失效):**TTL 加随机抖动** + **多级缓存** + **熔断降级**

### 面试答题节奏(故事版)

#### 1. 场景具体化

抖音电商商品详情页,日 PV 50 亿,峰值 100w QPS,Redis 集群承载 99.9% 读流量。MySQL 读 QPS 上限大概 5w,**只要缓存出问题流量穿到 DB,就是 P0 故障**——MySQL 直接打挂,详情页全站白屏。

#### 2. 三个问题不是一回事——本质对比

| 问题 | 本质 | 触发条件 | 危险等级 |
| --- | --- | --- | --- |
| 穿透 | 查**根本不存在**的 key | 攻击 / 错误查询 | 持续打 DB |
| 击穿 | **单个热 key** 失效瞬间 | TTL 到期 | 单 key 流量打爆单节点 |
| 雪崩 | **大量 key** 同时失效 | 整点 / 重启 / 预热失误 | DB 瞬间被打挂 |

三个问题的应对**完全不同**,不能混为一谈。

#### 3. 穿透——为什么 Bloom filter 是首选

最容易踩的坑:只用空值缓存。攻击者用**海量随机 key**(UUID / 时间戳)打,每个 key 缓存 60s,内存瞬间被占满,而且攻击者随机生成新 key 永远绕过空值缓存。

**Bloom filter 设计**:
```
存量 key:10 亿
误判率:0.1%
位数:14.4 亿 bit ≈ 180MB
hash 函数数:10
重建周期:每天凌晨全量重建
双 Bloom 切换:防止重建期间命中率下降
```

**为什么不能删 key**:Bloom filter 标准结构不支持删除(会误删其他 key),只能**双 Bloom 切换**——新 Bloom 后台构建好,原子切换。

#### 4. 击穿——三种方案对比

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| **互斥锁(SingleFlight)** | 强一致场景 | 抢锁失败的请求要等待,P99 上涨 |
| **逻辑过期** | 高读 + 容忍旧值 | 短暂返回过期数据 |
| **永不过期 + 后台刷** | 极热 key | 内存占用大,刷新延迟 |

**互斥锁陷阱**:抢到锁的实例查 DB 超时,锁没释放后续请求全卡。生产做法:
- 锁加 TTL(10s 强释放)
- 抢锁失败 → 返回**旧值** / 默认值,不阻塞
- Lua 释放锁(`WHERE value = uuid`,防止误删)

```go
if lock := redis.SetNX("lock:"+key, uuid, 10*time.Second); lock {
    defer redis.LuaDel("lock:"+key, uuid)
    val := db.Query(...)
    redis.Set(key, val, ttl)
    return val
}
// 抢锁失败,返回旧值或默认值
return getOldOrDefault(key)
```

#### 5. 雪崩——TTL 抖动 + 多级缓存

整点失效是雪崩的经典触发——00:00 大量缓存同时失效,DB 瞬间 10w QPS 被打挂。**TTL 加 0-5min 随机抖动**就能解决 90% 雪崩:
```go
ttl := baseTTL + time.Duration(rand.Intn(300)) * time.Second
```

多级缓存才是终极防御:
```
L0 浏览器(Cache-Control)  → 30% 流量
L1 CDN                     → 30%
L2 应用本地(Caffeine 1s)  → 30%
L3 Redis 集群              → 9%
L4 MySQL                   → 1%
```

**100w QPS 最终打到 MySQL 的只有 1w**,在 5w 红线内。

#### 6. 写一致性——Cache-Aside 标准做法

**写时:先更新 DB,再删缓存(不是更新缓存)**。

为什么先 DB 再删缓存而不是先删:
- 先删后写:读请求在写完前进来 → 重新填充旧值
- 先写后删:不一致窗口只有删除前的一小段,且 TTL 兜底
- 极端情况(主从延迟):**延迟双删**——写完延迟 1s 再删一次

**绝对不能"更新缓存"**:并发更新会导致旧值覆盖新值,不一致比删除严重得多。

#### 7. 热点 key 探测——单 key 30w QPS 怎么救

某商品突然爆款,单 key 30w QPS,**Redis 单节点上限 10w**,直接打挂。两层应对:
- **本地缓存兜底**(Caffeine 1 秒 TTL)——同实例内重复请求不打 Redis
- **热点 key 复制**——单 key 复制到 5 个 Redis 节点(`key:{hot}_0..4`),客户端随机读一个,**单点 QPS 降到 6w**

热点探测:Redis monitor 抽样 + 应用层埋点,QPS > 5000 自动标记 + 推到本地缓存。

#### 8. 监控——雪崩的早期信号

```
关键指标:
- 缓存命中率(目标 > 99%,< 95% → P2,< 80% → P0 已雪崩)
- 单 key QPS(> 5000 → 热点告警)
- 不存在 key 查询比例(> 5% → 穿透攻击)
- DB QPS 突增(可能缓存失效雪崩)
- Redis 内存(> 80% → P2,> 90% → P1)
```

**命中率从 99% 跌到 95% 就是雪崩前夜**,5 分钟内不响应可能就是 P0。

### 九维度深度展开(追问储备)

#### 1. 分布式一致性

- 缓存与 DB 的一致性是**最终一致**(Cache-Aside 模式)
- 写时:**先更新 DB,再删缓存**(不是更新缓存)
- 极小概率不一致:删除失败 / 主从延迟 → 通过 TTL 兜底 + binlog 监听异步刷新

#### 2. 服务治理(主战场)

**穿透防御**:

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| **Bloom filter** | 大量不存在 key | 1% 误判率,需重建 |
| **空值缓存** | 少量不存在 key | 占空间,TTL 短(60s) |
| **参数校验** | 格式攻击 | 网关层挡掉 |
| **风控限流** | 恶意攻击 | 单 IP / 单用户限频 |

**Bloom filter 配置**:
```
存量 key:10 亿
误判率:0.1%
位数:14.4 亿 bit ≈ 180MB
hash 函数数:10
重建周期:每天凌晨全量重建
```

**击穿防御**:
```go
// 互斥锁(Singleflight 模式)
func GetWithLock(key string) (string, error) {
    val, hit := redis.Get(key)
    if hit { return val, nil }
    
    // 抢锁,只有一个请求查 DB
    if lock := redis.SetNX("lock:"+key, 1, 10*time.Second); lock {
        defer redis.Del("lock:" + key)
        val := db.Query(...)
        redis.Set(key, val, ttl)
        return val, nil
    }
    
    // 没抢到锁,等 100ms 重试
    time.Sleep(100 * time.Millisecond)
    return GetWithLock(key)
}
```

**逻辑过期**:
```go
// value 内嵌过期时间,永不真过期
type CacheValue struct {
    Data       string
    ExpireAt   time.Time
}

func GetLogicalExpire(key string) string {
    val := redis.Get(key)
    if val.ExpireAt.Before(time.Now()) {
        // 已过期,异步刷新,先返回旧值
        go refresh(key)
    }
    return val.Data
}
```

**雪崩防御**:
```go
// TTL 加随机抖动
ttl := baseTTL + time.Duration(rand.Intn(300)) * time.Second
redis.Set(key, val, ttl)  // 5min ± 5min,避开整点失效
```

#### 3. 缓存与 DB 优化(主战场)

**多级缓存**:
```
L0 浏览器缓存(304/Cache-Control)→ 30% 流量
L1 CDN 缓存                       → 30%
L2 应用本地缓存(Caffeine,1 秒 TTL)→ 30%
L3 Redis 集群                     → 9%
L4 MySQL                          → 1%
```

**热点 key 探测**:
- Redis monitor + 抽样统计
- 单 key QPS > 5000 → 标记热点 → 自动复制到本地缓存
- 关键 key 提前预热(开抢前 10 分钟 warm)

#### 4. 异步消息

- **缓存刷新解耦**:DB 更新后发 MQ,消费者删 / 刷新缓存
- **避免发布消息时的级联失败**:消息消费失败 → DLQ + 重试

#### 5. 限流熔断降级

**Redis 挂的降级**:
```
正常:Redis(10w QPS) → MySQL 兜底
极端:Redis 挂 → 直接打 MySQL → MySQL 5w 限流 → 拒绝部分请求
```

**降级开关**:
- 缓存挂 → 静态降级页(库存紧张 / 详情简化)
- DB 挂 → 全静态(从 CDN 取最近一份)

#### 6. 容灾恢复(主战场)

| 故障 | 应对 |
| --- | --- |
| 单 Redis 节点挂 | 哨兵 / cluster 自动切从 |
| 整 Redis 集群挂 | MySQL 兜底 + 全局限流 |
| Bloom filter 误判 | 空值缓存兜底 |
| 缓存全部失效(冷启动)| 预热 + 限流保护 DB |

**冷启动预热**:
```
机器重启 / 集群扩容:
1. 配置中心标记"预热中"
2. 应用启动时拉取 Top 10000 热 key 到本地缓存
3. 异步预热 Redis(分批写入)
4. 预热完成 → 切流量
```

#### 7. 监控告警(主战场)

```
关键指标:
- 缓存命中率(目标 > 99%,< 95% → 告警)
- 单 key QPS(> 5000 → 热点告警)
- 不存在 key 查询比例(> 5% → 穿透攻击)
- Redis 内存(> 80% → P2,> 90% → P1)
- DB QPS 突增(可能缓存失效雪崩)

告警阈值:
- 命中率 < 95% → P2(可能开始雪崩)
- 命中率 < 80% → P0(已经雪崩)
- DB QPS > 平时 3× → P1(缓存可能挂)
```

#### 8. 压测与容量评估

```
日 PV 50 亿,峰值 100w QPS
Redis 集群:10 主 10 从,单节点 10w QPS
内存:10 亿 key × 200 字节 ≈ 200GB,每节点 20GB
本地缓存:Top 10000 key × 200 字节 = 2MB,可忽略
```

#### 9. 真实优化经验

**踩坑 1:Bloom filter 误判率监控缺失**
- 现象:误判率从 0.1% 涨到 5%,大量穿透
- 优化:监控误判率 + 定期重建 + 双 Bloom 切换
- 收益:误判率稳定 < 0.5%

**踩坑 2:缓存雪崩(整点失效)**
- 现象:00:00 大量缓存同时失效,DB 瞬间 10w QPS 打挂
- 优化:TTL 加 0-5min 随机抖动
- 收益:DB QPS 平滑

**踩坑 3:热点 key 单节点打挂**
- 现象:某商品突然爆款,单 key 30w QPS,单节点扛不住
- 优化:本地缓存 1 秒 TTL + 热点 key 复制到多节点
- 收益:单节点 QPS 降到 5w 内

**踩坑 4:缓存与 DB 不一致(主从延迟)**
- 现象:主库写完,缓存读从库还是旧值,缓存被刷脏
- 优化:写后延迟 1s 再删缓存(Cache-Aside Delayed Double Delete)
- 收益:不一致窗口 < 1s

**踩坑 5:Singleflight 锁未释放导致 DB 串行**
- 现象:抢到锁的实例查 DB 超时,锁未释放,后续请求全等
- 优化:锁加 TTL(10s)+ try lock 失败返回旧值
- 收益:不阻塞其他请求

### 量化数据卡

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 缓存命中率 SLO | > 99% | 健康水位 |
| 单 Redis 节点 | 10w QPS | 上限 |
| Bloom filter 内存 | 180MB | 10 亿 key + 0.1% 误判 |
| TTL 抖动 | 0-5min | 防雪崩 |
| 本地缓存 TTL | 1s | 热点 key |
| 互斥锁 TTL | 10s | 防永久 |

### 易错点

- ❌ 穿透只用空值缓存(攻击者用海量随机 key 打爆)→ 加 Bloom
- ❌ 击穿只用互斥锁(锁超时风险)→ 加锁 TTL + 旧值兜底
- ❌ 雪崩只设统一 TTL → 加抖动
- ❌ 写时先删缓存再更新 DB → 不一致(读请求填旧值)
- ❌ Bloom filter 不重建 → 误判率上涨
- ❌ 不监控命中率 → 雪崩看不到征兆

### 追问预案

1. **Bloom filter 怎么删 key?** 不能删,只能重建(双 Bloom 切换)
2. **空值缓存为什么 TTL 要短?** 防止恶意 key 长期占内存,60s 即可
3. **互斥锁会不会死锁?** 加 TTL + Lua 释放(WHERE value = uuid)
4. **逻辑过期 vs 互斥锁怎么选?** 逻辑过期(高读 + 容忍旧值);互斥锁(强一致)
5. **多级缓存 TTL 怎么协调?** 越靠近用户 TTL 越短(本地 1s,Redis 5min,CDN 1h)
6. **怎么测试雪崩?** Chaos Engineering:批量 EXPIRE 测试 + 压测 DB 兜底
7. **写多读少场景还要缓存吗?** 看读 / 写比,1:10 以下可考虑不缓存(写时维护缓存成本高)

### 面试回答版

> Redis 三大问题的本质区别要先讲清楚——**穿透是查不存在的 key**(攻击 / 错误查询)、**击穿是单热 key 失效瞬间**(单点流量)、**雪崩是大量 key 同时失效**(整点 / 重启)。三个问题应对完全不同,不能用一套方案。
>
> 穿透首选 **Bloom filter**(180MB 撑 10 亿 key,0.1% 误判)而不是空值缓存——攻击者用海量随机 key 打,空值缓存内存秒爆;Bloom 不能删 key,**双 Bloom 切换** 重建。再叠加参数校验 + 风控限流双兜底。
>
> 击穿核心是**互斥锁 + 旧值兜底**——抢到锁的查 DB,**抢锁失败不阻塞,返回旧值或默认值**。锁必须有 TTL(10s 强释放),Lua 释放防误删。强一致用互斥锁,高读容忍旧值用逻辑过期。
>
> 雪崩 90% 用 **TTL 加 0-5min 随机抖动**就能搞定,但终极防御是**多级缓存**——浏览器 30% / CDN 30% / 本地 Caffeine 30% / Redis 9% / MySQL 1%,100w QPS 最终到 MySQL 只剩 1w 在 5w 红线内。
>
> 写一致性必须 **Cache-Aside 先 DB 后删缓存**(不是更新缓存),主从延迟用**延迟双删**(写完 1s 再删一次)。绝对不能"更新缓存",并发覆盖比删除严重 10 倍。
>
> 还有热点 key 怎么救——某商品突然爆款单 key 30w QPS,Redis 单节点 10w 上限直接挂。**本地缓存 1 秒 TTL** + **热点 key 复制到 5 节点** (`key:{hot}_0..4` 客户端随机读),单点 QPS 降到 6w。
>
> 监控核心:命中率从 99% 跌到 95% 就是雪崩前夜,5 分钟内不响应可能 P0。

### 一句话核心

> **穿透 Bloom filter + 双切换;击穿互斥锁 + 旧值兜底(锁有 TTL);雪崩 TTL 抖动 + 多级缓存;写时 Cache-Aside 延迟双删;热点 key 复制 + 本地缓存**

### 背诵版(更精简)

> Redis 三大问题:**穿透**用 Bloom filter(180MB)+ 空值缓存(60s);**击穿**用互斥锁 / 逻辑过期 / 后台刷;**雪崩**用 TTL 抖动 + 多级缓存 + 熔断降级。多级缓存:浏览器 30% + CDN 30% + 本地 30% + Redis 9% + DB 1%。生产踩坑:Bloom 不重建误判涨、TTL 不抖动整点雪崩、热点 key 单节点打挂(本地缓存救命)、写时先 DB 后缓存(避免脏数据)。监控:命中率 / 单 key QPS / 不存在 key 比例 / DB QPS 突增。

## Q8 MQ 消息重复 / 丢失 / 顺序如何处理

### 场景设定

> 抖音电商订单系统用 RocketMQ,日 10 亿消息,峰值 50w TPS。生产 / 网络 / Broker / 消费四个环节都可能出问题:**重复**(三方回调常见)、**丢失**(消费者宕机)、**乱序**(同 key 消息散到不同分区)。要求**消息不丢、不乱、可幂等**,业务无损。

### 一句话本质

- **不丢**:**生产 ack** + **Broker 持久化** + **消费 ack**(三段确认)
- **不重**:**消费者幂等**(message_id / 业务 ID UNIQUE)
- **保序**:**同业务 key 同分区**(Kafka 用 key,RocketMQ 用 MessageQueueSelector)

### 面试答题节奏(故事版)

#### 1. 场景具体化

抖音电商订单 RocketMQ,日 10 亿消息,峰值 50w TPS。MQ 是订单系统的命脉——下单 / 库存 / 支付 / 通知全靠它解耦,**消息丢一条就是一笔订单丢失**。三个问题必须同时解决:重复、丢失、乱序。

#### 2. 不丢——必须做"三段确认"

不丢消息不是一道防线,是**三个环节都要扛**:

```
生产端           Broker             消费端
  │                │                  │
  │── 发送 ──→     │                  │
  │   ← ack ──     │                  │
  │   重试 3 次     │                  │
  │   失败 → 本地消息表兜底             │
  │                │                  │
  │                │── 同步刷盘        │
  │                │── 主从同步        │
  │                │                  │
  │                │── 投递 ──→       │
  │                │   ← ack ──       │
  │                │   超时重投         │
```

**最容易踩的坑**:消费端**先 ack 后处理**——收到消息立即 ack,然后业务异常,**消息就丢了**。正确做法:业务处理成功后再 ack,失败让 Broker 重投。

#### 3. Broker 持久化——同步刷盘 vs 异步刷盘的取舍

| 场景 | 配置 | 性能损失 |
| --- | --- | --- |
| **资金类(零丢失)** | 同步刷盘 + 同步双写 | -60% |
| **订单类(秒级可丢)** | 同步刷盘 + 异步复制 | -30% |
| **日志类(可丢秒级)** | 异步刷盘 + 异步复制 | 0 |

订单一般选 **同步刷盘 + 异步复制**——单机宕机不丢(刷盘保证),机房故障可接受丢 1-2 秒(异步复制),性能损失 30% 可接受。资金类必须 **同步双写**,零容忍。

#### 4. 不重——幂等用业务 ID 不用 message_id

最常见错误:**幂等用 message_id**。

```
生产端因 ack 超时重发 → 新 message_id
但业务上是同一笔订单
→ 消费两次,业务执行两次
```

**正确做法**:幂等用**业务 ID**(order_id / pay_no),跨重发也幂等。

```go
func consume(msg *Message) error {
    bizID := extractOrderID(msg)  // 用业务 ID 不用 msg.ID
    
    // L1 Redis 快速去重(60s TTL)
    if !redis.SetNX("idem:order:"+bizID, 1, 60*time.Second) {
        return nil  // 已处理,直接 ack
    }
    
    // L2 DB UNIQUE 兜底
    if err := db.Exec("INSERT IGNORE INTO consume_log (biz_id) VALUES (?)", bizID); err != nil {
        return err
    }
    
    return processOrder(msg)
}
```

#### 5. 保序——同 key 同分区是底线

订单状态机:`WAIT_PAY → PAID → SHIPPING → COMPLETED`,如果乱序消费,**CANCEL 先到 PAID 后到**,业务彻底崩溃。

**实现**:
```go
// RocketMQ:同 order_id 路由到同一队列
producer.SendOrderly(msg, func(mqs []*MessageQueue, msg *Message, arg interface{}) *MessageQueue {
    orderID := arg.(int64)
    return mqs[orderID % len(mqs)]  // 同 order_id 同队列
}, orderID)

// Kafka:同 order_id 用同 key
producer.Send(&kafka.Message{
    Key:   []byte(orderID),  // 同 key 同 partition
    Value: data,
})
```

**坑点**:同分区内**多线程消费 → 乱序**。必须 **MessageListenerOrderly**(分区内单线程)。

三种保序粒度:
- **全局有序**:单分区 + 单消费者 → 牺牲并发,只用于极少场景
- **分区有序**(99% 场景):同业务 key 同分区,分区内单线程
- **业务有序**:应用层重排,复杂度高,慎用

#### 6. DLQ 必须监控——静默丢消息的元凶

RocketMQ 消费失败 16 次 → 进 DLQ(`%DLQ%consumer_group`),**默认不会再消费**。

**最坑的真实事故**:DLQ 没监控,1 万条订单消息进 DLQ,1 周后用户投诉才发现,**全部要人工补单**。

必备 SOP:
```
DLQ 消息数 > 0 → P1 告警
SOP:人工查根因(代码 bug / 三方接口挂 / 数据脏)
   → 修复后从 DLQ 重投
   → 或人工补偿(对账后补单)
```

#### 7. 消息堆积——分级应对

```
堆积量      应对
< 10w      正常消费,无需干预
10-100w    扩消费者(scale up,但分区数是上限)
> 100w     临时建新 topic,生产端切到新 topic
           老 topic 用大批量异步消费 / 直接归档
> 1亿      建新 topic + 业务降级 + 老消息 24h 后归档处理
```

**根因排查**:消费速度变慢(GC / 慢 SQL / 第三方接口) vs 生产突增(上游异常)——日志 + 监控指标对比。

#### 8. 监控——四个指标 + 阈值

```
- 生产 TPS / 消费 TPS / 积压数
  → 积压 > 10w P2,> 100w P0
- 消费延迟(end_to_end)
  → > 30s P1
- DLQ 消息数(SLO = 0)
  → > 0 P1
- Broker 磁盘水位
  → > 85% P1,> 90% 拒绝写入
```

容量估算:50w TPS = 5 主 Broker × 10w + 32 分区(留 6× 余量),存储 1B 消息 × 1KB × 7 天 = 7TB,单 Broker 1.5TB。

### 九维度深度展开(追问储备)

#### 1. 分布式一致性(主战场)

**生产端不丢**:
```
RocketMQ:同步发送 + ack 确认 + 重试 3 次
失败兜底:本地消息表(详见 Q3)
极端:发送队列堆积 → 拒绝业务请求(熔断)
```

**Broker 端不丢**:
```
RocketMQ:
- 同步刷盘(SYNC_FLUSH)：每条都落盘,性能损失 30%
- 同步双写(SYNC_MASTER)：主从同步成功才 ack,损失再 30%
- 异步刷盘 + 异步复制:性能高,极端宕机丢 1-2 秒数据

折中:订单类用同步刷盘 + 异步复制(可接受机房故障丢秒级)
资金类用同步刷盘 + 同步双写(零丢失)
```

**消费端不丢**:
```
关键:业务处理成功后再 ack
- 错误:收到消息立即 ack,然后处理 → 处理失败消息丢
- 正确:处理成功后再 ack → 失败的消息会重投

重投 + 幂等 = 不丢不重
```

#### 2. 服务治理(主战场)

**幂等的三种实现**:

| 方案 | 适用 | 性能 |
| --- | --- | --- |
| **业务 ID UNIQUE** | 有自然 ID | 高(直接用) |
| **message_id 去重表** | 无业务 ID | 中(查表) |
| **Redis SETNX** | 不持久化 | 高(60s TTL) |

**Go 消费幂等代码**:
```go
func consume(msg *Message) error {
    // 1. Redis 快速去重
    if !redis.SetNX("idem:msg:"+msg.ID, 1, 60*time.Second) {
        return nil  // 已处理过,直接 ack
    }
    
    // 2. DB UNIQUE 兜底
    if err := db.Exec("INSERT IGNORE INTO consume_log (msg_id) VALUES (?)", msg.ID); err != nil {
        return err
    }
    
    // 3. 业务处理(自身也要幂等)
    return processOrder(msg)
}
```

#### 3. 缓存与 DB 优化

- **去重表分库分表**:按 `msg_id % 32` 分库,避免单表爆炸
- **TTL 清理**:去重表 30 天后归档,Redis 60 秒 TTL
- **批量消费**:Kafka 单次拉 100 条,提高吞吐

#### 4. 异步消息(主战场)

**保序的三种粒度**:

| 粒度 | 实现 | 代价 |
| --- | --- | --- |
| **全局有序** | 单分区(单消费者)| 牺牲并发 |
| **分区有序** | 同 key 同分区 | 99% 场景够用 |
| **业务有序** | 应用层重排 | 复杂度高 |

**RocketMQ 分区有序**:
```go
// 同 order_id 必到同一队列
producer.SendOrderly(msg, func(mqs []*MessageQueue, msg *Message, arg interface{}) *MessageQueue {
    orderID := arg.(int64)
    return mqs[orderID % len(mqs)]
}, orderID)
```

**消费乱序的常见错因**:
- 多线程消费:同分区内多线程并发 → 乱序
- 解决:分区内单线程消费(MessageListenerOrderly)

**死信队列(DLQ)**:
- RocketMQ:消费失败 16 次 → 进 DLQ(`%DLQ%consumer_group`)
- 监控 DLQ 消息数,> 0 → P1 告警
- 人工补偿:DLQ 消息重新投递 / 落库 / 业务侧补偿

#### 5. 限流熔断降级

- **生产端限流**:超过 50w TPS → 拒绝业务请求,避免 Broker 打挂
- **消费端限流**:消费者反压(backpressure),消费慢 → 拉取慢
- **Broker 熔断**:磁盘 90% → 拒绝写入(防爆盘)

#### 6. 容灾恢复

| 故障 | 应对 |
| --- | --- |
| Broker 主挂 | 从切主(同步双写不丢)/ 异步复制丢秒级数据 |
| 消费者全挂 | 消息堆积 Broker 等消费者恢复(72 小时保留) |
| 消息堆积 100w+ | 临时扩消费者 / 跳过非关键消息 / 批量处理 |
| 整集群挂 | 跨机房灾备 / 业务降级(本地消息表兜底) |

**消息堆积处理**:
```
1. 评估:堆积量 / 消费速度 → 预估清理时间
2. 应对:
   - 堆积 < 10w:正常消费,无需干预
   - 堆积 10-100w:扩消费者(scale up)
   - 堆积 > 100w:临时建新 topic,跳过堆积消息
3. 根因:
   - 消费速度变慢?(查 GC / 慢 SQL / 第三方接口)
   - 生产速度突增?(查上游业务)
```

#### 7. 监控告警(主战场)

```
关键指标:
- 生产 TPS / 消费 TPS / 积压数
- 消费延迟(end_to_end)
- 重试次数分布
- DLQ 消息数(目标 = 0)
- Broker 磁盘水位(< 80%)

告警阈值:
- 积压 > 10w → P2
- 积压 > 100w → P0
- 消费延迟 > 30s → P1
- DLQ > 100 → P1
- 磁盘 > 85% → P1
```

#### 8. 压测与容量评估

```
日 10 亿消息 = 1.16w QPS 平均
峰值 × 50 = 50w QPS
RocketMQ 单 Broker 10w TPS
集群 5 主 5 从 = 50w QPS
单 topic 32 分区 = 320w QPS 容量(留余量)
存储:1B 消息 × 1KB × 7 天 = 7TB,单 Broker 1.5TB
```

#### 9. 真实优化经验

**踩坑 1:消费者先 ack 后处理,处理失败消息丢失**
- 现象:消费者收到消息立即 ack,然后业务异常 → 消息丢
- 优化:业务成功后再 ack(默认就是)
- 收益:消息不丢,失败重投

**踩坑 2:幂等用 message_id,但生产端重发用了新 message_id**
- 现象:同业务两次发,消费两次,两次都成功
- 优化:幂等用业务 ID(order_id)而不是 message_id
- 收益:跨重发也幂等

**踩坑 3:同 order_id 散到不同分区**
- 现象:订单状态机乱序(WAIT_PAY → PAID → CANCEL,但 CANCEL 先到)
- 优化:同 order_id 用 Hash 路由到固定分区
- 收益:状态机推进有序

**踩坑 4:DLQ 没监控,业务静默丢失**
- 现象:消费 16 次失败进 DLQ,但没人看 → 业务静默丢
- 优化:DLQ 消息数 > 0 → P1 告警 + 人工 SOP
- 收益:DLQ 100% 处理

**踩坑 5:消息堆积导致内存爆**
- 现象:消费者拉 1000 条进内存处理,内存 OOM
- 优化:批量减小到 100 条 + backpressure
- 收益:内存稳定

**踩坑 6:压测时同步刷盘性能差**
- 现象:压测 50w TPS 同步刷盘只能撑 5w
- 优化:订单类业务改异步刷盘(可接受秒级丢失)
- 收益:TPS 10× 提升

### 量化数据卡

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 峰值 TPS | 50 万 | 抖音订单 |
| 单 Broker TPS | 10 万 | RocketMQ 上限 |
| 单 topic 分区数 | 32 | 320w 容量余量 |
| 消息保留期 | 7 天 | 默认 |
| DLQ 重试次数 | 16 次 | RocketMQ 默认 |
| 同步刷盘性能损失 | 30% | 对比异步 |
| 同步双写性能损失 | 30% | 对比异步复制 |

### 易错点

- ❌ 先 ack 后处理 → 消息丢失
- ❌ 幂等用 message_id → 业务重发不幂等
- ❌ 同 key 散分区 → 乱序
- ❌ 多线程同分区消费 → 乱序
- ❌ DLQ 不监控 → 业务静默丢失
- ❌ 异步刷盘用于资金类 → 极端宕机丢数据

### 追问预案

1. **怎么保证 100% 不丢?** 同步刷盘 + 同步双写 + 业务幂等 + DLQ 监控,但性能损失 50%+
2. **顺序消费性能差怎么办?** 业务能容忍则不强求(99% 场景),关键场景用业务 ID 局部有序
3. **消息堆积 1 亿怎么清?** 临时建新 topic + 老 topic 并行消费 + 老消息 24h 后归档
4. **Kafka vs RocketMQ 选?** 大数据 / 高吞吐用 Kafka;事务 / 顺序 / 延迟消息用 RocketMQ
5. **消费幂等性能差怎么办?** Redis 一级缓存(60s)+ DB UNIQUE 兜底,99% 场景 Redis 命中
6. **集群升级会丢消息吗?** 不会,Broker 优雅下线(等消费完成 + 暂停接收)
7. **怎么测试 MQ 容灾?** Chaos:杀 Broker / 断网 / 磁盘满,看消息丢失情况
8. **延迟消息怎么实现?** RocketMQ 内置(18 个等级)/ Kafka 自建延迟队列(时间轮)

### 面试回答版

> MQ 三大问题的本质是"消息在不同环节都可能出问题",必须**每个环节单独防御**——生产、Broker、消费三段都要扛,不能合并。
>
> **不丢**靠三段确认:生产端同步发送 + ack + 重试 3 次 + 本地消息表兜底;Broker 同步刷盘(订单类)或同步双写(资金类);消费端**业务处理成功后再 ack**,先 ack 后处理是最常见的丢消息原因。性能取舍上,订单选同步刷盘 + 异步复制(损失 30%),资金必须同步双写(损失 60%)。
>
> **不重**的关键是**幂等用业务 ID 不用 message_id**——生产 ack 超时重发会产生新 message_id,但业务上是同一笔,用 message_id 会重复执行。Redis SETNX 60s 一级 + DB UNIQUE 兜底,99% Redis 命中。
>
> **保序**靠"同业务 key 同分区"——RocketMQ 用 MessageQueueSelector、Kafka 用 key,同 order_id 路由到固定分区,分区内必须**单线程消费**(MessageListenerOrderly),多线程同分区会乱序。订单状态机乱序就是 P0,CANCEL 先到 PAID 后到业务彻底崩。
>
> **DLQ 必须监控**——消费失败 16 次进 DLQ,默认不再消费,**没监控就是静默丢失**。生产真实事故 1 万条订单进 DLQ 一周后才发现,全部要人工补单。DLQ > 0 必须 P1 告警 + 人工 SOP。
>
> 堆积分级应对:< 10w 正常消费,10-100w 扩消费者(分区数是上限),> 100w 建新 topic 跳过堆积。根因排查:消费慢(GC / 慢 SQL / 三方) vs 生产突增。

### 一句话核心

> **三段 ack 不丢(消费必须业务成功后 ack)+ 业务 ID 幂等不重(不用 msg_id)+ 同 key 同分区 + 单线程消费保序 + DLQ 监控防静默丢 + 同步刷盘资金双写**

### 背诵版(更精简)

> MQ 三大问题:**不丢**(生产 ack + Broker 同步刷盘 + 消费成功才 ack)+ **不重**(业务 ID UNIQUE,Redis SETNX 60s + DB 兜底)+ **保序**(同业务 key 同分区 + 单线程消费)。生产踩坑:先 ack 后处理丢消息、幂等用 message_id 不防业务重发、DLQ 不监控静默丢失、堆积 1 亿要建新 topic 跳过。容量:50w TPS = 5 主 Broker + 32 分区,资金用同步双写,订单用异步复制。

## Q9 服务超时重试怎么避免雪崩

### 场景设定

> 抖音电商系统,30+ 微服务,调用链 5-10 跳。某依赖服务(库存服务)突发慢请求(P99 从 50ms 涨到 5s),上游订单服务的线程池被打满,继续上游(网关)线程池被打满,**整个集群雪崩**。要求:**单点慢调用不能击穿整个集群**。

### 一句话本质

**超时设置(防止永久等待)+ 重试限流(防止重试风暴)+ 熔断器(快速失败)+ 资源隔离(线程池/信号量)+ 降级返回(优雅退化)**,核心是"快速失败 + 局部隔离 + 整体兜底"。

### 面试答题节奏(故事版)

#### 1. 场景具体化

抖音电商 30+ 微服务,调用链 5-10 跳。**真实雪崩事故**:库存服务 P99 从 50ms 涨到 5s(下游 DB 慢查询),订单服务调用库存的线程池被打满,订单 P99 也涨到 5s,网关线程池打满,**整个集群在 3 分钟内雪崩**。要解决的核心问题:**单点慢调用不能击穿整个集群**。

#### 2. 雪崩的传染链——为什么单点会击穿全局

```
库存慢 (50ms → 5s)
  → 订单调用库存的线程被占满(原本 50 线程,5s 一次,只能扛 10 QPS)
  → 订单服务整体响应变慢(其他业务也卡)
  → 网关调用订单的线程被占满
  → 网关无法响应任何请求
  → 全站不可用
```

本质问题:**资源没有隔离 + 没有快速失败**——慢请求占着线程不放,新请求进不来。

#### 3. 超时设置——必须递减,这是底线

最容易踩的坑:**外层超时 < 内层超时**。

```
❌ 错误:网关 1s,订单 3s,库存 5s
   → 网关 1s 后 timeout,但订单还在等库存,占着线程
   → 内层白干活,外层早返回

✓ 正确:网关 3s → 订单 2s → 库存 1s → DB 500ms
   → 内层时间用完,外层还有余量发降级响应
   → 资源不被无效占用
```

**口诀**:外层超时 > 内层超时总和 + 网络开销。

#### 4. 重试——必带"三件套",否则就是雪崩加速器

| 维度 | 设置 | 不做的后果 |
| --- | --- | --- |
| 重试次数 | **1-3 次** | 5+ 次重试 = 流量翻倍,雪崩 |
| 重试间隔 | **指数退避 + jitter** | 同时重试 = 同步打 DB |
| 重试条件 | **超时 / 5xx,4xx 不重试** | 4xx 重试 = 业务错误加重 |
| 重试上限 | **全局限流** | 单机限流不够,跨实例累加雪崩 |

```go
func callWithRetry(ctx context.Context) error {
    backoff := []time.Duration{100*time.Millisecond, 200*time.Millisecond, 400*time.Millisecond}
    for i := 0; i < 3; i++ {
        err := call(ctx)
        if err == nil { return nil }
        if !isRetryable(err) { return err }  // 4xx 不重试
        jitter := time.Duration(rand.Int63n(int64(backoff[i] / 2)))
        time.Sleep(backoff[i] + jitter)  // 关键:加 jitter
    }
    return errMaxRetry
}
```

**重试 + 幂等是孪生**——只重试不幂等 = 数据错乱。前面 Q2 / Q3 的 request_id / trade_no 兼顾了这一点。

#### 5. 熔断器——快速失败的核心

熔断三态:
```
CLOSED(正常)→ 错误率 > 50% → OPEN(熔断,直接失败)
                ↓
              30s 后
                ↓
          HALF_OPEN(试探)→ 成功 → CLOSED
                          → 失败 → OPEN
```

**关键配置**:
- 最小请求数 5(防偶尔抖动就熔断)
- 错误率阈值 50%
- 时间窗 30s
- 半开试探请求数 3

**熔断和限流的区别**:
- 限流:**主动**防过载(QPS 上限),保护自己
- 熔断:**被动**防级联(下游错误率高),保护上游不被拖垮

#### 6. 资源隔离——线程池 / 信号量

```
订单服务 50 个线程
├── 库存调用线程池(20 线程)→ 库存挂了只影响这 20
├── 用户调用线程池(10 线程)→ 用户挂了只影响这 10
├── 商品调用线程池(15 线程)
└── 主线程池(5 线程)→ 业务逻辑
```

**Go 用 semaphore(信号量,轻量)**:
```go
inventorySem := make(chan struct{}, 20)  // 最多 20 并发

select {
case inventorySem <- struct{}{}:
    defer func() { <-inventorySem }()
    return callInventory()
default:
    return fallbackInventory()  // 立即降级,不等
}
```

**为什么 Go 用信号量不用线程池**:goroutine 天生轻量,不需要预分配线程,信号量限制并发数即可。

#### 7. 降级——必须返回业务有效的值

**最坑的事故**:降级返回 nil,下游空指针,链路全挂——这种"降级"反而加速雪崩。

| 场景 | 降级返回 |
| --- | --- |
| 库存服务挂 | 返回"库存紧张",**允许下单**,后台补对账 |
| 用户服务挂 | token 内嵌信息,**跳过用户服务** |
| 推荐服务挂 | 返回**热销榜单**(本地缓存,提前准备好) |
| 物流查询挂 | 显示"**预计 3-5 天**"占位 |

降级数据**必须提前准备**——本地缓存 + 静态化 + 默认值,不能临时算。

#### 8. 监控 + 雪崩 SOP

```
关键指标:
- 调用链 P99(每跳)→ > 1s P2
- 错误率 → > 1% P1
- 重试率 → > 5% P1(上游有问题)
- 线程池占用率 → > 80% P0(雪崩前兆)
- 熔断开启次数 → > 0 P1

雪崩应急 SOP:
1. 发现:QPS 突降 + 错误率突增
2. 立即熔断:Sentinel 全局开关 → 拒绝慢服务调用
3. 降级返回:静态数据 / 缓存 / 默认值
4. 排查根因:看慢服务 trace(Jaeger / SkyWalking)
5. 扩容:慢服务横向扩容
6. 灰度恢复:10% → 50% → 100%
```

**Trace 错误请求 100% 采样**,正常 1%——故障必须可追溯,千万别采样率太低。

### 九维度深度展开(追问储备)

#### 1. 分布式一致性

- 雪崩与一致性无关,但**重试可能导致数据重复**(配合幂等)

#### 2. 服务治理(主战场)

```
若调用链 5 跳,每跳 100ms,总延迟 500ms
线程池估算:QPS × 延迟 = 1w × 0.5s = 5000 线程并发
实际线程池:留 20% 余量 → 6000 线程
```

#### 9. 真实优化经验

**踩坑 1:超时设置反了(外短内长)**
- 现象:网关 1s,订单 3s → 网关 timeout 时订单还在等
- 优化:超时递减(网关 3s → 订单 2s → 库存 1s)
- 收益:无效计算从 50% 降到 5%

**踩坑 2:重试无限制导致重试风暴**
- 现象:依赖挂了,所有调用都重试 5 次,流量 6×,雪崩
- 优化:重试限流(单服务全局 1w QPS 上限)+ 指数退避 + jitter
- 收益:重试流量稳定

**踩坑 3:线程池没隔离,一个慢服务打挂订单**
- 现象:库存慢 → 订单线程池占满 → 其他业务也挂
- 优化:每依赖独立线程池
- 收益:库存挂只影响下单,其他业务正常

**踩坑 4:熔断阈值太敏感**
- 现象:偶尔抖动就熔断,业务频繁报错
- 优化:最小请求数(> 5 次)+ 错误率 50% + 时间窗 30s
- 收益:抖动不熔断,真故障熔断

**踩坑 5:降级返回 nil 导致下游 NPE**
- 现象:依赖挂了返回 nil,下游空指针
- 优化:降级返回**业务有效的兜底值**(空数组、默认对象)
- 收益:降级链路完整

**踩坑 6:Trace 采样率 1%,关键问题看不到**
- 现象:错误请求采样率 1%,大部分错误 trace 没记录
- 优化:错误请求 100% 采样,正常 1%
- 收益:故障可追溯

### 量化数据卡

| 指标 | 数字 | 说明 |
| --- | --- | --- |
| 调用链超时递减 | 外 > 内总和 | 必须 |
| 重试次数 | 1-3 次 | 防风暴 |
| 重试退避 | 指数 + jitter | 防同步重试 |
| 熔断错误率阈值 | 50% | 默认 |
| 熔断时间窗 | 30s | 默认 |
| 线程池每依赖 | 20-50 | 隔离 |
| Trace 错误采样 | 100% | 故障可查 |

### 易错点

- ❌ 超时外短内长 → 内层做无效功
- ❌ 重试无限制 → 重试风暴
- ❌ 4xx 也重试 → 浪费 + 加重业务
- ❌ 不做线程池隔离 → 一服务挂全服务挂
- ❌ 熔断阈值太敏感 → 抖动就熔断
- ❌ 降级返回 nil → 下游 NPE
- ❌ Trace 采样率太低 → 故障看不到

### 追问预案

1. **超时多少合适?** 外层 3-5s,内层递减,DB 500ms-1s
2. **重试一定要做吗?** 关键调用必做(超时 / 5xx),非关键可不做
3. **熔断和限流的区别?** 限流防过载(主动),熔断防级联(被动)
4. **Hystrix 和 Sentinel 怎么选?** Java 生态用 Sentinel(国内),Hystrix 已停止维护
5. **怎么测试雪崩?** Chaos:注入慢请求 / 错误 / 资源耗尽,看是否扩散
6. **服务网格(Istio)能解决吗?** 能,但学习曲线陡 + 性能损失,中小团队不必上
7. **降级数据怎么准备?** 大盘静态数据 + 用户偏好缓存 + 默认推荐位
8. **多机房调用超时怎么算?** 跨机房 RTT 5-30ms,单机房 < 5ms,超时设置含 RTT

### 面试回答版

> 防雪崩的本质是**"快速失败 + 资源隔离"**——单点慢调用不能击穿整个集群。核心是五件套:超时 / 重试 / 熔断 / 隔离 / 降级,五件缺一不可。
>
> **超时必须递减**——外层超时 > 内层超时总和 + 网络开销,网关 3s → 订单 2s → 库存 1s → DB 500ms。最坑的反模式是外短内长,网关 timeout 时内层还在等,资源被无效占用。
>
> **重试带"三件套"**:1-3 次 / 指数退避 + jitter / 4xx 不重试。jitter 关键,没有 jitter 所有实例同时重试 = 同步打 DB 二次雪崩。重试必须和幂等配套(Q2 的 request_id / Q3 的 trade_no),只重试不幂等是数据灾难。
>
> **熔断器**做被动级联保护,和限流(主动过载保护)互补。配置最小请求数 5 + 错误率 50% + 时间窗 30s,防止偶尔抖动就熔断,真故障 30s 内快速熔断。30s 后半开试探,渐进恢复。
>
> **资源隔离**每依赖独立线程池(Java)或信号量(Go),库存挂了只影响调库存的 20 并发,其他业务不受影响。Go 用 channel 做信号量最自然,goroutine 本身轻量不需要预分配。
>
> **降级必须返回业务有效值**——返 nil 是反模式,下游 NPE 加速雪崩。库存挂返"库存紧张允许下单",推荐挂返热销榜单(本地缓存提前准备),物流挂返"3-5 天"占位。
>
> 监控核心:**线程池占用率 > 80% 就是雪崩前兆**,必须 P0。Trace 错误请求 100% 采样,故障可追溯。SOP:发现 → 熔断 → 降级 → 排查 → 扩容 → 灰度恢复。

### 一句话核心

> **超时递减 + 重试三件套(次数 / jitter / 4xx 不重试)+ 熔断器(50% / 30s)+ 信号量隔离 + 降级返业务有效值(非 nil)+ 线程池满 P0**

### 背诵版(更精简)

> 防雪崩五件套:**超时递减**(外 > 内总和)+ **重试限流**(1-3 次,指数退避 + jitter,4xx 不重试)+ **熔断器**(50% 错误率 + 30s 时间窗)+ **资源隔离**(每依赖独立线程池/信号量)+ **降级兜底**(返回有效数据,不返 nil)。生产踩坑:超时反了内层白做、重试无限制风暴、线程池不隔离一挂全挂、熔断太敏感抖动就断、Trace 错误采样率太低查不到故障。SOP:发现 → 熔断 → 降级 → 排查 → 扩容 → 灰度恢复。

## Q10 系统 QPS 从 1k 提到 10k 做了什么

### 场景设定

> 我负责的电商订单服务,初期 QPS 1k,P99 200ms,DB 单库,Redis 单实例。业务增长 10× 到 QPS 10k,要求 **P99 < 100ms,可用性 > 99.95%,成本控制在 2× 以内**。讲清楚:**做了哪几件事 / 每件事的收益 / 踩了哪些坑**。

### 一句话本质

**先压测找瓶颈 → 缓存先上 → DB 读写分离 + 索引 → 异步化解耦 → 水平扩展应用 → 全链路监控**,核心是"用 80% 精力解决 20% 瓶颈,不要全栈重构"。

### 面试答题节奏(故事版)

#### 1. 场景具体化

我负责的电商订单服务,初期 QPS 1k,P99 200ms,DB 单库,Redis 单实例。业务半年增长 10×,要 **QPS 10k,P99 < 100ms,可用性 > 99.95%,成本控制 2× 以内**。这种"5 倍 QPS / 5 倍延迟收紧 / 1 倍成本"的题目,**最容易踩的坑是上来就全栈重构**——我吃过这亏,讲讲我怎么爬出来的。

#### 2. 第一次的错误——上来就拆微服务

刚拿到这个任务时,我直接把单体拆成 8 个微服务 + 引入 K8s + 上 Service Mesh,**搞了 3 个月**,QPS 还是 2k 多,P99 反而涨到 500ms(网络多跳)。

**复盘**:80% 的性能问题是 **DB 慢查询**,索引一加 5× 提升,我却去搞架构升级。

**真正的方法论**:**先压测找瓶颈,再决定改什么**。

#### 3. 正确的优化时序——按瓶颈推进

| 阶段 | 主要瓶颈 | 优化动作 | 收益 |
| --- | --- | --- | --- |
| **1k → 3k** | DB 慢查询 | 慢 SQL + EXPLAIN 加索引 | 5× DB QPS |
| **3k → 5k** | DB 读压力 | Redis 缓存(Cache-Aside)| 10× 读性能 |
| **5k → 7k** | DB 写压力 | 读写分离(1 主 N 从)| 3× 读吞吐 |
| **7k → 10k** | 同步链路长 | MQ 异步化非关键路径 | 同步延迟 10× |
| **10k 平稳** | 应用单点 | 水平扩展 + LB | 容量弹性 |

**核心原则**:**每一步压测验证,不达标不进入下一步**。

#### 4. 慢 SQL——最高 ROI 的优化

```sql
-- 优化前(全表扫,1.5s)
SELECT * FROM orders WHERE user_id = ? AND created_at > '2026-01-01';

-- 优化:加联合索引
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at);

-- 优化后:覆盖索引,5ms
-- EXPLAIN: type=range, key=idx_user_created, rows=100
```

只加了 5 个核心索引,DB QPS 上限从 5000 提到 25000,**单次改动收益 5×**,改动量极小。

#### 5. Redis 缓存——10× 读性能的关键

多级缓存把 1 万读 QPS 摊到不同层:
```
L1 本地 Caffeine(1s TTL)→ 30% 流量(3k QPS,内存命中,P99 < 1ms)
L2 Redis(5 分钟 TTL)    → 69% 流量(6.9k QPS,P99 < 5ms)
L3 DB                    → 1% 流量(100 QPS,健康水位)
```

**DB QPS 从 1w 降到 100**。一致性靠 Cache-Aside(写时先 DB 后删缓存)+ binlog 异步刷,主从延迟用延迟双删。

#### 6. 读写分离——读你刚写的坑

引入 1 主 3 从后,读 QPS 平摊,但踩过经典坑:**用户下单完跳转订单详情,从库延迟 1s,显示"订单不存在"**,直接投诉。

解决方案:**"read your write"——用户读自己刚写的数据走主库**。
```go
// 路由规则:5 分钟内的用户写操作 → 后续读走主库
if userJustWroteWithin(5 * time.Minute) {
    return db.Master()
}
return db.RandomSlave()
```

实现:Redis 记录用户最近写时间戳 5 分钟,读时判断。

#### 7. MQ 异步化——同步延迟 10× 优化

```
原:下单 → DB 落 + 扣库存 + 发短信 + 加积分 + 推送 = 同步 500ms
改:下单 → DB 落 + 扣库存 = 同步 50ms
       → MQ "order_created" → 短信 / 积分 / 推送 = 异步
```

**用户感知延迟从 500ms 降到 50ms**,而且下游服务可独立扩缩容、单服务挂不影响主流程。

**界定哪些能异步**:
- 必须同步:扣库存、扣余额(强一致)
- 可异步:短信、积分、推送、统计(最终一致就行)
- 半异步:履约通知(用户能等 1-2 秒)

#### 8. 水平扩应用——别忘了缩连接池

应用从 5 个实例扩到 50 个时踩过坑:每个实例 50 个 DB 连接,**总连接 2500 远超 MySQL 上限 500**,直接打挂。

公式:
```
DB 连接池 = 应用实例 × 单实例并发 × 1.2(余量)
50 实例 × 8 连接 × 1.2 ≈ 480 < 500 上限
```

或者引入 **ProxySQL 复用连接**,应用看到几千连接,后端实际几百。

#### 9. 监控演进——故障定位 5× 快

```
阶段 1(1k):  基础监控(CPU / 内存 / QPS)    Prometheus + Grafana
阶段 2(3k):  APM 全链路追踪                  Jaeger / SkyWalking
阶段 3(5k):  业务监控(订单 / 漏斗 / 成功率) 自建大盘
阶段 4(10k): SLO 体系(错误预算燃尽率)      多维大盘 + 告警分级
```

**告警必须分级 + 收敛**——踩过坑,1 天 200 条告警 SRE 麻木。分级 P0/P1/P2 + 同 root cause 合并,告警有效率从 10% 提到 80%。

#### 10. 关键反思——10× 不是终点

QPS 10k 时已经能看到下一个瓶颈:
- 单库 DB 写 5000 TPS 上限,需要 **分库分表**(详见 Q6)
- 单机房风险,需要 **多机房灾备**
- 静态资源占带宽,需要 **CDN 静态化**

每个阶段的方案有效边界要清楚,**1k → 10k 的方案撑不到 100k**——分库分表是下一阶段必修课。

- 现象:告警风暴,1 天 200 条,SRE 麻木
- 优化:分级告警(P0/P1/P2)+ 告警收敛(同 root cause 合并)+ 告警值班
- 收益:告警有效率从 10% 提到 80%

### 量化数据卡

| 阶段 | QPS | P99 | 关键动作 | 收益 |
| --- | --- | --- | --- | --- |
| 起点 | 1k | 200ms | - | - |
| 索引优化 | 3k | 100ms | 加 5 个索引 | DB 5× |
| 引入 Redis | 5k | 80ms | Cache-Aside | 读 10× |
| 读写分离 | 7k | 60ms | 1 主 3 从 | 读吞吐 3× |
| 异步化 | 10k | 50ms | MQ 削峰 | 同步 10× |
| 监控完善 | - | - | APM + SLO | 故障定位 5× 快 |

### 易错点

- ❌ 不压测就重构(全栈)→ 80% 是 DB 问题
- ❌ 引入缓存不考虑一致性 → 数据脏
- ❌ 读写分离不处理"读自己写"→ 用户感知断层
- ❌ 水平扩应用不缩连接池 → DB 连接爆
- ❌ 不监控大 key → 阻塞拖慢全集群
- ❌ 压测配置 ≠ 生产 → 假绿
- ❌ 告警不分级 → 风暴 + 麻木

### 追问预案

1. **为什么先优化 DB 不是先拆服务?** DB 是 80% 瓶颈,索引和缓存性价比最高,拆服务是组织 / 复杂度问题
2. **怎么找到瓶颈?** 压测 + APM + 慢 SQL 日志 + Top N 接口耗时
3. **缓存预热怎么做?** 启动时拉 Top 1w 热 key + 灰度发布期间逐步切流
4. **数据库连接池怎么调优?** 公式:连接数 = 应用实例 × 单实例并发 × 1.2(余量)
5. **怎么平滑切换读写分离?** 灰度路由 → 部分读切从库 → 监控延迟 → 全量切
6. **下一步 10k → 100k 怎么做?** 分库分表 + 多机房 + CDN 静态化(详见 Q6)
7. **优化期间业务持续增长怎么办?** 先扩容(临时方案)+ 限流降级(保命)+ 优化(根因)
8. **优化收益怎么向 PM / 老板讲?** 用户感知延迟 / 成本节省 / 容量预留(都是钱)

### 面试回答版

> QPS 1k → 10k 的本质不是"扩容多少倍",而是**"按瓶颈推进"的方法论**——80% 的性能问题集中在 DB,先压测找瓶颈再决定改什么,**不要全栈重构**。我自己吃过这亏,刚拿到任务时直接拆 8 个微服务 + K8s + Service Mesh,3 个月 P99 反而涨到 500ms,后来发现 80% 是 DB 慢查询,索引一加 5× 提升。
>
> 正确的优化时序按瓶颈走:
> - **1k → 3k**:慢 SQL 加索引(5 个核心索引,DB 5×)
> - **3k → 5k**:Redis 多级缓存(本地 30% / Redis 69% / DB 1%,读 10×)
> - **5k → 7k**:读写分离 1 主 3 从(读吞吐 3×)
> - **7k → 10k**:MQ 异步化非关键路径(短信 / 积分 / 推送),同步延迟 10×
>
> 每一步必须**压测验证后再进入下一步**,不达标先复盘。
>
> 几个生产踩过的坑:**读写分离的"read your write"**——用户下单完跳详情页,从库延迟 1s 显示"订单不存在",必须 5 分钟内读自己的写操作走主库;**水平扩应用 DB 连接打满**——50 实例 × 50 连接超 MySQL 500 上限,必须缩连接池或上 ProxySQL;**Redis 大 key 阻塞**——某用户购物车 hash 5000 项 GET 50ms,必须拆 + 监控 key 大小。
>
> 监控演进同样按阶段走:基础(CPU / QPS)→ APM(全链路 trace)→ 业务监控(订单漏斗)→ SLO 体系(错误预算)。告警必须分级 P0/P1/P2 + 同 root cause 收敛,踩过 1 天 200 条 SRE 麻木的坑,分级后有效率从 10% 提到 80%。
>
> 10k 不是终点——单库写 5000 TPS 是 InnoDB 上限,下一步 100k 必须 **分库分表 + 多机房 + CDN**(详见 Q6)。

### 一句话核心

> **先压测后改(80% DB)+ 五步走(索引→缓存→读写分离→MQ 异步→水平扩)+ 读自己写走主库 + 缩连接池防 DB 爆 + 告警分级收敛 + 10k 不是终点(下一步分库分表)**

### 背诵版(更精简)

> QPS 1k → 10k 5 步走:**慢 SQL 索引**(DB 5×)→ **Redis 缓存**(读 10×)→ **读写分离**(读吞吐 3×)→ **MQ 异步化**(同步延迟 10×)→ **应用水平扩展**。监控演进:基础 → APM → 业务 → SLO。生产踩坑:全栈重构是误区(80% 是 DB)、缓存不一致用 binlog 兜底、读自己写要走主库、水平扩应用记得缩连接池、Redis 大 key 必拆、压测配置必须 = 生产、告警必须分级。下一步 10k → 100k:分库分表 + 多机房 + CDN。

## 文末总结

### 实战题答题套路(资深视角)

每道实战题答题时按以下框架推进,**不要只讲概念**:

```
1. 场景具体化(30 秒)
   - 业务规模(QPS / 数据量 / 用户数)
   - 痛点(超卖 / 慢 / 雪崩)
   - SLA 要求(P99 / 可用性 / 一致性等级)

2. 一句话本质(30 秒)
   - 用关键词浓缩方案("Lua 原子扣减 + MQ 异步落库 + 对账兜底")
   - 暴露设计哲学("不让 DB 扛压、不让单 key 扛压、不相信任何单点")

3. 主战场展开(3 分钟)
   - 选 2-3 个最关键维度展开
   - 给具体技术方案 + 量化数据 + 代码片段
   - 体现"为什么这样做"

4. 次战场带过(1 分钟)
   - 监控 / 容灾 / 压测 / 限流速带
   - 体现"全链路视角"

5. 真实踩坑(1 分钟,资深加分)
   - 讲 2-3 个具体坑 + 现象 + 排查 + 优化 + 收益量化
   - 体现"经历过故障 + 反思能力"

6. 追问准备
   - 准备 5-8 个追问预案
   - 不会的问题坦白说"没踩过这个坑,但我会这样思考"
```

### 资深 vs 初级的核心差异

| 维度 | 初级 | 资深 |
| --- | --- | --- |
| **概念** | 知道是什么 | 知道**为什么这样设计** |
| **方案** | 给一个方案 | 给方案 + 取舍 + 替代 |
| **数据** | 模糊"性能挺好" | 量化"P99 50ms,QPS 10w" |
| **故障** | 没踩过 | 讲过具体故障 + 反思 |
| **演进** | 一次性方案 | 分阶段(1k → 10k → 100k)|
| **边界** | 不讲限制 | 主动讲"什么时候不行" |
| **监控** | 想起来才说 | 主动讲监控 + 告警阈值 |
