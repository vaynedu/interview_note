## A. Channel 使用场景十讲(1~10)

> **核心认知**:**channel 不只是同步工具,它更像 goroutine 之间的通信线路**——比起 Mutex 保护共享内存,channel 通过"传消息"组织协作。Rob Pike 的原话:
>
> > "Don't communicate by sharing memory; share memory by communicating."
>
> 下面 10 类用法,**几乎覆盖了 Go 生产代码里 95% 的 channel 用途**。面试被问"channel 都用在哪儿"时,按这 10 类讲,远比一句"做同步"有说服力。

---

### 1. 传数据(Data Pipe)

**场景**:生产者把数据丢给消费者,典型如日志收集、事件上报。

```go
events := make(chan Event, 1024)

// 生产者(可能多个)
go func() {
    for e := range source {
        events <- e
    }
}()

// 消费者(可能多个)
for e := range events {
    handle(e)
}
```

**要点**:
- buffered channel 起**削峰**作用——生产突刺被 buffer 吸收
- buffer 大小要算:`buffer ≈ 峰值 QPS × 消费延迟`,过大占内存,过小退化成同步
- 关闭由**唯一 sender** 负责,多 sender 用 [sync.Once](../01-go-language/02-concurrency/channel.md#33-成功为止执行一次retryonce)

**易错**:把 channel 当无限队列用,buffer 设几万——满了照样阻塞,该上 MQ 就上 MQ。

---

### 2. 派任务(Task Dispatch)

**场景**:把任务分给一组 worker,实现并行处理。

```go
tasks := make(chan Task)
var wg sync.WaitGroup
for i := 0; i < runtime.NumCPU(); i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for t := range tasks {
            t.Run()
        }
    }()
}

for _, t := range allTasks {
    tasks <- t
}
close(tasks) // worker 收到 channel 关闭,range 自动退出
wg.Wait()
```

**要点**:
- N 个 worker 共享一个任务 channel,Go runtime **公平派发**
- 关 channel = "任务派发完了" 的广播信号——所有 worker 同时收到
- 完整封装见 [worker pool](../20-coding-problems/02-worker-pool.md)

**易错**:在 worker 里再开 goroutine 没有 wg.Add,主线程提前退出。

---

### 3. 收结果(Result Collection / Fan-In)

**场景**:N 个并发任务的结果汇总到一个 channel(fan-in)。

```go
results := make(chan Result, len(urls))
var wg sync.WaitGroup
for _, u := range urls {
    wg.Add(1)
    go func(u string) {
        defer wg.Done()
        results <- fetch(u)
    }(u)
}
go func() { wg.Wait(); close(results) }() // 全完了才关,避免提前关导致 send panic

for r := range results {
    aggregate(r)
}
```

**要点**:
- **`go func() { wg.Wait(); close(results) }()`** 是固定写法——主线程在 range 期间不能去 Wait(否则 results 没人收会卡住生产者)
- results 是 **buffered**(`len(urls)`),保证所有 worker 写完就退出,不被消费者拖慢
- 失败用 Result.Err 字段表达,**不要单独 errCh**(同步两个 channel 复杂度爆炸)

**易错**:`close(results)` 放在主 goroutine `wg.Wait()` 之前——还没人收就关,producer panic。

---

### 4. 做限流(Semaphore / 令牌桶)

**场景**:限制同时执行的并发数。

```go
sem := make(chan struct{}, 10) // 最多 10 并发

for _, t := range tasks {
    sem <- struct{}{} // 满了阻塞
    go func(t Task) {
        defer func() { <-sem }()
        t.Run()
    }(t)
}
```

**要点**:
- buffered channel **天然就是计数信号量**——容量 = 并发上限
- `struct{}{}` 零内存,纯做"占位"
- 取消用 `select { case sem <- struct{}{}: case <-ctx.Done(): return }`

**进阶**:令牌桶 / 漏桶限流见 [rate-limiter.md](../20-coding-problems/03-rate-limiter.md);分布式限流要用 Redis,不是 channel。

---

### 5. 发取消信号(Cancellation Broadcast)

**场景**:通知一组 goroutine 退出,**关闭一个 channel = 广播给所有 receiver**。

```go
done := make(chan struct{})

for i := 0; i < 100; i++ {
    go func() {
        for {
            select {
            case <-done:
                return
            case task := <-tasks:
                handle(task)
            }
        }
    }()
}

// 触发取消
close(done) // 100 个 goroutine 同时收到
```

**要点**:
- **关闭已关闭的 channel 是 done channel 的核心利用**——所有 `<-done` 都立即返回零值
- 用 `chan struct{}` 不用 `chan bool`——只传"事件",不传值
- 这是 **`context.Context.Done()` 的底层实现机制**

**易错**:多次 close → panic;用 [sync.Once](../01-go-language/02-concurrency/channel.md#32-syncone-的实现原理) 兜底。

---

### 6. 做超时选择(Timeout)

**场景**:等一个操作,超过 X 秒就放弃。

```go
select {
case v := <-ch:
    return v, nil
case <-time.After(3 * time.Second):
    return zero, errors.New("timeout")
}
```

**要点**:
- `time.After` 返回一个**只读 channel**,N 秒后写入当前时间
- **坑**:`time.After` 在 select 中**未触发也不能立刻 GC**(Go 1.23 前必须 timer 到期或被排空才释放)
- **高频循环**用 `time.NewTimer` + `timer.Reset` + `timer.Stop` 替代

**进阶**:多个超时叠加场景用 `context.WithTimeout`——可以**跨函数传递取消信号**,比 select+timer 干净。

---

### 7. 广播关闭(Broadcast Close)

**场景**:N 个监听者等同一个"事件发生"信号,**关闭 channel 是 Go 里最优雅的广播原语**。

```go
ready := make(chan struct{})

for i := 0; i < N; i++ {
    go func(id int) {
        <-ready // 全部阻塞等待
        run(id)
    }(i)
}

// 发令
close(ready) // N 个 goroutine 同时被唤醒
```

**要点**:
- 比"循环 `ready <- struct{}{}` N 次"高效——**一次 close 唤醒全部**
- 用途:并发测试同时起跑 / 服务就绪通知 / 配置加载完成
- 同义机制有 [Barrier](../20-coding-problems/14-barrier.md)(双向)和 `sync.WaitGroup`(主等子)

**对比第 5 条(取消信号)**:技术机制一样(关闭 channel = 广播),**语义不同**——5 是"停",7 是"开始"。

### 8. 管理生命周期(Lifecycle Management)

**场景**:把"启动 / 运行 / 退出 / 等退出完成"用 channel 表达。

```go
type Worker struct {
    stop chan struct{} // 触发停止
    done chan struct{} // 表示已停止
}

func (w *Worker) Start() {
    go func() {
        defer close(w.done) // 退出时关 done
        for {
            select {
            case <-w.stop:
                return
            case t := <-tasks:
                handle(t)
            }
        }
    }()
}

func (w *Worker) Stop() {
    close(w.stop)
    <-w.done // 等真正退出
}
```

**要点**:
- **两个 channel 分工**:`stop` 是"叫退",`done` 是"退完了"——分离触发和确认
- `Stop()` 阻塞等 `done` 关闭——**保证清理动作完成才返回**(等同 `WaitGroup.Wait`)
- 大型服务的 graceful shutdown 都是这个模式

**对比 ctx**:context 适合"传染式取消"(父取消所有子),lifecycle channel 适合"单点强耦合"(Stop 必须等到清理完)。

### 9. 串行化资源访问(Serializing Access)

**场景**:让某个资源**只被一个 goroutine 拥有**,所有操作通过 channel 排队,**用通信代替锁**。

```go
type Counter struct {
    inc chan struct{}
    get chan int
}

func NewCounter() *Counter {
    c := &Counter{
        inc: make(chan struct{}),
        get: make(chan int),
    }
    go func() {
        var n int
        for {
            select {
            case <-c.inc:
                n++
            case c.get <- n: // 把 n 发出去,谁收谁拿
            }
        }
    }()
    return c
}

func (c *Counter) Inc()      { c.inc <- struct{}{} }
func (c *Counter) Get() int  { return <-c.get }
```

**要点**:
- "持有数据的 goroutine"垄断对数据的访问——**根本不需要锁**
- 这是 Go 提倡的"share by communicating"的最经典示范
- 工业例子:数据库连接池的 Conn ownership / actor 模型(每 actor 一个 goroutine + 一个 mailbox channel)

**取舍**:
- ✅ 复杂状态机用这个写**思路最清晰**
- ❌ 简单计数器还是 `atomic.Int64` 更快——channel 有锁开销

### 10. 组织 pipeline(流水线)

**场景**:多个处理阶段串成流水线,每阶段一组 goroutine,**channel 当传送带**。

```go
// stage 1: 生成
gen := func(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}

// stage 2: 平方
sq := func(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in { out <- n * n }
    }()
    return out
}

// 拼装
for n := range sq(sq(gen(1, 2, 3, 4))) {
    fmt.Println(n) // 1 16 81 256
}
```

**要点**:
- 每阶段**自己负责关 out channel**(收到上游关就关下游),错误隔离
- 阶段之间 buffered channel = **流量缓冲**,平衡上下游速度差
- 并行化:某阶段如果 CPU bound,起 N 个 goroutine 都读同一个 in、写同一个 out(**fan-out + fan-in**)

**真实例子**:Go 官方 [Concurrency Patterns: Pipelines and cancellation](https://go.dev/blog/pipelines) — 必读。生产场景如 ETL 数据处理 / 图像处理流水线 / 编译器(词法 → 语法 → 语义)。

### Channel 场景速查表

| # | 场景 | 关键模式 | 容量 | 谁来 close |
| --- | --- | --- | --- | --- |
| 1 | 传数据 | producer → consumer | buffered(削峰) | sender |
| 2 | 派任务 | 1 chan → N worker | unbuf 或小 buffer | 派发方 |
| 3 | 收结果 | N goroutine → 1 chan | `len(tasks)` | `wg.Wait` 后单独 G 关 |
| 4 | 限流 | buffered 当信号量 | = 并发上限 | **不关** |
| 5 | 发取消 | close = 广播 | 0(unbuf 即可) | 触发取消者 |
| 6 | 超时 | `time.After` / `Timer` | 1 | runtime |
| 7 | 广播开始 | close = N 个唤醒 | 0 | 发令者 |
| 8 | 生命周期 | stop + done 两 chan | 0 | stop 由调用方,done 由 worker |
| 9 | 串行化访问 | actor / owner goroutine | 0 或 1 | 进程结束才关 |
| 10 | pipeline | stage → chan → stage | buffered(流量平衡) | **每阶段关自己的 out** |

---

### 一句话总结

> Channel 不是"加强版 Mutex",而是 **goroutine 的通信线路**——**10 种典型用法本质都是"用消息组织协作"**:
>
> - **数据流**(1/2/3/10)= 传送带
> - **协调控制**(5/7/8)= 广播 / 信号灯
> - **资源约束**(4/6)= 票据 / 沙漏
> - **状态封装**(9)= actor / owner
>
> 选 channel 还是锁的判断:**有"流"或"控制"语义优先 channel,纯共享变量优先锁/atomic**。
