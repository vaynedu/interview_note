## Q1 user_id 分片策略:为什么 32 库 1024 表,怎么扩容

### 题目

> 抖音电商场景,日 2000 万单,峰值大促 4 万 TPS,设计订单表的分库分表方案。回答要覆盖:容量推导、库表数选型、扩容策略、物理部署。

### 标准答案(4S 法)

**Scenario:抖音电商**
- 日 2000 万订单
- 峰值 TPS 4 万(大促 200× 削峰)
- C 端用户查自己订单 + B 端商家查店铺订单
- 3 年留存(热数据 1 年 + 温数据 2 年)

**Service:核心接口**
- 下单(写,带幂等)
- 支付回调(写,状态机推进)
- 用户订单列表(读,按 user_id)
- 商家订单列表(读,按 seller_id,走 ES 异构)

**Storage:容量推导**

```
日订单:2000 万
年订单:2000 万 × 365 = 73 亿
3 年留存:73 亿 × 3 = 220 亿行

为什么 × 3:
- 不是"每年增长 3 倍",是"保留 3 年的数据"
- 第 1 年:73 亿
- 第 2 年:146 亿(去年 + 今年)
- 第 3 年:220 亿(峰值留存)
- 3 年外冷归档,主库永远控制在 220 亿以内
```

**Scale:库表设计**

| 维度 | 数字 | 推导 |
| --- | --- | --- |
| 单表行数上限 | 2000 万 | InnoDB B+ 树 3 层覆盖,超过查询性能急剧下降 |
| 总表数 | 220 亿 ÷ 2000 万 = **1100 表**,取 **1024** | 凑 2^10 便于位运算 |
| 库数 | 1024 ÷ 32 = **32 库**,每库 32 表 | 32 = 2^5,位运算友好 |
| 路由公式 | `db_idx = user_id & 31`<br>`tbl_idx = (user_id >> 5) & 31` | 位运算 0.1ns,远快于取模 |

**为什么是 32 而不是 16 或 64**:
- 16 库:单库 64 表,QPS / 写连接数压力大,峰值 4 万 TPS 单库扛 2500
- **32 库**:单库 32 表,峰值单库 1250 TPS,留 4× 余量 ⭐
- 64 库:库太多,运维成本陡增,物理集群难以摊薄

**1024 表一次性创建(关键)**:
- 哈希函数必须固定,中途加表 → 全量数据 rehash
- 一次性建好 1024 张空表,DDL 成本一次性付清
- 扩容时**只扩物理集群,不扩逻辑库表**

### 物理部署拓扑

```
32 逻辑库 ÷ 4 物理集群 = 每集群 8 库

集群 1(db_00~07):
┌───────────────────────────────────────────────────────┐
│  机器 A 主(AZ-1) ─── 8 库全量(db_00~07)             │
│        ↓ 半同步复制                                    │
│  机器 B 从(AZ-1) ─── 同 AZ 高可用,秒级切换            │
│        ↓ 异步复制                                      │
│  机器 C 从(AZ-2) ─── 跨 AZ 灾备 + 读流量              │
└───────────────────────────────────────────────────────┘

集群 2(db_08~15) / 集群 3(db_16~23) / 集群 4(db_24~31)同构

主区:4 集群 × 3 机器 = 12 台
异地灾备:4 集群 × 2 机器(1 主 1 从)= 8 台
─────────────────────────────────────
总计 20 台物理 MySQL 实例
```

**关键理解**:
- 主从复制单位是**实例级**(整个 mysqld),不是按库切分
- 一集群 3 台机器都是**完整 8 库的副本**,通过 binlog 同步
- 应用层路由决定写哪个**逻辑库**,集群是物理隔离

### 扩容策略(生产真相)

| 扩容路径 | 代价 | 业界做法 |
| --- | --- | --- |
| **扩物理集群**(4 → 8 集群)| 数据物理迁移,应用配置改路由,周末窗口 4h | 抖音 / 淘宝主流 ⭐ |
| **冷数据归档** | 3 年外归档到 HBase / OSS,主库永远 220 亿以内 | 配合方案 ⭐ |
| **扩逻辑库表**(32 → 64 库)| 全量 rehash,3-6 个月迁移期 | 几乎不做 ❌ |

**核心信念**:逻辑库表数(32/1024)永久稳定,基因位锁死,变的只有物理集群数。

### 为什么扩容只扩物理集群,不扩逻辑库表

**一句话本质**:逻辑库表 = 路由函数的输出空间,改了就是全量 rehash;物理集群 = 承载逻辑库的容器,搬运不改路由。

#### 扩逻辑库表的真实代价(为什么不能动)

**1. 哈希函数变了,所有数据都要搬**

```
当前路由:db_idx = user_id & 31    (32 库)
扩到 64 库:db_idx = user_id & 63   (改了!)

用户 user_id = 100:
- 旧路由:100 & 31 = 4   → 落 db_04
- 新路由:100 & 63 = 36  → 落 db_36
→ 这个用户所有订单数据,必须从 db_04 物理搬到 db_36

全量算账:
220 亿行 × 50% 用户需要搬 = 110 亿行 ≈ 11TB 迁移
```

**2. 迁移期间的"双重地狱"**

```
T0:        开始迁移
T0~T+3 月: 双写期(新旧两套表同时写)
T+3 月:    历史数据迁移完成
T+3~T+4 月:灰度切读流量
T+4 月:    全量切流量
T+4~T+5 月:观察期 + 数据对账
T+5 月:    下线旧表

期间风险:
- 双写 = 应用代码复杂度翻倍
- 路由灰度 = bug 可能埋几个月
- 大促期间不敢做 → 一年只有几个窗口
- 头部公司真实数据:某电商 16→32 库,8 人投入 6 个月
```

**3. 基因法 order_id 也会失效**

```
当前 order_id 基因位 5 bit(32 库反查):
GetDBIndex = (orderID >> 17) & 0x1F  → 0-31

扩到 64 库需要 6 bit:
- 历史 order_id 仍 5 bit → 反查仍落 0-31
- 新 order_id 用 6 bit → 落 0-63
→ 客服按 order_id 查,要先判断新旧版本 → 业务代码爆炸
```

#### 扩物理集群的代价(为什么可以做)

**路由不变,数据搬家但归宿不变**:

```
扩容前:4 集群 × 8 库
集群 1: db_00~07
集群 2: db_08~15
集群 3: db_16~23
集群 4: db_24~31

扩容后:8 集群 × 4 库(集群 1 拆 1A + 1B)
集群 1A: db_00~03    ← 换了台机器
集群 1B: db_04~07    ← 换了台机器
集群 2~4: 不变

应用层路由:
- user_id & 31 = 2 → 落 db_02 → 不变!
- DBA 改 db_02 → ip 映射,应用配置 reload
```

**拆集群 1 步骤**:
1. 申请新机器组成集群 1B(1 主 + 2 从)
2. 集群 1B 作为集群 1 下游从,实时同步全量 8 库
3. 集群 1B 追平 binlog 后,改配置:
   - 集群 1 只服务 db_00~03
   - 集群 1B 只服务 db_04~07
4. 各自删除多余的库,完成

**关键差异**:**没有任何数据需要 rehash**,只是物理位置变化。4 小时窗口,业务零感知。

#### 哈希函数契约的本质

```
分库分表的核心契约:
   "user_id X 永远落在 hash(X) 这个位置"

如果契约变 → 所有依赖该契约的东西都要变:
- ✗ 历史数据物理位置
- ✗ order_id 基因位编码
- ✗ 应用层路由代码
- ✗ 二级索引(seller_id → user_id → db)
- ✗ 监控告警的库维度统计

如果契约不变 → 物理层可以随便折腾:
- ✓ 一台机器服务 N 个库 / N 台机器服务 1 个库
- ✓ 跨机房迁移 / 主从切换 / 集群重组
- ✓ 应用层零感知
```

#### 完整对比表

| 维度 | 扩逻辑库表(32 → 64) | 扩物理集群(4 → 8) |
| --- | --- | --- |
| 路由函数 | 改(`user_id & 63`)| 不变 |
| 历史数据 | 50% 需 rehash 迁移 | 物理搬家,不重分布 |
| 数据量 | 11TB 真实迁移 | 0 字节"重写" |
| order_id 基因位 | 失效,需新旧兼容 | 完全不影响 |
| 应用代码 | 路由 + 双写 + 灰度大改 | 配置 reload,零代码改 |
| 窗口期 | 3-6 个月 | 4 小时 |
| 人力 | 6-10 人月 | 2-3 人天 |
| 风险 | 双写不一致 / 灰度 bug | 配置错误(可秒级回滚)|
| 业务感知 | 双写期慢,切换期可能错 | 几乎无感 |

#### 什么时候真的要扩逻辑库

只有一种情况:**当初设计的库表数已无法承载,且冷归档也救不了**。

```
判断公式:
未来 N 年数据量 > 库数 × 表数 × 2000 万

抖音电商场景:
- 1024 表 × 2000 万 = 220 亿
- 3 年留存策略下,主库永远 ≤ 220 亿
- 3 年外归档到 HBase / OSS
- → 永远不需要扩逻辑库

什么场景会需要扩:
- 当初容量预估错误(设计 32 表,实际需要 1024 表)
- 业务模型变化(原本一单一行 → 一单 100 行明细)
- 监管要求(数据保留期从 3 年延长到 10 年)
```

#### 为什么不设计 65536 表"以绝后患"

```
表太多的成本:
- 1024 表已接近 MySQL 单实例性能上限(打开文件 / 元数据缓存)
- 65536 表 → 单库 2048 表,DDL 一次建表要几小时
- 应用层连接池 / 监控指标爆炸
- 跨表查询成本指数上升

1024 表的甜蜜区:
- 覆盖 3 年抖音电商主流业务
- 单表 2000 万行(B+ 树 3 层覆盖)
- DDL / 监控 / 运维成本可接受
- 配合冷归档实现稳态
```

#### 面试一句话答法

> "扩逻辑库要改哈希函数,触发全量 rehash(11TB 迁移、3-6 个月)、order_id 基因位失效、应用层双写灰度。扩物理集群只是把'谁服务哪个库'的映射改了,路由函数不变、数据零重分布、应用零感知,4 小时窗口完成。所以设计时一次性预建 1024 表覆盖 3 年容量 + 冷归档兜底,生产稳态永远不动逻辑库,只调整物理集群数。"

### 易错点

- ❌ "× 3 是每年 3 倍增长" → 实际是"留存 3 年"
- ❌ "可以中途加表" → 哈希函数固定,加表 = 全量 rehash
- ❌ "32 库 = 32 台机器" → 32 是**逻辑库**,物理可能只有 12 台(4 集群)
- ❌ "1024 表按需创建" → 必须一次性建好,避免热点和 DDL 风暴
- ❌ "主从复制按库切分" → 复制单位是 mysqld 实例,全量复制

### 追问预案

1. **为什么不用一致性哈希?**
   - 一致性哈希适合 Redis / 缓存(节点动态变化)
   - MySQL 分库分表是固定方案,直接取模更简单,运维可控

2. **同一用户的订单为什么落在同一库?**
   - 用户查自己订单是最高频场景,单库聚合无需跨库 JOIN
   - 用户分布天然均匀,不会热点

3. **如果某个大用户(企业号)订单量超大怎么办?**
   - 二级分片:user_id + month 联合分片
   - 或者大用户单独拆表(白名单机制)

4. **跨库查询(如运营后台)怎么处理?**
   - 走 ES 异构索引(详见 Q3-C)
   - 或者离线 ClickHouse 跑聚合

5. **DDL 怎么管理?**
   - gh-ost / pt-online-schema-change 在线 DDL
   - 1024 表分批执行,每批 32 张
   - 灰度发布,先小流量验证

### 背诵版

> 抖音电商日 2000 万单,3 年留存 220 亿行,按 user_id 取模分 32 库 × 32 表 = 1024 表,32 = 2^5 位运算友好。1024 表一次性预建,哈希函数永久固定。物理部署 4 集群(每集群 1 主 2 从跨 AZ)= 12 台 + 异地灾备 8 台 = 20 台。扩容只扩物理集群不扩逻辑库,冷数据归档配合主库 220 亿稳态。

## Q1.1 集群 1 主库挂了,业务影响什么,恢复多久

### 题目

> 接 Q1,假设集群 1 的主库(机器 A)突然宕机,详细说明:业务影响范围、读写链路表现、恢复时间、数据丢失风险。

### 标准答案

**一句话**:db_00~07 写入中断 5-30 秒(取决于切换方案),db_08~31 完全不受影响;读流量降级到从库可用。

### 业务影响范围(按分片精确切)

| 用户分片 | 影响 | 原因 |
| --- | --- | --- |
| `user_id & 31 ∈ [0, 7]` | **写入失败** | 路由到集群 1 主,主挂无法写 |
| `user_id & 31 ∈ [0, 7]` | **读可降级** | 路由到机器 B/C 从库,有 ms 级主从延迟 |
| `user_id & 31 ∈ [8, 31]` | **完全无感** | 路由到集群 2/3/4,物理隔离 |

**量化**:日 2000 万单 → 每集群 500 万单 → 故障影响 25% 用户的下单链路。

### 读写链路表现

**写链路(下单 / 支付确认)**:
```
用户(user_id & 31 = 3,落 db_03)
    ↓
应用层路由 → 集群 1 主(机器 A)
    ↓
TCP 连接拒绝 / 超时
    ↓
返回 5xx,前端"系统繁忙,请稍后重试"
```

**业务降级**:
- 下单:用户失败,刷新后(切换完成)成功
- 支付回调:支付网关重试机制(本身有幂等),延迟到账不丢
- **订单超时关闭**(附录 B 定时扫描):故障期间扫不到 db_00~07,延迟关闭

**读链路(订单详情)**:
```
应用层感知主挂 → 降级到机器 B / C 从库
    ↓
可能读到主挂前 N ms 的数据(主从延迟)
    ↓
"刚下单的订单可能查不到" → 业务可接受
```

### 恢复时间分层

| 方案 | 检测 | 切换 | 总恢复 | 业界采用 |
| --- | --- | --- | --- | --- |
| **MHA / Orchestrator 自动切** | 5-10s | 5-15s | **10-30s** ⭐ | 抖音 / 美团 / 头部电商 |
| **MySQL Group Replication** | 3-5s | 2-5s | **5-10s** | 金融 / 强一致场景 |
| **人工切换** | 1-5min | 5-10min | **10-30min** | 中小厂、内部系统 |
| **同城 AZ 整体故障** | + DNS 切换 | + 60s | **60-90s** | 跨 AZ 灾备触发 |

**MHA 恢复流程详解**:
```
T+0s:    机器 A 主库 crash
T+5s:    哨兵检测主不可达(连续 3 次心跳失败)
T+10s:   选举新主 → 选 binlog 位点最新的从(假设机器 B)
T+15s:   补齐 binlog 差异(MHA 拉取剩余 binlog 应用)
T+20s:   修改 VIP / 配置中心 → 应用层重新连接到机器 B
T+25s:   机器 C 重新挂载到新主 B 继续复制
T+30s:   全链路恢复
```

### 数据丢失风险

| 复制模式 | 主挂时数据丢失 | 性能 |
| --- | --- | --- |
| **异步复制** | 可能丢最后几十 ms 事务 | 最好 |
| **半同步**(`semi_sync_master_wait_for_slave_count=1`)⭐ | 几乎不丢 | 写延迟 +1-2ms |
| **全同步 MGR** | 完全不丢 | 写延迟 +5-10ms |

**抖音电商选择**:
- 半同步复制 + `sync_binlog=1` + `innodb_flush_log_at_trx_commit=1`(双 1)
- 极端情况(主和半同步从同时挂)才丢数据,概率极低

**丢了几条订单怎么办**(资深答法):
- **支付侧对账兜底**:T+1 对账发现"支付成功但订单不存在"→ 补单
- **MQ 消息回查**:RocketMQ 事务消息可重投
- **业务侧**:用户刷新发现订单消失 → 客服补录(罕见)

### 架构反思(资深加分)

> "分库的隐藏价值是**故障爆炸半径压缩**,不只是为了容量。"

```
没有分库:主挂 → 100% 用户写入失败
4 集群分库:主挂 → 25% 用户失败 30s + 75% 无感
16 集群分库(金融级):主挂 → 6.25% 用户失败 30s
```

金融系统选 16/64 集群,哪怕容量用不完,就是为了把故障半径压到 1/16、1/64。

### 易错点

- ❌ "主挂全站瘫痪" → 只影响 1/N 分片
- ❌ "切换 0 秒" → 至少 10-30 秒(MHA)
- ❌ "复制没延迟" → 跨 AZ 复制 ms 级延迟,极端情况秒级
- ❌ "半同步绝对不丢" → 极端双挂还是会丢

### 追问预案

1. **为什么半同步不开 `wait_for_slave_count=2`?** 写延迟翻倍,大促扛不住,1 个从足够
2. **切换期间业务怎么提示用户?** 网关层返回 503 + Retry-After 头,前端等待重试
3. **机器 C 跨 AZ 也挂了怎么办?** 启动异地灾备集群(4 集群在异地有 1 主 1 从)
4. **怎么避免脑裂?** MHA / Orchestrator 用第三方仲裁(ZK / etcd),避免双主写入
5. **大促期间故障怎么处理?** 提前预案:降级开关、限流加强、客服话术

### 背诵版

> 集群 1 主挂只影响 1/4 用户(`user_id & 31 ∈ [0,7]`),写入中断 30 秒(MHA 自动切),读流量降级到从库可用,半同步复制保证几乎不丢数据,极端情况靠支付对账兜底。分库的隐藏价值是把故障爆炸半径压到 1/集群数,这是 4 集群架构的灵魂。

## Q2 order_id 位段设计 + 基因法扩容代价

### 题目

> 设计抖音电商的 order_id,要求全局唯一、趋势递增、64 位 long,不查路由表能直接反推数据库分片,并评估 32→64 库扩容时基因法的代价。

### 标准答案:Snowflake 改造 + 基因位

**64 位结构**:
```
┌─────┬──────────────────────────────────┬─────────┬─────────┬──────────┐
│ 1bit│         41bit 时间戳              │  5bit   │  5bit   │  12bit   │
│符号 │      毫秒级,可用 69 年            │ 基因位  │ 机器位  │  序列号  │
│ 0   │  (从 2024-01-01 起)              │ 分片定位│ workerID│ 同毫秒内 │
└─────┴──────────────────────────────────┴─────────┴─────────┴──────────┘
   1            41                            5         5         12
                                            = 32       = 32      = 4096
```

**各位段为什么这样切**:

| 位段 | 长度 | 容量 | 为什么 |
| --- | --- | --- | --- |
| 符号位 | 1 bit | 0/1 | Java long 兼容,固定 0 |
| 时间戳 | 41 bit | 69 年 | 够用到 2093 年,2024 起算 |
| **基因位** | **5 bit** | **32 库** | `= log2(32)`,刚好覆盖所有分片 ⭐ |
| 机器位 | 5 bit | 32 实例 | 发号器节点数,够全国部署 |
| 序列号 | 12 bit | 4096/ms | 单机 400 万 QPS,远超需求 |

### 生成与反查(核心代码)

```go
func GenerateOrderID(userID int64) int64 {
    timestamp := time.Now().UnixMilli() - epoch  // 41 bit
    geneBit := userID & 0x1F                      // user_id 低 5 位 = 基因
    workerBit := workerID & 0x1F                  // 5 bit
    seqBit := atomic.AddInt64(&seq, 1) & 0xFFF    // 12 bit

    return timestamp<<22 | geneBit<<17 | workerBit<<12 | seqBit
}

func GetDBIndex(orderID int64) int {
    // O(1) 位运算抽取基因位,无需查路由表
    return int((orderID >> 17) & 0x1F)  // = user_id & 31
}
```

### 基因法的核心价值

| 场景 | 无基因位 | 有基因位 |
| --- | --- | --- |
| 用户查自己订单 | 知道 user_id,正常 | 一样正常 |
| **客服按 order_id 查** | 查映射表 2 次 ≈ 2ms | **位运算 0.1ms** ⭐ |
| **支付回调按 order_id 更新** | 扫 32 库或查映射表 | 位运算定位单库 |
| **风控按 order_id 反查** | 全库扫描 | 部分推导 |

**1000× 性能差异来源**:
- 无基因位:32 库扫描 ≈ 100ms
- 有基因位:1 次单库查询 ≈ 0.1ms

### 基因位本质

```
user_id = 87654321
user_id & 31 = 17 (二进制 10001)
                       └── 这 5 位"基因",编码进 order_id
                       
order_id 携带 user_id 低 5 位"DNA",查询时抽出反查分片
```

### 32→64 库扩容代价(关键)

**表面问题**:基因位 5 bit 锁死,扩 64 库需要 6 bit,**位段不够了**。

**三种扩容路径**:

| 方案 | 代价 | 适用 |
| --- | --- | --- |
| **A. 提前预留位段** | 设计时给 7 bit(支持 128 库),时间戳压到 39 bit(17 年)或序列号压到 10 bit | 长期规划 |
| **B. 重新发号 + 双写** | 新订单 6 bit,老订单保留 5 bit | 容量真不够时 |
| **C. 不扩库,扩集群** ⭐⭐ | 32 库不变,把承载 db_00~07 的集群拆成集群 1A + 1B | 生产首选 |

**方案 C 详解(生产真实做法)**:
```
扩库的真实成本:
1. 重新分布 220 亿行(user_id & 63)
2. 50% 数据迁库,3-6 个月迁移期
3. 业务峰值期间不敢做

扩集群的成本:
1. 32 库 / 基因位 / order_id 全不变
2. 物理迁移 + 应用配置改路由
3. 周末 4h 窗口完成,业务无感
```

**业界做法对比**:

| 公司 | 时间戳 | 基因 | 机器 | 序列 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 抖音电商 | 41 | 5 | 5 | 12 | 32 库 |
| 淘宝 | 41 | 10 | 4 | 8 | 1024 库,基因位最长 |
| 美团 | 41 | 6 | 6 | 10 | 64 库 |
| 京东 | 41 | 7 | 5 | 10 | 128 库,长期规划 |

### 基因法的边界(资深主动讲)

| 场景 | 为什么不行 |
| --- | --- |
| **B 端商家查** | 基因位是 user_id 编码,商家维度需 ES 异构(Q3-C) |
| **三方订单 ID** | 支付宝 / 微信回调用对方 trade_no,要建映射表 |
| **订单合并 / 拆单** | 子订单 user_id 可能不一致,基因位失真 |
| **运营聚合** | "查所有待发货",还是扫全库 |

### 易错点

- ❌ "基因位 5 bit 只能区分 32 个用户" → 是分片定位,不是用户标识
- ❌ "扩库 = 加位段" → 位段锁死,只能换发号或扩集群
- ❌ "UUID 也可以" → 128 位无序,B+ 树插入随机分裂,写性能差 10×
- ❌ "数据库自增也行" → 单点瓶颈、不唯一、泄露业务量

### 追问预案

1. **时钟回拨怎么办?** NTP 监控 + 回拨 < 5ms 等待,> 5ms 报警拒绝发号
2. **跨年序列号溢出?** 12 bit = 4096/ms,溢出 sleep 到下一毫秒
3. **基因位泄露用户分布?** 5 bit 信息量极小,只是分片归属,不暴露 user_id
4. **双 11 5 倍流量?** workerID 5 bit = 32 节点,横向扩,无状态服务
5. **新业务接入怎么发号?** 同一发号器服务,通过 bizType 参数区分,基因位由调用方传入

### 背诵版

> order_id 用 Snowflake 改造 = 1 符号 + 41 时间戳 + 5 基因 + 5 机器 + 12 序列 = 64 位。基因位 = `user_id & 31`,实现 O(1) 反查分片(1000× 性能差异)。32→64 库扩容时基因位锁死,生产首选**扩物理集群不扩逻辑库**,逻辑库 / 基因位 / order_id 永久稳定。B 端、三方、合单场景基因法失效,需要 ES 或映射表配合。

## Q3-A 订单状态机:15 状态 + CAS 推进 + 死锁预防

### 题目

> 设计完整订单状态机,要求覆盖:状态拆分、不可逆约束、并发推进的 CAS 实现、死锁预防方案。

### 标准答案

**完整 15 状态(抖音电商生产)**:

```
                    ┌─────────────┐
                    │ 0. INIT     │ 下单中(瞬态,不落库)
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │ 1. WAIT_PAY │ 待支付
                    └──┬───────┬──┘
              支付成功  │       │ 超时/取消
                       ↓       ↓
            ┌──────────────┐ ┌─────────────────┐
            │ 2. PAID      │ │ 11. CANCELED    │
            └──────┬───────┘ └─────────────────┘
                   ↓
            ┌──────────────┐
            │ 3. STOCK_OUT │ 已扣库存,待商家发货
            └──────┬───────┘
                   ↓
            ┌──────────────┐
            │ 4. SHIPPING  │ 已发货,运输中
            └──┬───────────┘
               ↓
        ┌─────────────────┐
        │ 5. DELIVERED    │ 已签收
        └──┬─────────┬────┘
           ↓         ↓
   ┌──────────┐  ┌─────────────────┐
   │ 6. DONE  │  │ 7. AFTERSALE    │ 售后中
   └──────────┘  └──┬──────────────┘
                    ↓
         ┌──────────────────────────┐
         │ 8. REFUNDING (退款中)    │
         │ 9. REFUNDED  (已退款)    │
         │ 10. RETURN_REJECTED     │
         └──────────────────────────┘

最终态(不可变):6 / 9 / 10 / 11 / 12-EXCEPTION
```

### 不可逆约束(核心)

| 约束类型 | 含义 | 实现 |
| --- | --- | --- |
| **单调推进** | 状态值只增不减 | `WHERE state < new_state` |
| **特定路径** | 不能跳跃(1→4 非法)| 状态机表 + 校验 |
| **最终态锁死** | DONE/CANCELED 不可改 | `WHERE state NOT IN (终态)` |
| **幂等** | 重复推进返回成功 | `affected_rows = 0` 时查当前态 |

### CAS 推进(防并发覆盖)

```sql
-- ❌ 错误:可能被覆盖
UPDATE orders SET state = 'PAID' WHERE order_id = ?;

-- ✅ 正确:CAS 带前置态校验
UPDATE orders 
SET state = 'PAID', updated_at = NOW()
WHERE order_id = ? 
  AND state = 'WAIT_PAY'      -- 断言当前态
  AND expire_time > NOW();    -- 断言未过期

-- 根据 affected_rows 判断:
-- 1 → 成功
-- 0 → 失败(已支付/取消/过期),查当前态决定后续
```

### 并发死锁场景(高频考点)

**场景**:支付回调 + 超时关单 同时触发同一订单。

```
Goroutine A(支付回调):
  BEGIN
  UPDATE orders SET state='PAID' WHERE order_id=X ...    -- 持锁 X
  UPDATE inventory SET sold=sold+1 WHERE sku_id=Y         -- 等锁 Y
  
Goroutine B(定时关单):
  BEGIN
  UPDATE inventory SET sold=sold-1 WHERE sku_id=Y         -- 持锁 Y
  UPDATE orders SET state='CANCELED' WHERE order_id=X ... -- 等锁 X
  
→ 死锁!
```

**4 种预防**:

| 方案 | 实现 | 优劣 |
| --- | --- | --- |
| **统一加锁顺序** ⭐ | 永远先锁 orders 再锁 inventory | 简单可靠,首选 |
| **CAS 替代行锁** | UPDATE 带 WHERE 不显式 SELECT FOR UPDATE | 减少锁持有时间 |
| **拆分事务** | 状态推进 + 库存操作分两事务 + MQ 兜底 | 最终一致 |
| **乐观锁 version** | `WHERE version = ?` 失败重试 | 适合高冲突场景 |

### 完整推进链路(支付成功)

```go
func PaymentCallback(orderID int64) error {
    // 1. 基因法定位库,查当前态
    order := query(orderID)
    
    // 2. 幂等检查
    if order.State == "PAID" {
        return nil  // 已处理
    }
    if order.State != "WAIT_PAY" {
        return ErrIllegalStateTransition
    }
    
    // 3. CAS 推进
    tx := db.Begin()
    affected := tx.Exec(`
        UPDATE orders SET state='PAID', paid_at=NOW()
        WHERE order_id=? AND state='WAIT_PAY' AND expire_time > NOW()
    `, orderID).RowsAffected
    
    if affected == 0 {
        tx.Rollback()
        return handleStateConflict(orderID)
    }
    
    // 4. 发 MQ:库存实扣 + 商家通知 + 物流触发
    tx.Exec(`INSERT INTO order_event (order_id, event_type) VALUES (?, 'PAID')`, orderID)
    tx.Commit()
    
    return nil
}
```

### 易错点

- ❌ "状态字段用 int" → 用字符串枚举,可读性 + 兼容性
- ❌ "可以从 SHIPPING 退到 PAID" → 状态不可逆,只能新增 REFUND 分支
- ❌ "幂等靠业务层判断" → 必须 DB 层 CAS,业务判断有 TOCTOU 漏洞
- ❌ "事务内做太多事" → 状态推进与下游解耦,用 MQ

### 追问预案

1. **状态机怎么扩展?** 状态表 + 转移表(`state_transition`)配置化,新状态加配置不改代码
2. **历史状态怎么查?** `order_state_history` 表记录每次推进,审计 + 排查必备
3. **支付成功后扣库存失败怎么办?** 状态改回 WAIT_PAY?不行!补偿:发 MQ 异步重试 + 告警
4. **如何避免脑裂(双消费者同时处理)?** 消息层加分布式锁 + DB CAS 双重保证
5. **状态机能 Saga 化吗?** 可以,每步推进 = Saga step,失败回滚发补偿消息

### 背诵版

> 订单状态机 15 状态,核心约束:单调推进 + 路径校验 + 最终态锁死 + 幂等。CAS 推进用 `UPDATE ... WHERE state=旧态`,affected_rows = 0 时查当前态判断幂等还是冲突。死锁预防 4 招:统一加锁顺序(首选)、CAS 替代行锁、事务拆分 + MQ、乐观锁 version。状态推进与下游(库存/物流)解耦走 MQ,避免长事务和死锁。

## Q3-B 大促 200× 削峰:五层架构 + 上下游级联保护

### 题目

> 抖音双 11 大促,日常 2300 TPS,大促峰值 4 万 TPS(瞬时 10 万),如何用 MQ + Redis 预占 + 异步落库扛住?上下游(库存/支付/物流)如何级联保护?

### 标准答案

**容量挑战**:
```
日常:日 2000 万单 ÷ 86400 = 230 TPS,峰值 ×10 = 2300 TPS
大促:日 4 亿单(×20)峰值 ×10 = 4 万 TPS,瞬时 10 万
→ 相对日常基线 200× 放大
```

### 五层削峰架构

```
用户 → CDN/接入层(L1)
       ↓
       网关限流(L2)
       ↓
       Redis 预占库存(L3,核心)⭐
       ↓
       MQ 异步下单(L4,削峰填谷)
       ↓
       MySQL 落库(L5,稳态)
```

**L1 CDN / 接入层**:
- 商详 / 活动页 CDN 静态化(99% 流量挡源站外)
- 用户态、购物车走 Redis,不打 DB
- LVS / Nginx 限流(单 IP / 单用户 N QPS)

**L2 网关限流**:
- 令牌桶:全局 5 万 TPS 上限
- 滑动窗口:单用户 10 次/秒
- 黑白名单:风控羊毛号直接拒
- 排队令牌:发"准入券"按券进下单

**L3 Redis 预占(核心)**:
- 单 Redis 节点 10 万 QPS
- 集群 10 节点 = 100 万 QPS
- 热点 SKU 分 32 桶 → 单 SKU 也能 100 万 QPS(详见 24-order-system 附录 C)
- Lua 脚本 0.1ms 完成"判断 + 扣减 + 防重"

**L4 MQ 削峰(关键)**:
```
Redis 预占成功(同步)→ 用户立刻"下单成功,请支付"
                  ↓
                  发 MQ(异步)
                  ↓
              下单消费者(限速 5000 TPS 稳态)
                  ↓
              MySQL 落 orders 表

削峰原理:
- 峰值 10 万 TPS 进 MQ(MQ 扛得住)
- 消费者按 DB 容量稳态消费(5000 TPS)
- 峰值积压 5 分钟 → 用 20 分钟消化
- 用户感知:已下单(基于 Redis),订单详情可能延迟 N 秒可见
```

**L5 MySQL 稳态**:
- 写入控制在 5000 TPS(主库 IOPS 上限)
- 分库后单库 5000/32 = 156 TPS(轻松)
- 读流量走从库 + 缓存
- 大促前主库扩容 + IOPS 升级

### 上下游级联保护

| 链路 | 保护手段 |
| --- | --- |
| **库存系统** | Redis 预占 + 异步同步 MySQL,DB 永远稳态 |
| **支付系统** | 支付前置(微信/支付宝)有自己限流,我方做幂等回调 |
| **物流系统** | 物流单 T+1 生成,大促延后是用户预期 |
| **优惠券系统** | 提前预热 Redis,核销走分布式锁(详见 [14b-coupon-system-4s.md](../10-system-design/14b-coupon-system-4s.md))|
| **商家系统** | 推送商家走 MQ,商家端通知可延迟 1-5 分钟 |
| **风控系统** | 异步风控(下单后秒级),识别羊毛冻结订单 |

### 兜底降级(5 级)

```
L1: 关闭非核心功能(订单历史、推荐)
L2: 详情页降级(只显示价格 + 库存,不展示评论)
L3: 排队模式(用户进入"排队中,前面 N 人")
L4: 部分商品下架(无库存 SKU 直接屏蔽)
L5: 整体限流(返回"系统繁忙",保住核心交易)
```

### 大促前准备清单

- [ ] 容量评估(往年峰值 × 1.5 预留)
- [ ] DB 扩容(主库升配 + 从库加机)
- [ ] Redis 集群扩容(热点 SKU 分桶预热)
- [ ] MQ topic 扩容(分区数翻倍)
- [ ] 全链路压测(3 轮:基线 / 峰值 / 极限)
- [ ] 限流参数调优(网关 / 应用 / DB 三层)
- [ ] 应急预案(降级开关 / 灰度回滚 / 数据回补)

### 易错点

- ❌ "MQ 能扛无限峰值" → MQ 也有上限(Kafka 单 topic 百万 TPS,但写盘有瓶颈)
- ❌ "Redis 集群无限扩" → 单 key 落单节点,热点 SKU 必须分桶
- ❌ "用户预占成功 = 下单成功" → DB 落库可能失败,需对账兜底
- ❌ "限流只在网关做" → 必须多层(网关 / 应用 / DB),网关挡不住所有

### 追问预案

1. **Redis 挂了怎么办?** 本地内存兜底(单机预占)+ 降级到 DB 直扣(QPS 限制)
2. **MQ 消费失败怎么办?** 死信队列 + 人工补偿 + 用户告知"订单处理中"
3. **DB 写满了怎么办?** 主库切只读 + 降级 + 提前归档冷数据
4. **怎么保证消费有序?** Kafka 按 order_id hash 分区,单分区单消费者
5. **大促后数据怎么追平?** Redis 与 MySQL 异步同步,T+1 对账,差异 < 0.01%

### 背诵版

> 大促 200× 削峰五层:CDN 静态化 / 网关令牌桶 / Redis Lua 预占(单节点 10w 集群 100w QPS,热点分 32 桶)/ MQ 异步落库(峰值进 MQ 消费稳态 5000 TPS)/ MySQL 分库后单库 156 TPS 轻松。上下游级联保护:库存预占 + 支付幂等 + 物流延后 + 商家异步通知。5 级降级兜底:关非核心 / 降详情 / 排队 / 下架 / 限流。

## Q3-C B 端商家 ES 异构索引:CDC 同步 + 一致性 + 索引爆炸

### 题目

> C 端用户查订单走 MySQL 基因法定位单库 0.1ms,B 端商家查"店铺所有订单"需要全库扫描。如何用 ES 异构索引解决?如何保证数据一致?如何防止索引爆炸?

### 标准答案

**为什么 C 端 OK,B 端崩**:
```
C 端(查自己订单):
SELECT * FROM orders WHERE user_id = ?  
→ 基因法定位单库 → 0.1ms ✅

B 端(查店铺所有订单):
SELECT * FROM orders WHERE seller_id = ? AND state = 'WAIT_SHIP'  
→ 32 库全扫 → 100ms+,QPS 撑不住 ❌

商家查询模式:
- 按时间范围(订单列表)
- 按状态(待发货、待退款)
- 按金额、SKU、买家关键字
- 多条件组合 + 分页排序
→ 需要倒排索引 + 多维聚合 → ES 天然适配
```

### 整体架构

```
MySQL 32 库(主存,C 端读写)
    ↓ binlog
Canal / Flink CDC(数据同步)
    ↓
Kafka(削峰 + 多消费者)
    ↓
ES 集群(异构索引,B 端读)
    ↑
B 端商家后台查询
```

### CDC 同步链路

```
1. 订单写 MySQL → 产生 binlog
2. Canal 监听 binlog → 解析为变更事件
3. 推送到 Kafka topic(按 order_id hash 分区,保序)
4. ES 写入消费者:
   - 全字段 upsert 到 ES index
   - 失败重试(死信队列兜底)
5. 商家查询直接打 ES
```

### 数据一致性(核心难点)

| 一致性级别 | 延迟 | 实现 |
| --- | --- | --- |
| **强一致** | 不可能 | ES 异构本质是异步 |
| **秒级一致** ⭐ | 1-5 秒 | CDC + Kafka + ES,主流 |
| **分钟级** | 1-5 分钟 | T+5 离线同步,只适合分析 |

**业务侧妥协**:
- 商家看到订单可能延迟 1-3 秒(可接受)
- 关键操作(发货)回 MySQL 二次校验(防 ES 数据陈旧)
- 商家 UI 显示"数据延迟约 N 秒"

### 查询路由(关键设计)

```go
func QueryOrder(req QueryReq) Result {
    switch req.Scenario {
    case "user_own_orders":  
        return queryMySQL(req)  // C 端,基因法
    case "seller_dashboard":  
        return queryES(req)     // B 端,异构索引
    case "payment_callback":  
        return queryMySQL(req)  // 强一致,必须 MySQL
    case "ops_report":        
        return queryClickHouse(req)  // OLAP 分析
    }
}
```

### 索引爆炸治理(资深考点)

**问题**:订单日增 2000 万,ES 单 index 一年 70 亿文档,查询性能崩。

**4 种治理**:

| 方案 | 实现 | 适用 |
| --- | --- | --- |
| **按时间分 index** ⭐ | `orders_2026_06` 每月一个 | 主流 |
| **冷热分离** | 热 SSD,冷 HDD,3 月前归档 | 节省成本 |
| **routing 优化** | 按 seller_id routing,商家查只命中部分分片 | 高频查询 |
| **聚合预计算** | 商家概览预聚合 Redis,不走 ES | 极端高频 |

```
ES 索引配置示例:
orders_2026_06(当月,30 分片,SSD,3 副本)
orders_2026_05(上月,20 分片,SSD,2 副本)  
orders_2026_04(2 月前,10 分片,HDD,1 副本)
orders_archive(3 月前,关闭,需要查再开)
```

### 双写一致性兜底

```
T+1 对账:
- 每天凌晨扫 MySQL 当天数据 ↔ ES 比对
- 缺失文档 → 补写 ES
- 字段不一致 → 以 MySQL 为准修复
- 报告异常数据量(SRE 监控)

实时兜底:
- ES 写入失败 → 死信队列
- 死信消费者定时重试
- 重试 3 次失败 → 告警 + 人工
```

### ES 容量估算

```
单订单文档:约 2KB(订单字段 + 商品快照)
日增:2000 万 × 2KB = 40GB
月增:1.2TB
年增:14.4TB
3 副本:43TB/年

热数据(1 月):1.2TB × 3 = 3.6TB → 6 台 SSD 机
温数据(2-3 月):2.4TB × 2 = 4.8TB → 4 台 SSD 机
冷数据(3 月+):归档 OSS,需要再开

ES 集群配置:
- master 3 节点(选举,小规格)
- data 热 6 + 温 4 + 冷 2 节点
- coordinating 4 节点(查询路由)
```

### 同步 lag 监控

```
关键指标:
- Canal 解析延迟(binlog → Kafka)   目标 < 100ms
- Kafka 积压(producer - consumer offset)目标 < 1 万
- ES 写入延迟(Kafka → ES 可查)    目标 < 1 秒
- 端到端 lag(MySQL 写 → ES 可查)  目标 < 3 秒,告警 > 10 秒

故障自愈:
- lag > 10s → 自动扩 consumer 实例
- lag > 60s → 告警 + 降级(商家端提示数据延迟)
- ES 完全挂 → 降级 MySQL 慢查询(限流保护)
```

### 易错点

- ❌ "ES 能实时一致" → 异步本质,最快秒级
- ❌ "binlog 直接打 ES" → 必须中间过 Kafka 削峰 + 解耦
- ❌ "ES 永久存" → 索引爆炸,必须按时间分 + 冷热分
- ❌ "ES 挂了商家不能用" → 降级 MySQL 慢查询 + 提示

### 追问预案

1. **Canal 单点怎么办?** 主备模式,ZK 选主,主挂秒级切换
2. **Kafka 分区怎么定?** order_id hash,保证同订单 update 有序消费
3. **ES mapping 怎么设计?** 关键字段 keyword(精确查),text(全文),date 时间
4. **ES 分片数怎么定?** 单分片 30-50GB,按数据量推导,后期可 split
5. **怎么处理订单删除?** 软删除(state=DELETED),ES 同步删除标记,定期物理清理

### 背诵版

> B 端商家查走 ES 异构:MySQL binlog → Canal → Kafka → ES,秒级一致。查询路由按场景区分(C 端 MySQL / B 端 ES / 强一致 MySQL / OLAP ClickHouse)。索引爆炸 4 治理:按月分 index / 冷热分离 / seller_id routing / 聚合预计算。T+1 对账兜底,lag > 10s 告警,ES 挂降级 MySQL 慢查询。
