# 分布式

> 后端架构核心。本目录按 **"为什么 → 三大块 → 怎么做 → 环环相扣 → 通用学习模板"** 五层组织——从体系层面理解分布式,而不是死记技术名词。

## ★ 第一层:为什么会有分布式?

因为**单机扛不住**或**单机风险太高**。具体五个驱动力:

| 维度 | 单机瓶颈 | 业务后果 |
| --- | --- | --- |
| **性能瓶颈** | CPU / 内存 / IO 撑不住 | QPS 上去 = 慢 = 超时 = 雪崩 |
| **容量瓶颈** | 数据撑爆单库单表 | 10 亿订单 = 单表查询 / 写入崩 |
| **可用性问题** | 单点故障 = 全站挂 | 机房断电 = 业务死 |
| **协作效率** | 单体仓库迭代慢 | 多团队互等 = 上线卡 |
| **地域问题** | 跨地域延迟高 | 跨洋请求 200ms+ = 不可用 |

但**分布式不是免费午餐**,它带来一堆新问题:

- **网络不可靠** — 超时 / 丢包 / 分区
- **调用链变长** — 单机一步,分布式十跳
- **数据一致性变难** — 跨节点状态不再天然一致
- **故障点变多** — N 个组件 = 故障概率 N 倍
- **排查复杂** — 一次报错可能涉及 5 个服务

→ 分布式的**所有技术,本质都是在解决"分布式带来的新问题"**——这是三大块的来源。

## ★ 第二层:三大块解决什么问题?

| 块 | 解决问题 | 关键词 | 主要文件 |
| --- | --- | --- | --- |
| **🧱 分布式原理(协同)** | 多机协同工作,数据 / 状态 / 调用链不乱 | CAP / 共识 / 事务 / 锁 / ID / 治理 / 追踪 | 01-05、09-10 |
| **⚡ 高性能设计(扛流量)** | 大流量来了不慢 / 不炸 / 不打穿 DB | 限流 / 缓存 / MQ / 分库分表 / 连接池 / 压测 | 06(限流)、07 + ../04-redis + ../05-mq |
| **🛡 高可用设计(扛故障)** | 部分异常时核心能力还能用 | 熔断 / 降级 / 隔离 / 重试 / 补偿 / 监控 / 灰度 | 06(熔断/降级)、08 |

**因果关系(环环相扣)**:

```
🧱 原理是地基  → 没原理就无从谈协同(CAP / 共识是物理边界)
       ↓
⚡ 性能解决"忙的时候不挂" → 大流量来了能扛(限流 / 缓存 / 削峰)
       ↓
🛡 可用解决"挂了不影响用户" → 真挂的时候有兜底(熔断 / 降级 / 多活)
```

> **三块缺一不可**:只有原理没性能 = 单机式集群,只有性能没可用 = 平时快关键时刻挂,只有可用没原理 = 故障状态都不一致。

## ★ 第四层:环环相扣——一次下单的完整防御链

> 三大块**不是孤立技术**,而是围绕同一个问题协作。看一次下单怎么把它们全串起来:

```
高并发流量进来
    ↓
1. 入口 限流(⚡)             —— 防打爆
    ↓
2. 查商品 走缓存(⚡)          —— 降 DB 压力
    ↓
3. 扣库存 Redis Lua(🧱 锁)    —— 并发安全
    ↓
4. 下单 MQ 削峰(⚡)           —— 保护数据库
    ↓
5. 消费 MQ 幂等(🧱 幂等)      —— 消息可能重复
    ↓
6. 支付回调 幂等(🧱 幂等)     —— 支付平台会重试
    ↓
7. 超时未支付 延迟消息释放库存(🧱 状态机) —— 不丢单不超卖
    ↓
8. Redis 挂了 降级/熔断(🛡)   —— 不拖垮全站
    ↓
9. 服务异常 监控告警 + 补偿对账(🛡) —— 止损 + 兜底
```

→ 这些点**不是散的**,它们围绕同一个核心问题:

> **大流量 + 不可靠网络 + 多服务协作下,业务怎么"正确 / 快速 / 稳定"地完成。**

→ 三大块是**同一个问题的三个侧面**:协同保证"正确",性能保证"快",可用保证"稳"。

## ★ 第五层:通用学习模板(7 问拷问法)⭐

学**任何新技术**(Raft / TCC / Redis / Kafka / etcd / Sentinel ……)都用 7 问自查:

| # | 问题 | 答得出 = 真理解 |
| --- | --- | --- |
| 1 | **它为什么出现?** | 没它之前痛点是什么 / 替代方案为什么不行 |
| 2 | **它解决什么问题?** | 一句话核心价值(< 30 字) |
| 3 | **它怎么解决?** | 核心机制 / 算法 / 数据结构 |
| 4 | **它有什么代价?** | 性能 / 一致 / 复杂度 / 学习成本损失 |
| 5 | **它适合什么场景?** | 业务规模 / 流量级别 / 一致性要求 |
| 6 | **它和其他技术怎么配合?** | 上下游 / 替代 / 互补关系 |
| 7 | **不用它会怎样?** | 反面假设,凸显不可替代性 |

> **死记 API = 假懂,答得出 7 个 = 资深。** 这是**整个知识库的元学习方法**,不只是分布式。

## 设计原则

- **图文并茂**,关键流程用 Mermaid
- **每篇独立可读**,不强制跨文件
- **场景驱动**:原理服务于"为什么 / 怎么用 / 坑在哪"
- **三层框架**:每块知识先回答"为什么"再讲"怎么做",拒绝平铺名词
- **7 问拷问**:学新技术先用 7 问自查,死记 API = 假懂
- **环环相扣**:孤立技术点要能拼回业务全链路,讲得出协作关系
